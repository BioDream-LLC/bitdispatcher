Del 1

Utrykningsstyring

Operatørens skjerm og alt som gjøres fra den: anrop, hendelser, enheter, kartet og kommandolinjen.

Kapittel 1

Komme i gang

bitdispatcher er et CAD-system (computer-aided dispatch) for 911-sentraler: ett program med sitt eget webgrensesnitt. Det oppretter og følger hendelser, anbefaler enheter etter kjøretid over veinettet, viser enheter, anrop og hendelser på et utrykningskart med flyfoto, gir feltmannskaper en mobil terminal, og registrerer hver handling i en manipuleringssikker hovedbok som rapporter bygges fra.

Den første timen

  1. Sign in som administrator med passordet som skrives ut ved første oppstart, og velg Administrator. Se Logge inn (kapittel 3).
  2. Spill inn kartet: Admin › Map, velg sentrum og radius, trykk Record. Omtrent to minutter for 100 miles. Open Map (kapittel 108)
  3. Stasjoner og enheter: hvor enheter er stasjonert og hva de er. Open Stations (kapittel 104) Open Units (kapittel 103)
  4. Anropstyper og utrykningskort: hva hver slags hendelse trenger. Standardverdiene er en fornuftig start. Open Call types (kapittel 106)
  5. Brukere: operatører, ledere og feltmannskaper. Open Users (kapittel 113)
  6. Anropshåndtering: koble til BitVoice, eller pek et hvilket som helst anropshåndteringssystems ALI-spill og EIDO mot bitdispatcher. Open Integrations (kapittel 111)

Admin › Setup checklist følger disse trinnene og resten av det som kommer før det første reelle anropet, og Admin › Go-live check tester resultatet. Se Selvbetjent oppsett (kapittel 97). Open the checklist (kapittel 98)

bitdispatcher gir råd; operatøren bestemmer. Ingen funksjon sender ut en enhet, lukker en hendelse eller endrer en prioritet på egen hånd.

Demomodus

Startet med -demo seeder bitdispatcher et fiktivt etat på kartet over Roanoke, Virginia (stasjoner på reelle stasjonsposisjoner, oppdiktede enheter). Med bvsim, en simulert BitVoice, ringer anrop og radioer melder posisjoner; alt som er simulert, er merket SIMULATED.

Kapittel 2

Installing it

Dette kapitlet ble endret etter at det ble oversatt, og vises på engelsk inntil oversettelsen er oppdatert.

bitdispatcher runs as a service on one computer, and every console opens it in a browser. Each installer sets it up to start with the computer, before anyone signs in, and shows the first administrator's password once, at the end. Upgrading means running a newer installer: the records, the settings and the users are kept. Uninstalling keeps the records unless you confirm twice that they should go.

Download them from the latest release at github.com/BioDream-LLC/bitdispatcher/releases, where SHA256SUMS lists each file's checksum. Or build them from the source on any computer with Go (see the README): make windows (needs NSIS), make linux and make macos (on a Mac) write them to the bin folder.

In every case the records folder is closed to everyone but the service and administrators: it holds criminal justice and personal information. The service listens on port 8443 (HTTPS) unless you choose another.

Windows

Run bitdispatcher-setup.exe and approve the administrator prompt. The pages: licence, what to install, the folder, Settings (the port and the records folder; a port another program holds is refused), and the First sign-in password. It adds a firewall rule for domain and private networks, and Start menu entries: bitdispatcher, its manual, and Reset admin password. It is removed from Settings › Apps.

For IT, a silent install: bitdispatcher-setup.exe /S /PORT=8443 /DATA=D:\bitdispatcher /NOFIREWALL (each option may be left out). A silent install shows no password: run Reset admin password afterwards. A silent uninstall keeps the records.

Linux

With the package manager: sudo apt install ./bitdispatcher_VERSION_amd64.deb or sudo dnf install ./bitdispatcher-VERSION-1.x86_64.rpm. The password is printed at the end. Without one: unpack the .tar.gz and run sudo ./install.sh, with --port 9443 for another port and --open-firewall to open it in ufw or firewalld; sudo ./uninstall.sh removes it, --purge deletes the records after you type DELETE twice.

Change the port or the records folder in /etc/default/bitdispatcher, then sudo systemctl restart bitdispatcher. A lost password: sudo systemctl stop bitdispatcher, sudo -u bitdispatcher bitdispatcher reset-password -data /var/lib/bitdispatcher admin, then start it again.

macOS

Open the .pkg and follow it. At the end a dialog shows the password, with Copy password and Open bitdispatcher. If port 8443 is taken it uses the first free port from 9443 and says so. It keeps the Mac awake while the service runs (a dispatch server must answer at any time; the display may still turn off): set BITDISPATCHER_KEEP_AWAKE=no in the settings file to let it sleep. If macOS's firewall is on, bitdispatcher is allowed through it.

Applications › bitdispatcher holds four things: bitdispatcher opens the console, Reset admin password, Uninstall bitdispatcher (it asks twice before deleting the records) and the manual. From Terminal: sudo installer -pkg FILE -target / installs without dialogs and leaves the password in /usr/local/etc/bitdispatcher.first-sign-in for root to read once; delete that file afterwards. After changing the settings file: sudo launchctl kickstart -k system/com.biodream.bitdispatcher.

The certificate

On first start bitdispatcher makes its own certificate, so each browser warns once until it trusts it. Give it one your network trusts with the -tls-cert and -tls-key options (on Linux and macOS in BITDISPATCHER_FLAGS in the settings file).

What has been tested

  • Windows: installing, three upgrades, the password reset and uninstalling, on one Windows desktop computer; and on every change, a silent install, upgrade and uninstall on Windows Server 2022 in CI.
  • Linux: the Intel .deb, .rpm and .tar.gz in Debian 12 and Red Hat UBI 9 containers running systemd (install, upgrade, reset, remove); the Arm ones in the same containers on an emulated Arm processor, not yet on Arm hardware; the .deb on Ubuntu 24.04 in CI.
  • macOS: installing, two upgrades, opening the console, the password reset and uninstalling with the records kept, on one Apple silicon Mac with macOS 26; in CI also a reinstall over the kept records and a full removal. Not yet on an Intel Mac, and not with macOS's firewall on.
  • Not signed. Windows SmartScreen warns about the installer, and macOS asks before opening a downloaded .pkg (System Settings › Privacy & Security › Open Anyway). Signed installers need code-signing certificates, which BioDream has not bought yet.

Kapittel 4

Anropsregistrering: anropsmottakerens arbeidsflate

I webgrensesnittet: /taker

En rolig arbeidsflate for anrop: anropslisten til venstre, de pågående anropene ved siden av, ti faner langs toppen med bare den valgte vist, og anropet (plasseringen, transkripsjonen og det som ble hørt) med narrative alltid til høyre.

Ovenfra og ned, i den rekkefølgen et anrop håndteres

  1. Anropet knytter seg selv til. Et anrop besvart ved din plass åpnes med én gang på anropsregistrering med sin ANI, ALI og enhver supplerende plassering, hver med sin kilde. Det trengs ikke et nytt valg av anropet. En oppmøtt person eller en radiorapport skrives inn uten et anrop.
  2. Hendelsesplasseringen først (se Steder og plassering (kapittel 38)): adressen, punktet på kartet, hvordan den er fastsatt (et verifisert adressepunkt, et estimert intervall, innringerens enhet, et kartpunkt, eller tvunget for denne hendelsen) og plasseringen inni den: navn på virksomhet eller bygning, kompleks, bygning, etasje, leilighet eller rom, og inngangs- eller portdetalj. Markeringer ved et verifisert sted vises med én gang, før anropet sendes, på hver fane.
  3. Innringeren og tilbakeringingen, lest tilbake og haket av som bekreftet.
  4. Anropstypen (skriv en kode eller et ord; piltaster og Enter velger), prioriteten og modifikatorene (noen hever prioriteten, noen legger til personer som skal varsles; de for personellsikkerhet vises i rødt).
  5. Send (F4 eller Ctrl+Enter). Narrative til høyre tar imot kommentarer hele veien: Enter legger til en kommentar med tidspunktet, det finnes ingen andre knapp. Kommentarer skrevet før sending følger med anropet.

Når noe anropet trenger mangler, navngir meldingen det, og markøren går til det feltet. Det eneste et anrop må ha for å kunne sendes, er typen; en ikke-verifisert eller tvunget plassering holder det aldri tilbake.

Flere pågående anrop

Til venstre for anropsregistreringen holder Working calls hvert pågående anrop i sin egen skjerm, opp til antallet etaten tillater for tjenesten (tre for en anropsmottaker med mindre noe annet er angitt). Hver beholder sin egen innringer, plassering, type, personer, kjøretøy og kommentarer.

  • Next call (F2 eller F5) åpner en ny anropsregistreringsskjerm og beholder den nåværende nøyaktig som den er, sendt eller ikke. Når etatens grense er nådd, spør den om et sendt anrop skal lukkes for å gi plass.
  • Et sendt anrop forblir åpent for flere kommentarer og oppdateringer fra innringeren til du trykker Close call (lukk anropet). Å sende, velge et annet anrop eller åpne en annen skjerm lukker det aldri.
  • Hver skjerm viser sitt nummer, typen eller hendelsen, stedet, hvor lenge det har vært åpent, ACTIVE, SENT, og ! når det fortsatt mangler en type eller adresse.
  • Å lukke en usendt skjerm med informasjon i spør først og spør hvorfor; protokollen registrerer hver som åpnes, flyttes, sendes, lukkes eller forkastes. De kommer tilbake etter en ny innlasting eller ved en annen konsoll.

Kapittel 5

Resources: godkjent veiledning sammen med anropet

Etter hvert som anropstypen, modifikatorene og det som sies endrer seg, finner Resources-fanen avsnittene i etatens godkjente retningslinjer, anropsveiledere, responsveiledere og sjekklister som gjelder, og lyser opp når det er noe nytt. Hvert avsnitt viser sitt dokument, sin seksjon, versjon og ikrafttredelsesdato, om det er policy (mandatory), en veileder, en sjekkliste eller foreslåtte spørsmål, og hvorfor det ga treff; The whole document åpner hele den godkjente teksten på den seksjonen. Utdaterte avsnitt og to retningslinjer som begge gjelder er merket. Når ingenting gjelder, sier den det.

Bare godkjent tekst vises, ord for ord; ingenting genereres. Å åpne fanen registrerer hvilke avsnitt, i hvilke versjoner, som ble vist for hendelsen, slik at en gjennomgåer senere ser hva som var tilgjengelig på tidspunktet. Dokumenter oppbevares i Godkjent veiledning (kapittel 119).

Kapittel 10

Utrykningsstyring: begrunnelser, advarsler, planer og kvittering

  • Send rec på en ventende hendelse i køen sender ut anbefalingen med ett trykk.
  • En begrunnelse. Å sende andre enheter enn anbefalingen spør hvorfor (hurtigvalg, eller dine egne ord); på kommandolinjen skriver du den etter en skråstrek: D E5 / closer by radio. Begrunnelsen og responsplanen som ble fulgt oppbevares med utsendingen.
  • Advarsler. Når plasseringen ikke er verifisert, er usikker eller mangler, sier anbefalingen fra, og du bekrefter før du sender.
  • Responsplaner. Når en plan (kapittel 107) gjelder, leder dens forventede rekkefølge; en planlagt enhet som ikke kan rykke ut er overstreket med hvorfor, og enheten som rykker ut i stedet sier hvem den tar plassen til. Når anbefalingen endres, vises endringen inntil du markerer den som sett.
  • Kvittering. En utsendt enhet som ikke har kvittert innen etatens sekunder blinker NO ACK; trykk på den (eller ACK E1) når den gjør det. Et mannskap kvitterer på terminalen sin.
  • Fakta fra anropsregistreringen på hendelsen: modifikatorer, personer og kjøretøy, en endret plassering (i gult i en halvtime), hvor innringeren er, BOLO-treff, talegruppen (TG FIRE-OPS2) og varsler som fortsatt skal gis, hvert med done.
  • Situasjon: vaktskiftets passdown-logg, aktive BOLO-er (utsted, kanseller; BOLO text på kommandolinjen; mannskaper ser dem) og facilities med åpne / omdirigering / lukket med ett trykk.

Kapittel 20

Enhetsanbefalinger

For den valgte hendelsen bygger bitdispatcher en anbefaling ut fra meldingstypens utrykningskort: for hver linje ("3 × engine", "1 × als") de tilgjengelige enhetene med den kapasiteten, nærmest først. Enheter som allerede er på hendelsen fyller linjene først, og sjeldne kapasiteter fylles før vanlige slik at en enhet med flere roller ikke brukes der en annen ville holdt.

  • Kjøretider kommer fra det registrerte veinettet: skiltede eller typiske hastigheter, enveiskjørte gater overholdes, fra enhetens ferske AVL-posisjon eller dens stasjon. Begrunnelsen sier det: "1.7 mi by road, 4 min via Franklin Road".
  • Stengte veier og trafikk teller med straks: en kjøretur går rundt en stengt vei (kapittel 25), og en vei som sanntidstrafikken melder som treg tar lengre tid. Kildelinjen under anbefalingen sier når de endret den ("around 1 road closure, with live traffic").
  • Utenfor det registrerte kartet, eller uten vei imellom, er tiden et anslag i luftlinje og merkes ~.
  • En enhet som dekker en annen stasjon rangeres ut fra der den er stasjonert.
  • Merknader varsler når ingen enhet har en kapasitet (vurder gjensidig bistand) eller når utsending av enhetene ville etterlate en stasjon tom.

De anbefalte enhetene velges ut; Dispatch (Ctrl Enter, eller REC) sender dem. Klikk på enheter for å endre valget, Use recommendation for å gå tilbake til det, eller skriv D E1 M2. Loggboken registrerer hva som ble anbefalt og hva som ble sendt.

Kapittel 21

Rådgivende forslag

Ved siden av hendelsen og på Situation-panelet kan det rådgivende panelet foreslå noe: to hendelser som kan være den samme, et anrop som kan handle om en åpen hendelse, ord som ikke passer anropstypen ("smoke" på en brannalarm, "not breathing" på et fall), en gjentatt adresse, en prioritet 1 fortsatt uten en enhet, en enhet på stedet man ikke har hørt fra.

  • Hvorfor: åpne et forslag for å se bevisene det bygde på (med kilden: enhet, innringer, operatør, maskin), hva det antok fraværende, og regelen i klartekst.
  • Cannot determine er et svar: når kilder av lik vekt er uenige ("smoke" og "no smoke" fra to innringere), sier det det og du bestemmer.
  • Accept kjører den foreslåtte kommandoen som deg (endre typen, knytt til anropet, send ut anbefalingen), eller noterer den bare. Reject med en begrunnelse på ett klikk; det vises ikke igjen. Begge registreres.
  • Det gir bare råd. Det slår aldri sammen, omklassifiserer, omprioriterer eller sender ut på egen hånd, og kjerneutrykningsstyringen virker likt når det er av eller nede.

Når en oppgradering leverer en ny regel (som *Silent or abandoned 911 call*), tilbyr Admin › Advisory panel den over reglene: Add it, så Save version. En lagret kodebok endres aldri av seg selv.

Kapittel 22

  • Når stasjonens egen enhet er tilbake, sender en Home-knapp dekningen hjem (RET E3).

Stengte veier og trafikk

En stengt vei endrer kjøretider og enhetsanbefalinger straks: ruteren går rundt den, uten at kartet bygges om.

  • Steng en strekning: høyreklikk på kartet på veien, Close a road from here, klikk deretter langs den stengte strekningen og Done. Si hvorfor, hvor lenge (tomt: til noen opphever den), omkjøringen, og om det skal noteres på den valgte hendelsen.
  • Steng et område: høyreklikk, Close the roads around here, og oppgi radiusen: hver vei med en del i sirkelen stenges (en flom, en brann, et åsted).
  • De stengte veiene tegnes med røde streker. Klikk på en for hvorfor og siden når, og Lift for å åpne den igjen. En stenging med et sluttidspunkt opphever seg selv.
  • En enhet kan likevel sendes til et sted på en stengt vei: der en kjøretur starter og slutter nektes aldri, bare veiene imellom.
  • Mannskaper ser veiene som er stengt nå, med omkjøringene, på den mobile terminalen (kapittel 48).
  • Sanntidstrafikk, når etaten har et datastrøm (Road closures & traffic (kapittel 89)), gjør veiene den melder tregere: en veis kjøretid er dens registrerte tid ganger hvor mye tregere den er, opptil ti ganger. Kildelinjen i en anbefaling sier når trafikk og stengninger endret den.
  • Hver stenging, endring og oppheving er en tilskrevet hendelse i loggboken.
Kapittel 26

Kameraer nær en hendelse

Når etaten har slått på kameraer (Kameraer (kapittel 90)), lister en hendelse med en kartposisjon Cameras near (kameraer nær): etatens kameraer innenfor radiusen, de som ser mot stedet først, med hvor langt unna og om de ser hitover.

  • Trykk på ett: det spør hvorfor (hendelsen, eller en grunn), og åpner det deretter. Et kamera med et stillbilde viser hva det ser nå, oppdatert hvert 5. sekund; ett med en live-visning åpner det i kamerasystemet, som logger deg inn selv.
  • Hver åpning registreres med hvem, når, hvorfor og hendelsen, og kommer på hendelsens tidslinje. Vaktledere ser registreringen i Admin › Cameras (kapittel 90).
  • bitdispatcher oppbevarer ingen video og registrerer ingenting fra kameraet; stillbildet hentes for den personen som åpnet kameraet, og bare i en halvtime.
Kapittel 27

Flyfoto

Operatører finner steder etter tak ("det hvite huset bak kirken"). Med Photos på (F7 eller knappen på kartet) er flyfoto grunnlaget og gatene, navnene og husnumrene tegnes over dem.

  • Foto spilles inn i Admin › Map: full detalj nær sentrum, mindre detalj ut mot kanten. Å zoome inn forbi det som ble spilt inn forstørrer fotoet under det, slik at kartet aldri blir tomt.
  • Brikken ved siden av knappen sier når fotoet i kartets sentrum ble tatt, der kilden publiserer det ("2023, 12 inch ortho"): et gammelt foto tas aldri for dagens.
  • Der ingenting er spilt inn, henter serveren fotoet når det bes om og beholder det, med mindre det er slått av.
Kapittel 28

Visninger: stedet fra alle sider

Flyfoto viser taket. Views viser forsiden, baksiden og sidene: hvor bakdøren er, gjerdet, trappen, siden hydranten er på.

  • Views på hendelsespanelet (ved siden av plasseringen), i anropsmottakerens Hazards-fane, på mannskapenes mobile terminal (kapittel 48), og fra et høyreklikk på kartet.
  • N E S W: de fire skråfotoene, som ser mot nord, øst, sør og vest, fra etatens egen EagleView-lisens. Å se mot nord viser sørsiden av en bygning. Piltastene dreier kompasset.
  • Street-foto som ser på stedet, nærmest først og høyst to per retning, fra Panoramax eller Mapillary (åpne foto, CC-BY-SA, dekning avhenger av hvem som har fotografert gaten).
  • Pre-plan-foto: etatens egne bilder av en eiendom (Knox-boksen, gassavstengningen, bakinngangen), frakoblet og på denne serveren. Mannskaper legger dem til fra terminalen med enhetens kamera, operatører og administratorer herfra eller fra Premises (kapittel 117); ledere fjerner dem.
  • Hvert bilde sier hvor det kom fra og når det ble tatt, slik at et gammelt bilde aldri tas for dagens. Utvid-knappen viser det i full størrelse.
  • Google Street View, når det tilbys, åpner Google i en ny fane; ingenting fra Google vises inne i bitdispatcher.
Å slå opp et sted forteller leverandøren hvor hendelsen er. Hver leverandør er av inntil en administrator slår den på i Integrations (kapittel 111), og bildene går gjennom denne serveren, slik at nøkler aldri når en nettleser.
Kapittel 29

Meldinger til og fra mannskapene

Meldinger går fra gulvet til mannskapenes terminaler, og fra mannskaper til utrykningsstyringen eller til en annen enhet, uten radioen.

  • Write i Messages (Situation-panelet): til én enhet eller flere (E1 M2), en disiplin (ALL-FIRE, ALL-EMS, ALL-POLICE) eller alle (ALL). La To stå tom for å skrive til enhetene på den valgte hendelsen. ! gjør den haster.
  • Kommandolinje: MSG E1 M2 / Stage at the north lot, MSG ALL-EMS ! Carilion on diversion, MSG #26-000123 / Caller says the back door is open.
  • Fra mannskapene: meldinger til utrykningsstyringen er uthevet inntil en operatør klikker på dem, og meldes etter hvert som de kommer. En melding på en hendelse skrives også på tidslinjen dens.
  • Read: terminalen markerer en melding lest når den vises (en som haster når mannskapet trykker Got it); gulvet ser *read by E1*, eller *not read yet* etter to minutter.
  • Hver melding og hver lesing er en hovedbokhendelse. Mannskaper skriver til utrykningsstyringen eller til enheter, aldri til alle.

For meldinger med et emne, prioritet, vedlegg, utløp og versjoner, og for BOLO-er og betjentsikkerhetsvarsler, bruk Meldinger og BOLO-er (kapittel 30).

Kapittel 30

Meldinger og BOLO-er: innboksen

En innboks som e-post inne i CAD, for messages, BOLOs, officer-safety og administrative varsler (konvolutten i statuslinjen; etaten kan legge til sine egne slag).

Å skrive en

Compose: slaget, priority, et emne og teksten (den vesentlige advarselen går i teksten, aldri bare i et vedlegg), To og CC, den eiende etaten, hendelsen og relaterte hendelser, og for en BOLO kjennemerket, kjøretøyet, personen og beskrivelsen. Adressater kan være enheter, ALL, ALL-FIRE, ALL-EMS, ALL-POLICE, DISPATCH, en etat (@agency:RPD: dens CAD-posisjoner og dens enheters terminaler), en rolle, en tjeneste, en navngitt person eller en konsoll. En BOLO uten noen navngitt går til hver posisjon og terminal til den eiende etaten. Attachments (bilder, PDF-er og de typene etaten tillater) kontrolleres etter innholdet, skannes der etaten kjører en virusskanner, og oppbevares med hashen sin. Effective- og expires-datoer; *no expiration* der etaten tillater det. Save draft holder den under Drafts.

Prioriteter

PrioritetViser og lyder
UrgentEt avbrytende banner og en gjentakende alarm inntil kvittert; ledere får beskjed når ingen kvitterer i tide
HighEt banner og en særegen tone; kvittering kan kreves, gjentas og eskaleres

Etaten setter hvert nivås tone, gjentakelse, kvittering og eskalering (Admin › Operations rules, der Play lar deg høre hver av dem). Tonene skiller seg ved rytme og styrke, ikke bare tonehøyde: alarmen er fem raske pulser, varselet tre, klangen to myke toner, tikket én stille puls, hver med overtoner slik at den bærer over et rom og gjennom et hodesett. Flere som kommer sammen lyder én gang, med tonen til den høyeste. Hver prioritet vises i ord og med et ikon, aldri bare med farge; bare nivåer etaten tillater kan dempes.

Nettlesere holder en side stille inntil noen har brukt den. Etter en ny innlasting slår det første tastetrykket eller klikket på lyden; inntil da sier et banner som haster the browser is keeping this console silent med en knapp for å slå på lydene.

Mapper, kvitteringer og versjoner

Inbox, Drafts, Sent, Active BOLOs og Archived (utløpte, kansellerte og erstattede, merket som sådan). Levering, åpning og kvittering registreres for personen og tjenesten de jobbet, ikke bare skjermen. Update sender en ny versjon og Cancel en kansellering; tidligere versjoner oppbevares, vises i historikken, og blir stående på hendelsens tidslinje med vedleggene (ikke lastet opp to ganger). En person ser en kommunikasjon bare når den er til dem, eller som leder eller arkivansatt i etaten dens. Alt er i hovedboken.

Kapittel 31

Søk: hendelser, BOLO-er, personer, kjøretøy og enheter

Ett søk (forstørrelsesglasset i statuslinjen, eller Recall i de klassiske tastene) på tvers av hendelser (nummer, type, adresse, narrative og kommentarer), meldinger og BOLO-er (hver versjon), personer (navn i hvilken som helst rekkefølge, aliaser, fødselsdatoer, telefoner, adresser, identifikatorer, beskrivelser), kjøretøy (kjennemerke, delvis kjennemerke med ? for et tegn du ikke kjenner, VIN, merke, modell, farge), vedlegg (filnavn, bildetekster, og ordene inne i dem: rene tekstfiler, teksten i PDF-er, og ordene i bilder der serveren leser dem) og enheter (kallesignal, radio-ID, hvem som er om bord).

  • Resultater grupperes, med filtre for slagene, etaten, datoene og statusen.
  • Hvert sier hvorfor det ga treff (samme kjennemerke, delvis VIN, delt telefon, lignende beskrivelse, *i filens tekst* med ordene rundt) og hvor sterkt: exact, partial eller similar (lignende skrivemåter når det bes om).
  • Possible matches er merket som sådan: et søk knytter aldri en person, et kjøretøy eller en hendelse til noe.
  • Utløpte, oppdaterte og kansellerte BOLO-er sier det med store bokstaver; en gammel advarsel ser aldri gjeldende ut.
  • Du søker i etatene du dekker og overvåker; beyond my agencies bare der du har lov til å jobbe dem, og hvert resultat navngir sin etat. Navn på mindreårige og medisinske merknader holdes tilbake fra folk uten rett til det, og ingenting begrenset telles eller vises.
  • Hvert søk, og hver post åpnet fra det, registreres i hovedboken.

Unit recall (fra en enhet i resultatene, eller en enhets History): én enhet over en periode, i én tidslinje: dens statuser og mark-outs, hendelsene med type og adresse, hvem som bemannet den og i hvilken posisjon, statussjekker, meldinger, og hvor den var etter AVL eller radio. Snevre den inn etter utrykningsenhet, status eller hendelse; last den ned som CSV.

Kapittel 32

Alarmer, skiltlesere og skuddeteksjon

Alarmselskaper, skiltlesere og skuddeteksjon sender varslene sine til bitdispatcher (Admin › Integrations; kontrakten er docs/ALERTS.md). Hvert varsel kommer inn i 911-anropslisten som et anrop, data only (kun data), med hva det er ved et raskt blikk: alarmtypen og sonen, VERIFIED når alarmselskapet verifiserte det, skiltet og dets overvåkingsliste, antall skudd.

  • Velg det: hendelsespanelet viser alt avsenderen oppga (eiendom, konto, bevilling, nøkkelansvarlig, operatørens tilbakeringingslinje, kameraet og retningen, en lenke til leserens bilde).
  • Lag hendelsen av det, eller knytt det til en, som fra et hvilket som helst anrop; etatens egne alarm- og skuddløsningstyper foreslås når de finnes.
  • En oppdatering fra avsenderen endrer samme anrop; en cancel (avbestilling) fra et alarmselskap kommer på hendelsen som en prioritert merknad.
  • Alarmselskaper får vite hva som ble av alarmen deres: akseptert, utsendt, på stedet, avsluttet.
  • Hver alarm kontrolleres mot etatens permit register (bevillingsregister): *Alarm permit P-1: valid*, *EXPIRED*, *SUSPENDED*, eller *none on the register*. Adressens falske alarmer det siste året telles; ved etatens grense sier merknaden REPEAT FALSE ALARMS (Alarmselskaper & bevillinger (kapittel 91)).
  • Phoned alarm (telefonmeldt alarm) (over 911-anropene): når en alarmselskapsoperatør ringer på telefon, skriv inn alarmen på alarmkortet (selskap, operatør, hendelsesnummer, alarm, sone, eiendom, adresse, bevilling, nøkkelansvarlig). Det kommer i køen som et innsendt, med de samme kontrollene, og sier hvem som skrev det inn.
  • Et varsel ingen handler på forlater køen etter 30 minutter; det blir værende i loggboken.
ASAP over Nlets, den nasjonale standarden for alarmer, er ikke koblet til ennå: den trenger standardens skjema og delstatens meldingssentral. Inntil da kan hvert selskap ha sin egen adresse og token over HTTPS (Alarmselskaper & bevillinger (kapittel 91)).

Stasjonsskjermen og utkalling med toner

I webgrensesnittet: /station

Når enheter sendes ut, kalles stasjonene deres ut med toner (der en administrator slo det på i Integrations). I brannstasjonen viser en skjerm på en skrivebeskyttet konto på #/station (velg stasjonen én gang; den huskes) stasjonens enheter og statusene deres, og ved et varsel:

  • stigende toner, dobbelt så mange for en prioritet 1, så anropet lest høyt to ganger: enhetene, anropstypen og gaten;
  • anropet i stor skrift: prioritet, type, adresse, enhetene, de siste prioritetsnotisene;
  • Acknowledge stopper det og setter *ST1 acknowledged the alert* på hendelsen; Read it again gjentar det.

Kapittel 34

Hendelser med naboetater

Hendelser går til og kommer fra naboetaters CAD-er som EIDO-er, NENA-standarden (Admin › Integrations › Neighbouring agencies; docs/CAD-TO-CAD.md).

  • Send: på en åpen hendelse, Send to a neighbouring agency…, velg etaten og si hvorfor (*mutual aid, need a ladder*; *on your side of the line*). Den går med plasseringen, tilbakeringingen, våre enheter på den og notisene; tidslinjen sier at den ble sendt.
  • Receive: det en nabo sender kommer inn i 911-anropslisten som et anrop fra den etaten, bare data, med deres hendelsesnummer, type og notiser. Lag hendelsen fra det eller knytt det til som fra et hvilket som helst anrop.
  • Hver sending er et trykk: lukking og enhetsstatus flyter ikke tilbake av seg selv her. For en nabo som også kjører bitdispatcher, går overflow (kapittel 76) lenger: de tar anrop for oss, og det hvert blir til kommer tilbake til dem.

Kapittel 38

Steder og plassering

Hendelsesstedet er stedet utrykningsmannskapene drar til, ikke bare gateadressen.

Hvordan plasseringen fastsettes

ValgBetyr
Verifisert adressepunktValgt fra etatens adressedata og bekreftet med innringeren
Estimert (adresseintervall)Adressesøket plasserte det langs et kvartalintervall
Innringerens enhetsplasseringTelefonens posisjon, uten eksakt adresse

Tvunget for denne hendelsen krever et punkt på kartet og en grunn fra etatens liste (og et notat når etaten ber om det). Bare tjenester etaten tillater kan tvinge en plassering; et avvist forsøk registreres på hendelsen, og anropsinformasjonen forblir som den var.

Plasseringen

Navn på virksomhet eller bygning, kompleks eller campus, bygning, etasje, leilighet eller rom (typen og nummeret) og inngang, port eller atkomstdetalj er egne felt. De er søkbare, og de avgjør hvilke markeringer som gjelder. En endring her endrer aldri etatens sentrale adresseregister.

Hva som skjer videre

Enhver slik plassering åpner et plasseringsavvik og varsler den vakthavende veilederen med én gang (se Veilederens gjennomgang (kapittel 44)). Når etaten senere verifiserer eller slår sammen adressen, kobles hendelsen til det sentrale punktet; det som ble lagt inn og det mannskapene fikk se, forblir i protokollen.

Kapittel 39

Markeringer for sted og sikkerhet

I webgrensesnittet: /admin/flags

En markering er etatens advarsel om en verifisert adresse eller en person: sted, plassering, fare, personellsikkerhet, medisinsk, virksomhet, nøkkelholder eller vedlikehold, usikker bygning, vold i nære relasjoner, farlig dyr, valglokale, evakueringssted (etaten kan gi nytt navn til, legge til eller slå av kategorier).

  • Omfang: hver markering plasseres på det snevrest riktige stedet: hele eiendommen, et kompleks, en navngitt virksomhet, en bygning, en etasje eller én leilighet. En leilighets advarsel vises aldri for resten av komplekset.
  • Når den vises: så snart anropsmottakeren verifiserer adressen, før anropet sendes, som en linje på hver fane, deretter på operatørens hendelse og på den mobile terminalen. Kritiske og høye markeringer står i den linjen; Hazards-fanen (Farer) lister opp hver enkelt med hva mannskapene bør gjøre.
  • Hva den sier: alvorlighet og kategori i ord, en tittel, hva bekymringen er og hvorfor, og hva mannskapene bør gjøre. Åpne den for kilden og detaljene.
  • Begrensede kategorier (medisinsk, vold i nære relasjoner, personellsikkerhet, nøkkelholder): de etaten ikke tillater, ser advarselen og hva som skal gjøres, ikke grunnen eller kilden. Åpning av detaljen registreres; en avvist forespørsel også.
  • Versjoner: å endre, fornye, pensjonere eller gjenopprette en markering lager en ny versjon. Hver hendelse beholder versjonen den viste, slik at senere endringer aldri skriver om det operatørene så.
  • Ikke-verifiserte plasseringer får aldri en permanent markering. Markeringer nær et ikke-verifisert punkt vises bare som POSSIBLE MATCH NEARBY (mulig treff i nærheten); et notat som bare gjelder hendelsen, kan beholdes i stedet.
  • Hvem som kan: hver kategori angir hvilke tjenester som oppretter, godkjenner og ser den. Andre (og opplæringskandidater) foreslår; en veileder godkjenner eller avviser. To markeringer av samme kategori på samme omfang vises for en avgjørelse, i stedet for at den ene overskriver den andre.

Legg til en markering fra anropsregistrering (Hazards, Add a flag or a note for this place (legg til en markering eller et notat for dette stedet)) eller her i Admin, der foreslåtte markeringer venter på godkjenning. Åpne Flags (kapittel 39)

Kapittel 40

Personer og kjøretøy

Personer, ovenfra og ned

Rollen (mer enn én når det passer), så First, Middle and Last name (fornavn, mellomnavn og etternavn) i egne felt, suffiks og alias; hvor personen er (hendelsen, et annet sted med bygning, etasje og enhet, ukjent, uten fast bopel); telefonnumre (flere, med type, internnummer, kilde og om de er verifisert); signalementet samlet (kjønn, rase, etnisitet, høyde, vekt, kroppsbygning, hår, øyne, klær, arr, merker og tatoveringer, med de godkjente kodene); deretter identifikatorene: personnummer, førerkort og delstat, annen legitimasjon, fødselsdato og, separat, en oppgitt omtrentlig alder. Alderen regnes ut fra fødselsdatoen. Notater til slutt.

Officer-safety concern (bekymring for personellsikkerhet) åpner en obligatorisk del: en kort varseltittel, hva som skjedde og hvorfor det er en bekymring, våpen eller trussel, hva mannskapene bør gjøre, kilden og dens pålitelighet. Det kan ikke lagres uten dem. Velg This incident only (bare denne hendelsen) eller Propose a permanent warning (foreslå en permanent advarsel): et forslag går til etatens gjennomgang som en personmarkering. Overalt vises varselet som OFFICER SAFETY: og tittelen, og åpner til grunnen, kilden og instruksjonen.

Search (søk) i hver navnedel for seg (fornavnet John finner hver John), med fødselsdato, omtrentlig alder, telefon, adresse, førerkort, kjønn, rase, et tilknyttet skilt, lyder-som og delvis treff. Possible same person (mulig samme person) vises mens du skriver et navn og blokkerer aldri lagring.

Personnummer og førerkortnummer vises maskert på hver delt skjerm. Open (recorded) (åpne, registrert) viser dem til de tjenestene etaten tillater, med formålet registrert.

Kjøretøy, ovenfra og ned

Rollene (mistenkt, offer, stjålet, gjenfunnet, trafikkontroll, bevis, tauet og flere), skiltet med etatens delstat først, skilttypen og tilstanden (midlertidig, delvis, uleselig, ingen, flere), VIN (kontrollert mens du skriver; en delvis VIN beholdes med et notat), så Run DMV (kjør DMV) eller Run NCIC (kjør NCIC) når skiltet og delstaten eller en full VIN er inne. Svaret knyttes til det kjøretøyet med tidspunkt, hvem som kjørte det og hvem som ba om det. Offisielle verdier vises ved siden av det som ble oppgitt, og en forskjell navngis; ingenting som er oppgitt, overskrives. En ny kjøring er en ny versjon.

Koble sjåfører, eiere, leietakere, passasjerer og personer i kjøretøyet til personer på anropet; hver person viser også sine kjøretøy. Et mulig stjålet eller etterlyst treff vises som POSSIBLE HIT: not confirmed (mulig treff: ikke bekreftet) inntil en treffbekreftelse er besvart (se NCIC- og delstatsforespørsler (kapittel 41)).

Tow (tauing) på et kjøretøy åpner tauingen for det kjøretøyet: neste firma i etatens rotasjon øverst med telefon og siste tur, så Accepted (akseptert), Declined (avslått, med grunn) eller No answer (ikke svar), tidspunktet for hvert trinn, sjåføren, bilen, lagringsplassen, inntauingsnummeret, holdet og utleveringsbegrensningen. Et firma som avslår, mister turen og det neste tilbys. Hvert kjøretøy beholder sine egne tauinger. På kommandolinjen SE.AD6 så F10 åpner den samme tauingen for AD6 på den valgte hendelsen og spør hvilket kjøretøy.

Kapittel 44

Veilederens gjennomgang

I webgrensesnittet: /supervisor

Én skjerm for veilederens gjennomgangsarbeid, i faner. Hvert element blir værende til det er behandlet.

Plasseringsavvik

Enhver tvunget, estimert eller på annen måte ikke-verifisert hendelsesplassering varsler den vakthavende veilederen med én gang (en melding som haster eller er høy) og venter her med det som ble skrevet, den aksepterte plasseringen og kartpunktet, kilden og konfidensen, de nærmeste verifiserte alternativene, innringerens koordinater, hvem som la den inn ved hvilken plass, grunnen, enhetene og hendelsesstatusen. Å åpne hendelsen fjerner den ikke. Acknowledge (kvitter ut), og svar så på to separate spørsmål:

  1. Ble den beste tilgjengelige plasseringsinformasjonen brukt? Ja, eller nei med hva som var bedre.
  2. Trenger etatens adressekilde eller arbeidsflyt oppfølging? Ingen videre handling, Send inn en adresse- eller GIS-oppdatering, Rett eller slå sammen den sentrale oppføringen, Henvis til en annen jurisdiksjon, Opplærings- eller arbeidsflytgjennomgang, Systemfeil eller Oppfølging pågår, hver med en eier og en frist, så done (ferdig).

Adressekøen fører den gjennom New, Under review (under vurdering), Verified (verifisert), Rejected (avvist) eller Merged (sammenslått); å verifisere eller slå sammen kobler hendelsen til den sentrale adressen (operatørene og enhetene på en aktiv hendelse ser endringen) og beholder det som ble lagt inn.

Kritiske hendelser

Etaten bestemmer hvilke anropstyper, modifikatorer, prioriteter, hendelser (en enhetsnødssituasjon) og fraser som gjør en hendelse kritisk (Admin › Critical incidents). En utløser varsler veilederen og åpner én gjennomgang per hendelse; flere utløsere legges til den. En veileder kan også merke en hendelse som kritisk, eller fjerne den, med en grunn; utløserne blir værende i protokollen.

Open full review (åpne full gjennomgang) setter den sammen når det bes om det: kildeoversikten, personene og deres tjenester, milepæler i anropshåndteringen med hendelsen hver kommer fra, hver enhets tider, merket radiotrafikk (maskinmerker, bare et hjelpemiddel), forespørsler (metadata), QA-matrisen og bevisbegrensningene. Hver beregnede tid viser hendelsene den ble målt mellom. Besvar hvert QA-mål med Met (oppfylt), Not met (ikke oppfylt), Not applicable (ikke aktuelt), Unable to determine (umulig å avgjøre) eller Needs follow-up (trenger oppfølging) med en kommentar og beviset det hviler på. Velg en bevisgrense og Issue (utsted) en versjon (dens hash beholdes); senere bevis lager en ny versjon. Records-request copy (kopi for innsynsbegjæring) og Accreditation copy (kopi for akkreditering) anvender etatens offentliggjøringsregler på en egen kopi med en sladdelogg; selve gjennomgangen endres aldri. Offer support (tilby støtte) og Open after-action (åpne etterevaluering) registrerer bare operasjonelle handlinger; ingen klinisk eller velferdsrelatert detalj går inn i CAD.

Fravarsler

Konfigurerte fraser som høres i anrops- eller radiotranskripsjoner eller skrives i narrativet, varsler veilederen med konteksten, kilden, kanalen, taleren og tidspunktet. En negert frase («ingen skudd avfyrt») merkes NEGATED (negert) for gjennomgang, og en med lav konfidens UNCERTAIN (usikker). Avgjør hver enkelt: Reviewed no action (gjennomgått ingen handling), Critical incident opened (kritisk hendelse åpnet), Linked to existing review (koblet til en eksisterende gjennomgang), False positive (falskt treff) eller Follow-up required (oppfølging kreves).

Shift Intelligence

En rapport for hver driftsperiode (Admin › Call entry rules fastsetter periodene), satt sammen fra protokollen: større og åpne hendelser, plasseringsavvik og gjennomgangen av dem, kritiske hendelser, nye og kritiske markeringer, BOLO-er og meldinger som haster, enheter med for lite bemanning, forfalte statuskontroller, åpne forespørsler og oppfølgingen som skyldes, hver med sin kilde, tid, status, eier, frist og neste handling. Kjør den for nåværende periode, en tidligere eller et egendefinert intervall. Legg til veilederens sammendrag og overleveringsnotater (holdt atskilt fra fakta) og Finalize (ferdigstill); senere endringer er tillegg med en grunn. Den påtroppende veilederen acknowledges (kvitterer ut) og aksepterer eller omfordeler hver åpne oppfølging, som føres videre, ett element per kilde, til den er ferdig. Begrenset detalj vises bare til dem som har tillatelse.

Personer

Hver persons periode: tjenester og plasser, pålogginger, besvarte anrop og tidene for dem, opprettede hendelser, utkallinger, statusendringer, forespørsler, kritiske hendelser og deres del i dem, formelle pauser og, atskilt fra dem, konsolllåser (en lås er ikke en pause). Et mulig gap i arbeidsdelingen vises som en gjennomgangsoppfordring med konteksten som forklarer det, aldri som en poengsum eller en rangering. Personer legger til kontekst eller rettelser i sin egen oppføring.

Oppfølging og tastetester

Hver sporet oppfølging, med sin historikk, eier og frist; og hver arbeidsstasjons siste tastetest (kapittel 43).

Kapittel 49

Hendelsesrapporter (RMS)

I webgrensesnittet: /rms

Betjenter og operatører skriver hendelsesrapporter på #/rms, eller med Report på en hendelse (hendelsens plassering og tid fylles inn). Et mannskap på en mobil terminal skriver sin egen fra bilen.

  • Seksjoner: når og hvor (plasseringstype, om det ble avklart), lovbrudd, personer, eiendom, kjøretøy og narrative. Koder vises i ord og velges med ett klikk; skjermen spør bare om det lovbruddet trenger (et våpen for et overfall, inntrengingsmåten for et innbrudd, stoffet for et beslag, skaden og forholdet til hver mistenkt for et lovbrudd mot en person).
  • Lagret mens du skriver: et utkast lagrer seg selv et øyeblikk etter at skrivingen stopper.
  • Before it is submitted lister hva som fortsatt mangler for hendelsesbasert rapportering: FBIs NIBRS-dataelementer og -kontroller, med Virginias tillegg (eiendomsmengde, indikatoren for kjennemerkeleser, stofftyper). Submit er tilgjengelig når listen er tom.
  • Approval: en annen leder enn forfatteren godkjenner den, eller returnerer den med hva som skal rettes. Hver lagring og beslutning er en hovedbokhendelse.

Delstatsfilen

Ledere ser State IBR file under listen. Velg måneden og trykk File: bitdispatcher skriver månedens godkjente rapporter i Virginias hendelsesbaserte rapporteringsformat (FBIs posisjonsbaserte flate fil med Virginias tillegg, 2025.2-spesifikasjonen): Group A-hendelser med sine lovbrudds-, eiendoms-, offer-, gjerningsperson- og pågrepet-segmenter, Group B-pågripelser, eller en nullrapport når det ikke er noe. Last den opp til Virginia Crime Repository innen den 15. i neste måned. Rapporter som ikke består kontrollene utelates og listes. Å lage filen er en hovedbokhendelse, med sin SHA-256.

Format: FBI national skriver de samme rapportene i FBIs eget flat-fil-oppsett, uten Virginias tillegg, for delstater som tar den nasjonale filen. Den filen er kontrollert med SEARCHs NIBRS Pre-Certification Tool-validator, som anvender FBIs kontroller (scripts/nibrs-validator.sh); å bestå den er ikke FBI- eller delstatssertifisering.

Transkripsjoner og det som ble hørt

Kapittel 66

Admin: Drones

I webgrensesnittet: /admin/drones
Dette kapitlet ble endret etter at det ble oversatt, og vises på engelsk inntil oversettelsen er oppdatert.

Drones bitdispatcher flies itself, over MAVLink, the protocol of the PX4 and ArduPilot autopilots. Each drone has:

  • MAVLink link: udp-listen:0.0.0.0:14550, udp:host:port, tcp:host:port or serial:/dev/ttyUSB0:57600, and the autopilot's system id (0 takes the first one heard).
  • Signing key: 64 hex digits for MAVLink 2 signing. Turn it on: without it anyone who can reach the link can command the drone. A drone signing with another key is ignored.
  • Camera: an RTSP address for H.264 video. The password is masked here and never logged.
  • Height (10 to 120 m) and the lowest battery for a launch.
  • Needs pilot approval and the pilots: listed pilots approve a launch; with none listed, supervisors do. A launch rule always waits for a person.
  • Record video: while the drone is on an incident its video is kept with the incident, with its size and SHA-256 written to the ledger every 10 seconds. A recording that no longer matches is not served.

On an incident, Send a drone picks the nearest ready drone. Dispatchers can press Hold or Return home; the pilot's own controller can take over at any time. Training boards never fly real drones. Check Part 107, Remote ID and your state's drone laws before flying.

Tested with the bundled simulator (bin/dronesim) only, not yet a real drone. Details in docs/DRONES.md. Open Drones (kapittel 66)

Kapittel 69

Kritiske anrop og omsorg

Noen anrop blir hos folkene som tar dem. En hendelse er et critical call når anropstypen er merket kritisk (hjertestans, skyting og knivstikking til å begynne med) eller når ord som puster ikke, HLR, politi skadet eller spedbarn sies på den.

  • Alle som arbeidet med den (anropsmottakeren og operatørene som registrerte, sendte eller noterte) går på care list på ledertavlen (kapittel 51), med begrunnelsen.
  • Lederen tilbyr en pause til hver person, arrangerer en gjennomgang (med en merknad om når og hvor) og markerer den Done. Hvert registreres.
  • Når hendelsen lukkes, ser hver person en stille linje på sin egen konsoll: det var et vanskelig anrop, ta et øyeblikk, og støttelinjen satt i Settings. Take a break setter dem på pause.
  • Sett ordene, støttelinjen og anropstypene i Admin › Settings (kapittel 110) og Call types (kapittel 106).
Kapittel 70

Pauser og arbeidsmengde

Koppen på statuslinjen setter deg på pause og tilbake; ledertavlen viser det.

Tavlens People-panel lister hver innlogget posisjon: anrop den siste timen, handlinger, tid siden siste pause, kritiske anrop på fire timer, og en tilstand:

  • watch: to timer uten en pause (Settings), et kritisk anrop, eller en svært travel time;
  • relieve: tre timer uten en pause, eller to kritiske anrop.

Den navngir de minst travle posisjonene som er ledige til å avløse noen.

Kapittel 71

Opplæring

Hak av Training når du logger inn. Konsollen åpner en egen tavle, merket TRAINING i fiolett: etatens enheter, stasjoner, anropstyper, eiendommer og kart, på en egen hovedbok. Hver opplæringskandidat har sin egen tavle, selv på en delt konto; en som står ubrukt i to timer tømmes. Ingenting gjort der når den levende tavlen. Administrasjon der er klargjøring: en administrators endringer blir på opplæringstavlen inntil de publiseres (se Øvelser, injects og klargjøring (kapittel 72)); brukere, tilkoblinger og kart tilhører den levende tavlen.

  • Scenarios spiller anrop, transkripsjoner, kollisjonsdata og radiotrafikk inn i den på etatens eget kart: en husbrann med tre innringere, en hjertestans på spansk, en motorveikollisjon med kollisjonsdata, et væpnet ran, og en flom av anrop på linjen.
  • Score kontrollerer hva som ble gjort: hver innringer på en hendelse, anropstypen, enhetene sendt, et svar på innringerens språk, og hver hendelses kvalitetsgjennomgang (kapittel 73).
  • Reset tømmer tavlen din og starter den på nytt; andre opplæringskandidaters tavler er urørt.
Kapittel 72

Øvelser, injects og klargjøring

En øvelse er én opplæringstavle for alle som blir med på den: hak av Training ved innlogging og skriv øvelsens navn (et hvilket som helst navn; den første som blir med lager den). Opplæringskandidater logger inn med sine egne tjenester, slik at en anropsmottaker, operatører og en leder jobber den sammen, og mannskaper kan bli med på den mobile terminalen (kapittel 48) på samme måte. Øver du alene, la navnet stå tomt.

Instruktøren (en leder eller administrator) trykker Inject: en ny innringer (hvor, hvem, og hva de sier mens øvelsen pågår), innringeren som sier mer eller beveger seg, en enhet som går ut av tjeneste, en nødknapp, eller en enhet på radioen. Timeline laster ned hver hendelse for gjennomgangen, og når øvelsen slutter beholdes tidslinjen dens (Supervisors: /api/exercises).

Klargjøring. En administrator innlogget med Training endrer anropstyper, enheter, stasjoner, responsplaner, veiledning eller fasiliteter på opplæringstavlen, prøver dem der, og åpner så Staged changes: den lister hva som avviker fra den levende tavlen; velg delene, si hvorfor, og Publish. Med *Change configuration only through staging* på (Settings) kan de endringene ikke gjøres på den levende tavlen direkte.

Opplæringstavlen er ikke en sikkerhetskopi av den levende tavlen. Et kontinuitetssted er en separat, testet ordning: se Flere steder (kapittel 115).

Kapittel 74

Å jobbe gjennom et driftsbrudd

Hver konsoll beholder den siste tavlen den hadde. Når serveren ikke kan nås, sier en gul linje det, og konsollen viser den tavlen, slik den var, med tidspunktet. En konsoll som lastes inn på nytt under driftsbruddet åpnes fortsatt.

  • Offline log: nye hendelser, notiser og enhetsstatuser oppbevares i denne nettleseren, i rekkefølge.
  • Når serveren er tilbake tilbyr linjen Send them now: hver går inn merket "entered offline at 14:02 by jlee"; alt serveren avviser blir stående, med begrunnelsen.
  • For en server som aldri går bort, kjør bitdispatcher på to steder (Flere steder (kapittel 115)): hvert fortsetter å virke når det andre er avskåret.
  • Når internett, og ikke serveren, er borte, eller sentralen må forlate bygningen sin, se Continuity (kapittel 75).
Kapittel 75

Kontinuitet: driftsbrudd og reservestedet

I webgrensesnittet: /continuity

Continuity-siden (redningsbøye-knappen i statuslinjen, eller en brikke der når noe er galt) er det som holder sentralen i gang når en forbindelse eller bygningen går tapt.

Når internett går

bitdispatcher kjører på sentralens egen server, så det å miste internett stopper ikke utrykningsstyringen. Anropsregistrering, hendelser, enheter, det innspilte gatekartet, ruting og adresser, hovedboken og utskrift fortsetter å virke.

  • Det som venter på internett: online kartfliser, Street View og flyfoto som ikke er spilt inn, trafikk, kartoppdateringer, nabosentraler og overflow, NERIS, PSC PIP, og BitVoice eller personsøk når de nås over internett.
  • bitdispatcher sjekker adressene en administrator setter (Admin › Continuity (kapittel 116)), BitVoice, de andre stedene og hver overflow-nabo. Når ingen av internettsjekkene svarer, viser hver konsoll Internet down i rødt og veilederne får en melding; en annen forbindelse nede vises som en gul brikke.
  • Hver forbindelse som går ned og kommer tilbake er i hovedboken; siden lister forbindelsene og driftsbruddene.

Flytting til reservestedet

Når sentralen må forlate bygningen sin, går personalet til reservestedet: et annet bitdispatcher-sted fylket eier eller kjører i skyen (Flere steder (kapittel 115)). Det holder allerede hver post, så arbeidet fortsetter der det var.

  1. På reservestedet trykker en veileder We are working from the backup site, med en merknad. Hver konsoll på hvert sted viser At backup site, og alle på vakt får en melding.
  2. Sjekklisten satt i Admin › Continuity hakes av etter hvert som den gjøres (omruting av 911, radiokontrollstasjoner, beskjed til felt); hver avhuking er i hovedboken.
  3. Tilbake hjemme avslutter We are back in our building det.
911-anropene når reservestedet bare når telefonnettet sender dem dit: 911-myndighetens alternative ruting, eller BitVoices ruting i NG911. bitdispatcher kan ikke flytte anropene selv.

Kontinuitetspakken

Open to print gir en side med de åpne hendelsene (med innringernes navn og tilbakeringinger), hver enhet og dens status, sjekklisten, kontaktene og blanke loggelinjer, for å jobbe på papir hvis CAD ikke kan nås i det hele tatt. Den kan skrives etter en tidsplan til mapper en administrator setter: en delt stasjon eller en USB-disk på en annen maskin beholder en fersk kopi hvis denne serveren går tapt. Behandle utskrifter som poster.

Kapittel 76

Overflow til en nabosentral

I webgrensesnittet: /overflow

Når sentralen er overveldet, eller ute av bygningen sin, kan en nabosentral som også kjører bitdispatcher ta anropene dens; og denne sentralen kan ta deres. Det settes opp for hver nabo i Admin › Continuity (kapittel 116), etter at begge sentralene har avtalt det skriftlig.

Å be om hjelp

  1. På Overflow-siden trykker en veileder Ask (neighbour) to take our calls, sier hvorfor og for hvor lenge (4 timer med mindre annet er angitt).
  2. Naboens veileder aksepterer eller avslår; en nabo hvis innstillinger aksepterer av seg selv starter med én gang. Begge sentralenes statuslinjer viser det: *(neighbour) is taking our calls*.
  3. Hvert anrop de tar blir en hendelse her, under våre numre og anropstyper, merket Taken for us by (neighbour) med navnet på anropsmottakeren deres. Våre operatører sender våre enheter, med mindre vi lar naboen tildele dem også.
  4. En veileder ved en av sentralene trykker End når det er over.

Å ta anrop for en nabo

Mens det varer, viser Overflow-siden Take a call for (neighbour): plasseringen, anropstypen deres, innringeren, tilbakeringingen og det som skjedde. Send lager hendelsen i CAD-en deres og viser nummeret.

  • Det anropet blir til kommer tilbake: statusen, enhetene på det, notisene deres og lukkingen. Notiser lagt til her går til dem.
  • Hvis de lar oss, lister Their units deres tilgjengelige enheter å tildele.
  • Hvis CAD-en deres ikke kan nås, holdes anropet her og sendes igjen hvert 20. sekund; si fra til dem per radio eller telefon hvis det haster.

Hva som krysser

Bare anropene naboen tar, og det de blir til: ingen andre hendelser, ingen poster, ingen personhistorikk, ingen NCIC-svar. Hver forespørsel, svar, anrop, notis og tildeling er i begge sentralenes hovedbøker.

Selve 911-anropene når naboen gjennom telefonnettets alternative ruting, som 911-myndigheten setter opp, eller gjennom BitVoices ruting i NG911. Overflow bærer arbeidet, ikke anropene.
Kapittel 77

Linjeangrep (TDoS)

Et telefoni-tjenestenektsangrep fyller linjene slik at reelle innringere ikke kommer gjennom. bitdispatcher overvåker anropene og reiser Possible telephony denial-of-service på hver konsoll og ledertavlen når:

  • langt flere anrop kommer på et minutt enn vanlig (fem ganger den siste timens rate, minst 12, eller antallet satt i Settings);
  • ett nummer ringer fem ganger eller mer på ti minutter (vist som ×5 på anropene sine);
  • åtte eller flere stille eller svært korte anrop kommer på fem minutter.

En leder kvitterer det; det nullstilles etter ti rolige minutter. Fortsett å svare: en reell nødsituasjon kan være blant dem.

Kapittel 79

Alarmnivåer: 2nd- og 3rd-alarmer

En brann under utvikling vokser fra sitt første utrykningskort. Hver anropstype kan ha further alarms (Admin › Call types): 2nd-alarmen, 3rd, hver legger enheter til det hendelsen trenger. Den første alarmen er anropstypens eget utrykningskort.

Oppgradering

  • På hendelsen sier Upgrade to 2nd alarm hva den legger til (+2 engine, 1 ladder…); eller skriv ALARM (2ND, 3RD, ALARM 3 for et nivå).
  • Oppgraderingen er en prioritetslinje på tidslinjen hver operatør og mannskap ser, med hva den legger til.
  • Anbefalingen fyller så det større utrykningskortet, teller enhetene som allerede er der, og REC (eller Ctrl Enter) sender de ekstra enhetene. Utkallingsgrupper og stasjonsvarsler følger utsendingen som vanlig.
  • Bring down går et nivå tilbake, med en begrunnelse.
Oppsett: Admin › Call types › en type › Further alarms. Hver alarm har et navn og utrykningskortlinjer (kapabilitet og antall). Structure fire-typen kommer med en 2nd- og 3rd-alarm å redigere.
Kapittel 80

Personell og mannskaper

I webgrensesnittet: /admin/personnel

Rosteren er etatens folk: et nummer, navn, grad, kvalifikasjoner (paramedic, EMT, sjåfør, betjent…), hjemstasjon, og hvordan de kalles ut (en telefon for tekstmeldinger, en e-post, et push-emne). Legg dem til én etter én eller Import from CSV (kolonner: id, navn, grad, kvalifikasjoner skilt med ;, stasjon, telefon, e-post, frivillig).

Hvem som er om bord

På en hvilken som helst enhet (enhetens panel › Crew › change) eller fra mannskapets egen terminal (Crew), velg hvem som kjører den denne vakten. Et medlem er på én enhet om gangen: å sette dem på en annen flytter dem. Hendelsens tidslinje registrerer mannskapsendringer på en enhet som jobber den.

Hva bemanning endrer

  • Minimum aboard (Admin › Settings › Unit types, eller per enhet i Admin › Units): en enhet under det vises underbemannet, i anbefalingens begrunnelser og på lederens unntak.
  • What a capability needs (Admin › Settings › Crews): som standard trenger ALS en paramedic om bord. En medic-enhet hvis registrerte mannskap ikke har en paramedic anbefales ikke for en ALS-linje (den er fortsatt BLS og transport).
  • En enhet med no crew recorded regnes som bemannet: en etat som ikke fører rostere her ser ingen endring.
Operatører ser rosteren uten telefonnumre og e-poster; ledere ser dem.
Kapittel 81

Bemanning: hvem som er på vakt og på hver enhet

I webgrensesnittet: /staffing

Staffing (folk-knappen i statuslinjen) viser hvem som er på vakt, hvor, og hvem som faktisk bemanner hver enhet. Et kallesignal alene er ikke nok: mannskapet følger enheten inn i hendelser, anbefalinger, historikk og rapporter.

Folk på vakt

Sign on med slaget tjeneste (ordinær, overtid, forlenget vakt, et midlertidig oppdrag og hvor, en tilbakekalling), vakten, til når og tilgjengelighet (tilgjengelig, tildelt, utilgjengelig, opplæring, rett, måltid, stasjonstjeneste, administrativ). Sign off fjerner personen fra enhver enhet. Søk etter navn, kvalifikasjon, etat, stasjon, enhet og tilgjengelighet.

Mannskaper

Edit crew navngir folkene på en enhet og deres posisjoner (sjåfør, betjent, brannmann, medic, partner, teamleder, eller etatens). Slaget enhet kan kreve posisjoner og et minimum (Admin › Settings › Unit types). Et mannskap kan logge seg selv på fra terminalen; etaten bestemmer per slag enhet om det er tillatt, trenger en leders godkjenning (Sign-ons waiting) eller er bare for utrykningsstyringen.

  • Én person er på én aktiv enhet om gangen. Å sette dem på en annen spør: move them (avløsning, et bytte) eller et secondary assignment med en begrunnelse.
  • Hver endring har en begrunnelse og en effective-tid, oppbevart ved siden av når den ble registrert.
  • En enhet etterlatt knapp (under minimumet sitt, en posisjon tom) er limited, eller satt out of service, slik etaten sier, med mindre en leder registrerer et override med en begrunnelse.
  • Et tapt samband logger ingen av.

På hendelser og senere

Når en enhet tildeles, beholder hendelsen hvem som var om bord og hva de var kvalifisert for i det øyeblikket; senere endringer skriver det aldri om, og endringer under hendelsen (hvem som kom til, hvem som dro, posisjoner) er på tidslinjen dens. En leder kan correct en mannskapspost med en begrunnelse: originalen blir værende ved siden av rettingen, med de registrerte og effektive tidene. Unit recall og rapporter viser folkene så vel som kallesignalet.

Ledere ser også saved crews for et shift change i ett trinn (hver person og tid fortsatt registrert), og coverage: minimum antall kvalifiserte folk etaten vil ha på vakt, mangler, utløpende sertifiseringer og hver enhets kapabilitet (en ledervisning etaten kontrollerer).

Kapittel 82

Kvalifikasjoner, spesialteam og sertifiseringer

I webgrensesnittet: /admin/qualifications

Hver etat fører en kontrollert ferdighetsfil (Admin › Qualifications & teams; ledere).

  • Qualifications: spesialteam (Swift Water, HazMat, Technical Rescue, Dive, K-9, SWAT, UAS), spesialiteter (bevistekniker, brannetterforsker, kriseforhandler, taktisk operatør), opplæringsroller (CTO, FTO, instruktør, evaluator) og sertifiseringer (EMT, paramedic…), hver med sine nivåer, etaten som eier den, hvor mange måneder den varer, når fornyelsen forfaller, dens forutsetninger, om den må være verified før den teller, og dokumentene den trenger.
  • En persons sertifiseringer: nivået, tilstanden (opplæringskandidat, kvalifisert, instruktør, evaluator, begrenset, midlertidig utilgjengelig, suspendert, utløpt), utsteder, datoer, begrensninger og vedlagte attester. En leder markerer en verified; en ubekreftet selvregistrering teller aldri der verifisering kreves. Hver endring oppbevares.
  • Equivalencies: en annen etats kvalifikasjon godtatt som en av våre, med sitt omfang og sin utløpstid, for gjensidig bistand; personens egen post slås aldri sammen eller overskrives.
  • Reminders: ledere får beskjed én gang når en sertifiserings fornyelse forfaller og når den utløper.

Levende kapabilitet

En enhets kapabilitet kommer fra materiellet og folkene gyldig kvalifisert om bord nå: en HazMat-enhet uten de påkrevde teknikerne er ikke HazMat-kapabel, og viser LIMITED med begrunnelsen (hva hver kapabilitet krever av et mannskap settes i Personnel). Anbefalingen bruker den levende kapabiliteten; etaten bestemmer om det å sende en knapp enhet bare advares, trenger en leders override, eller blokkeres. Operatører ser kapabiliteten og kvalifikasjonsnavnene; sertifiseringsdetaljer er for ledere og personen.

Kapittel 83

Brannsted-mannskapskontroll: opprop (PAR)

På en brann under utvikling tar innsatslederen et opprop (en PAR) av hvert mannskap på stedet med faste intervaller, og utrykningsstyringen holder klokken.

  • En anropstype merket Fire-ground accountability (Admin › Call types) starter klokken når den første enheten ankommer stedet; Start roll calls starter den på en hvilken som helst brannhendelse.
  • Hendelsen viser tiden siden klokken startet og når neste PAR forfaller; den blir gul når forsinket, og lederens tavle lister den.
  • All accounted for (eller PAR) registrerer et opprop av hvert mannskap på stedet. Et mannskap som ikke svarte: klikk det, så Report … missing (eller PAR MISSING E3). Det er en rød, blinkende linje på hendelsen og et unntak som haster for lederen inntil E3 found (PAR FOUND E3).
  • Benchmarks lederen melder (primærsøk fullført, brann under kontroll, tap stanset…) er ett klikk hver, eller BM UC, med tiden siden hendelsen startet.
  • Klokken stopper når hendelsen lukkes; den kan ikke stoppes mens et mannskap er savnet.
Intervallet er 20 minutter med mindre endret i Admin › Settings eller på anropstypen.
Kapittel 84

Utkalling av utrykningspersonell

I webgrensesnittet: /admin/paging

Frivillige og brannfolk og EMT-er utenom tjeneste kalles ut med page. En paging group sier hvem som kalles ut sammen og hvordan:

  • Medlemmer fra rosteren (Personell (kapittel 80)).
  • Gateways: hvordan utkallinger går ut, satt opp av en administrator i Admin › Integrations › Paging: en tekst via Twilio, en e-post, et push til telefoner via ntfy, en webhook, eller IamResponding og Active911 (begge tar utrykningsdata per e-post i sine dokumenterte formater).
  • Automatic: kall ut gruppen når en av enhetene eller stasjonene dens sendes ut, eller når en hendelse av en av anropstypene dens får enheter. Hver gruppe kalles ut én gang per hendelse etter regelen sin.

En utkalling

Utkallingens emne er anropstypen og adressen, teksten hendelsens sammendrag og enheter. Hver person får en lenke for å svare: Responding to the station, Going straight to the scene, eller Not available, med når de venter å ankomme. Ingen innlogging: lenken er nøkkelen, og virker bare for den personen og den utkallingen.

På hendelsen viser Responders hvor mange som ble kalt ut og svarer, hver persons svar og minutter unna; Page kaller ut flere grupper. PAGE <group> / text gjør det fra kommandolinjen. En utkalling ingen har svart på etter fem minutter er på lederens unntak; mislykkede leveringer er på tidslinjen.

Sett address responders open (Admin › Integrations › Paging) til adressen telefoner når denne serveren på; uten den går utkallinger ut uten svarlenke. Testet mot stand-ins for Twilio, ntfy, e-post og en webhook; ikke sertifisert av IamResponding eller Active911.
Kapittel 85

Bergingsrotasjon

I webgrensesnittet: /admin/tows

Politi tilkaller bergingsbiler fra godkjente selskaper etter tur. Hvert selskap berger noen klasser (lett, middels, tung) i noen soner (Admin › Settings lister begge; én sone for hele området som standard).

  • Next on rotation på hendelsen (eller TOW, TOW heavy North) gir selskapet hvis siste tur i den klassen og sonen er eldst, med nummeret å ringe, og registrerer anropet.
  • Marker hva de sa: Accepted, Declined eller No answer (begge mister turen; be om den neste), så Arrived eller Cancel.
  • Et owner's choice eller officer's choice av selskap registreres men tar ingens tur.
  • Et suspendert selskap hoppes over, og rotasjonsskjermen sier hvorfor hvert selskap tilbys eller ikke tilbys.

Hver forespørsel og hvert svar er på hendelsens tidslinje og i hovedboken, slik at rotasjonens rettferdighet kan vises.

Kapittel 86

Planlagte anrop og spesielle arrangementer

Arbeid kjent på forhånd (kalenderknappen i statuslinjen):

  • Et scheduled call (en planlagt transport, en eskorte, en bedriftskontroll) blir en hendelse av seg selv på tidspunktet sitt, eller et fastsatt antall minutter tidlig, og sender enhetene sine hvis de er tilgjengelige (de som ikke er navngis på hendelsen).
  • Et special event (et marked, en parade, en kamp) blir en beredskapshendelse for timene sine, og listes som pågående på hver konsoll.
  • Enten kan gjentas hver dag, på hverdager eller hver uke, til en siste dag.

Scheduled today på situasjonspanelet lister hva som kommer de neste 24 timene og hva som pågår nå. En forekomst som bommes med mer enn en time (serveren var nede) lages ikke forsinket; den hoppes over og registreres.

Kapittel 87

Kontaktkatalog og vaktlister

Kapittel 95

Varsling av publikum

Ledere advarer publikum fra konsollen: shelter in place, evacuate, politiaktivitet, et farlig utslipp, et savnet barn, 911 nede. Trykk megaphone i statuslinjen, eller Alert the public på en hendelse.

Å skrive et varsel

  • Real alert, Exercise eller Test: en øvelse eller test merkes som en overalt den går. Kontroller dette først.
  • Kind of alert: SAME-hendelseskoden (SPW shelter in place, EVI evacuation, LEW law enforcement, HMW hazardous materials, CAE child abduction, TOE 911 outage…). Å velge en fyller ordlyden, på engelsk og spansk, å starte fra.
  • Headline, what is happening og what to do.
  • Phone alert: hva telefoner viser først (Wireless Emergency Alerts, 90 tegn) og hva tekstmeldinger og push-varsler sier; telleren blir rød forbi grensen. Et longer phone alert (360) er valgfritt.
  • Also in Spanish legger til en spansk versjon; folk på listene som valgte spansk får den.
  • Where: rundt hendelsen (en kvart mile til to miles), et område tegnet på kartet (Admin › Geofences), eller everyone i jurisdiksjonen (dens fylkeskoder).
  • Expires after en til 24 timer.
  • Send to de abonnentlistene og CAP-systemene (sirener, varslingsprogramvare) valgt; keep it off some channels ber IPAWS-varslingsprogramvare utelate radio og TV, værradio, telefoner eller offentlige nettsider.

Check viser CAP-meldingen den lager og alt som er galt med den, og hvor mange folk den når. Send spør én gang til, med den nøyaktige telefonteksten og området. Med two-person approval på venter varselet inntil en annen leder trykker Approve (megafonen viser *to approve*); dets forfatter kan trekke det tilbake, og den andre lederen kan avvise det med en begrunnelse.

I kraft

Et varsel i kraft vises rødt på kartet (gult for en test) og på megafonen, og er i den offentlige varslingsstrømmen. Update sender en ny versjon til de samme folkene som erstatter det; Cancel sender faren-over. Hvert varsel, hver godkjenning og hver levering er i hovedboken og på hendelsens tidslinje.

Å sende til IPAWS selv (Wireless Emergency Alerts og EAS) trenger FEMAs avtale og etatens egen varslingsopprinnelsesprogramvare; bitdispatcher skriver meldingene sine til IPAWS-profilen for den programvaren, og kontrollerer dem med Googles CAP-bibliotek og dets IPAWS-profil og med EAS Stations feedleser. Ingen melding er sendt til IPAWS.

Offentlige varsler: innstillinger og lister

I webgrensesnittet: /admin/publicalerts

Hvordan offentlige varsler skrives og hvor de går (Admin › Public alerts). Administratorer endrer innstillingene; ledere fører listene.

  • Sender: etatens CAP-avsender-ID, en adresse den eier (alerts@county.gov), og navnet sitt.

Kapittel 97

Selvbetjent oppsett

Et etat kan sette opp bitdispatcher selv, uten noen utenfra på stedet. Alt konfigureres på administrasjonsskjermene, og oppsettssjekklisten (kapittel 98) viser hva som gjenstår. Støtte, enten fra fellesskapsstøtte eller en støtteavtale, er fjernstyrt: e-post, telefon eller en videosamtale.

Hvem gjør hva

  • Administratoren din arbeider seg gjennom sjekklisten på administrasjonsskjermene: kartet, stasjonene, enhetene, anropstypene, brukerne og tilkoblingene.
  • IT-personalet ditt drifter serveren (eller to, for et annet sted (kapittel 115)), dens sikkerhetskopier og dens sertifikat.
  • Dine leverandører av telefoni, radio og personsøk kobler systemene sine til bitdispatchers dokumenterte grensesnitt: ALI-spill eller EIDO for anrop, gatewayen for stasjonsvarsling, personsøk-gatewayene. Alt som krever hender, kabler eller et besøk på stedet er deres.
  • Den som støtter deg svarer på spørsmål og leser støttepakken (kapittel 100) du sender. Ingen trenger å se skjermen din eller logge inn på systemet ditt.

Rekkefølgen som fungerer

  1. Installer én server og logg inn som administrator. Se Komme i gang (kapittel 1).
  2. Arbeid sjekklisten ovenfra: Admin › Setup checklist. Hvert trinn åpner sin side og sitt kapittel her. Open the checklist (kapittel 98)
  3. Hent inn det gamle systemets data: eiendommer og farer, anropstyper og utrykningskort og, hvis du vil ha dem, tidligere hendelser (Migrering (kapittel 118)); alarmtillatelser (Alarmselskaper & bevillinger (kapittel 91)).
  4. Lær opp i Training-modus: en kopi av systemet der ingenting når reelle enheter. Se Opplæring (kapittel 71).
  5. Kjør ved siden av det gamle systemet i noen uker: legg inn anrop i begge, og sammenlign anbefalingene og tidene.
  6. Bestå go-live check: Admin › Go-live check. Rett det som feiler og kjør den på nytt. Open the check (kapittel 99)
  7. Bytt over i en rolig time, med det gamle systemet fortsatt i drift skrivebeskyttet i en dag.

Sikkerhetskopier

Hovedboken (kapittel 54) er systemet: hver innstilling, enhet og hendelse bygges opp igjen fra den. Kopier hele datamappen vekk fra serveren hver natt, behold flere netter, og en gang i blant gjenopprett en på en reservedatamaskin og logg inn. Et annet sted er ikke en sikkerhetskopi: en feil kopieres til begge samtidig. Go-live check beviser at hovedboken spilles av på nytt; den kan ikke se kopier oppbevart andre steder, så sjekklisten ber deg bekrefte dem.

bitdispatcher sender ingenting til BioDream eller noen andre av seg selv. En støttepakke forlater systemet ditt bare når en administrator laster den ned og velger å sende den.
Kapittel 98

Oppsettssjekkliste

I webgrensesnittet: /admin/setup

Admin › Setup checklist lister opp alt som skal gjøres før det første reelle anropet, i rekkefølge. bitdispatcher sjekker selv de fleste trinnene mens du arbeider: et trinn er gjort når siden har det den trenger.

  • Required-trinn (påkrevde) må gjøres før idriftsetting: etatens navn, det innspilte kartet, stasjonene, enhetene, anropstypene med utrykningskort, personene (administratorer med en godkjenner-app), ingen demonstrasjonsdata, nattlige sikkerhetskopier, opplæring, og en bestått go-live check (kapittel 99) fra den siste uken.
  • Recommended-trinn (anbefalte) gjør systemet mye mer nyttig: fylkets GIS, telefonsystemet, stasjonsvarsling og personsøk, et annet sted, kjøring ved siden av det gamle systemet, og hvem som støtter deg.
  • Optional (valgfritt): NCIC gjennom statens meldingssvitsj, som statens CJIS-kontor må godkjenne.

Hvert trinn sier hvorfor det betyr noe og hva bitdispatcher fant (*3 stasjoner; ikke på kartet: Station 4*). Open går til siden som gjør det; ? åpner kapitlet.

Mark done er for det bare et menneske kan vite: opplæring gitt, sikkerhetskopier kopiert vekk fra serveren, parallellkjøringen fullført. Legg til en merknad om du vil (*alle tre skift*). Not needed er for et anbefalt eller valgfritt trinn etaten klarer seg uten, med grunnen (*ingen personsøk: stasjoner varsles over radio*). Trinn bitdispatcher sjekker selv kan ikke markeres som gjort for hånd. Hver markering er i hovedboken med hvem som gjorde den; Undo tar den tilbake.

Kapittel 99

Go-live check

I webgrensesnittet: /admin/golive

Admin › Go-live check kjører automatiske tester før det første reelle anropet. Kjør den på nytt etter enhver stor endring: et nytt kart, nye stasjoner, et nytt telefonsystem. Run the check tar noen sekunder; resultatet er i hovedboken, og oppsettssjekklisten (kapittel 98) regner den som gjort når ingenting feilet den siste uken.

Hver test består, har noe å se på, eller feiler:

  • Hovedboken er intakt: hver hendelses hash og lenke, fra den første.
  • Hovedboken gjenopprettes: en kopi av hovedboken spilles av for seg selv og sammenlignes med systemet i drift (stasjoner, enheter, anropstyper, hendelser).
  • Plass på disken: feiler under 2 GB ledig, varsler under 10 GB.
  • Ingen demonstrasjonsdata: ingen demostasjoner, -eiendommer, -kontoer eller NCIC-simulator.
  • Administratorer bruker en godkjenner-app (CJIS krever en annen faktor).
  • FIPS 140-3-kryptografi: bestått når serveren er bygget med make fips (Go Cryptographic Module under FIPS 140-3-sertifikat #5247); advarer ellers. CJIS krever validert kryptografi for strafferettslig informasjon.
  • Et klarert sertifikat: varsler når serveren bruker sitt eget, selvsignerte.
  • Det innspilte kartet dekker hver stasjon.
  • Testanrop ved hver stasjon: hver anropstype med et utrykningskort, ved hver stasjon som har enheter. Hvert regnes ut og kastes: ingenting skrives til hovedboken og ingen enhet berøres. Den varsler når kjøretider er rette linjer, når en annen stasjons enhet kommer før stasjonens egen (en responsplan (kapittel 107) kan være grunnen), og når et utrykningskort ber om enheter etaten ikke har tilgjengelig.
  • Telefonsystemet er tilkoblet, stasjonsvarsling og personsøk fungerer (en side levert de siste 30 dagene) og et annet sted kopierer (de siste 2 minuttene).

Fix åpner siden som retter en test. Sjekken sender aldri personsøk, SMS eller spørring til noen. Den kan ikke se sikkerhetskopier oppbevart andre steder, telefonsystemets egen kabling eller radioen: bekreft dem på sjekklisten.

Kapittel 105

Kapittel 106

Anropstyper og utrykningskort

I webgrensesnittet: /admin/calltypes

En anropstype er en slags hendelse (SF structure fire, CHEST chest pain) med en standardprioritet, en disiplin og et utrykningskort: hvor mange enheter av hver kapabilitet den trenger ("3 × engine, 1 × ladder, 1 × als"). Anbefalinger fyller utrykningskortet. Kapabiliteter kommer fra enhetstyper (Admin › Settings) og enheter.

Critical call setter folkene som arbeider en på lederens omsorgsliste (kapittel 69); Send a drone får drone-utskytingsregelen til å spørre om en drone (kapittel 65).

Auto-dispatch (bare typer med prioritet 3 til 5): når ingen operatør har sendt enheter innen ventetiden i Settings (60 sekunder med mindre endret), rykker de anbefalte enhetene ut av seg selv, loggført som *auto-dispatch*. Bare en fullstendig anbefaling uten advarsler sendes (en verifisert plassering, hver linje fylt); ellers sier tidslinjen hvorfor og en operatør sender den. Den prøver én gang per hendelse.

Kapittel 107

Responsplaner

I webgrensesnittet: /admin/plans

En response plan er en utrykningsrekkefølge: enhetene en etat vil ha, i forventet rekkefølge, når en plan gjelder. Anbefalingen følger en plans forventede rekkefølge når en gjelder; hvis en planlagt enhet ikke kan rykke ut sier den hvorfor og hvem som rykker ut i stedet. En person bestemmer alltid.

En plan gjelder når alle betingelsene dens matcher hendelsen:

  • Call types: de valgte kodene (tom betyr hver type).
  • Modifiers: de valgte modifikatorene, om noen.
  • First-due station area: en stasjons område, eller Anywhere.
  • Addresses: hendelsesadressen starter med en av disse linjene (én per linje), for en adressespesifikk plan.
  • From / To: et tidsvindu på døgnet (HH:MM), valgfritt.

Den forventede rekkefølgen er enhets-id-ene i rekkefølgen de ønskes; legg til fra listen, omorganiser med opp- og ned-knappene, fjern hvilken som helst. En plan uten en rekkefølge snevrer ingenting inn og ignoreres.

Kapittel 108

Å spille inn kartet

I webgrensesnittet: /admin/map

bitdispatcher spiller inn OpenStreetMap-dataene for en sirkel rundt sentralen din inn i sitt eget lager, tegner så utrykningskartet, ruter enheter etter vei og finner adresser fra det lageret uten internett.

  1. Velg sentrum (et forhåndsvalg, konsollkartets sentrum, eller en posisjon) og radiusen (100 miles dekker et fylke og dets naboer for gjensidig bistand).
  2. Nedlastingene området trenger listes straks (delstatsutdrag fra Geofabrik). Trykk Record.
  3. Innspillingen tar noen minutter; utrykningsstyringen fortsetter med det gjeldende kartet, som blir værende inntil det nye er fullstendig. Hver innspilling er en hovedbokhendelse.

Bring up to date anvender OpenStreetMaps daglige endringsfiler (Geofabrik publiserer en om dagen per utdrag) siden kartet ble spilt inn: noen få megabyte i stedet for hele utdragene, så bygges lageret på nytt. Spill inn på nytt for et nytt område, eller når kartet er mer enn et år bak; nedlastinger allerede gjort kontrolleres mot sine publiserte sjekksummer og gjenbrukes.

Automatiske oppdateringer

Automatic updates gjør det samme etter en tidsplan: av, daglig eller ukentlig, til timen du velger, i etatens tidssone (Admin › Call entry rules › operational periods).

  • Det nye kartet bygges ved siden av det som er i bruk, som fortsetter å virke hele tiden. Det byttes til bare når det er fullstendig og ikke har mistet mer enn prosentandelen du angir (10 som standard) av veisegmentene eller adressene sine; en skadet endringsfil viser seg som veier borte, og avvises.
  • En kjøring som feiler, mangler internett eller finner en innspilling allerede i gang, lar kartet i bruk være som det var, og neste vindu prøver igjen. En mislykket planlagt kjøring melder fra til veilederne og administratorene.
  • Hver kjøring er i hovedboken. Panelet viser neste kjøring og utfallet av den siste, og det gjør også Continuity (kapittel 75)-siden.

Flyfoto

Under kartet spiller Aerial photos inn foto rundt det samme sentrum: full detalj innen radiusen du velger (zoom 19: tak og biler) og mindre detalj ut mot kanten (zoom 16). Estimatet (fliser, størrelse, tid) følger skjemaet; fliser allerede spilt inn hoppes over, slik at en stoppet innspilling fortsetter der den var. Kildene og vilkårene deres listes: VGINs Virginia Base Mapping Program for Virginia, USGS The National Map (NAIP, offentlig eiendom) ellers.

Kapittel 116

Admin: kontinuitet og overflow

I webgrensesnittet: /admin/continuity

Det Continuity (kapittel 75)- og Overflow (kapittel 76)-sidene bruker.

Internettsjekker

Inntil 10 https-adresser bitdispatcher spør hvert 30. sekund (10 til 600); svarer en eneste av dem, virker internett. Velg dem sentralen er avhengig av: portalen til delstatens meldingssvitsj, personsøkleverandøren, et stort offentlig nettsted. Uten noen satt kan konsollene ikke si om internett er oppe; BitVoice, de andre stedene og overflow-naboene sjekkes uansett.

Flytting til reservestedet

  • Checklist: ett trinn per linje, haket av på Continuity-siden når sentralen flytter.
  • Contacts: reservestedet, naboene, telefonselskapet, 911-myndigheten; skrives ut på kontinuitetspakken.

Kontinuitetspakke

Hvor ofte den skrives (1 til 240 minutter, eller ikke etter en tidsplan) og inntil 5 mapper, som fulle stier, ved siden av datakatalogen. Filer er lesbare bare for serverens konto.

Overflow

Legg først til naboen i Admin › Integrations › Neighbouring agencies, med adressen til CAD-en deres (https://their-cad/api/cad/eido/(ID-en de ga oss)) og et token hver vei; hvis sertifikatet deres er deres eget og ikke fra en myndighet, legg til SHA-256-fingeravtrykket for å feste det. Deretter, for hver nabo:

  • We may ask them to take our calls, og they may assign our units mens de gjør det.
  • We take their calls when they ask, og accept their requests on our own for en avtale som sier ja på forhånd.
  • Our agencies de kan ta anrop for (tom: alle; med én blir deres anrop dens hendelser og bare dens enheter deles), og call types de kan bruke (tom: alle).
  • An overflow lasts 240 minutter med mindre annet er angitt eller den avsluttes.
Avtal overflow skriftlig med naboen, og med 911-myndigheten, som setter opp telefonnettets alternative ruting som sender 911-anropene over.

Kapittel 119

Godkjent veiledning

I webgrensesnittet: /admin/guidance

Approved guidance er etatens retningslinjer, anropsveiledere, responsveiledere og sjekklister. Anropsmottakerens Resources-fane viser de matchende passasjene med henvisninger; ingenting er oppdiktet, bare godkjent tekst vises.

Et dokument har en id, tittel, kind (Policy (mandatory), Guide, Prompts eller Checklist), versjon, ikrafttredelsesdato, en valgfri utløpstid, hva det erstatter, og kilden der den fulle godkjente kopien er. Snevre det inn til anropstyper, modifikatorer eller ord, eller marker det always shown. Bare et dokument merket Approved for use vises til anropsmottakere.

Teksten er Markdown med #/##/###-overskrifter. Overskrifter deler den inn i passasjer. Under en overskrift snevrer en linje som Applies: CARD, CHEST; modifiers: WEAPONS; words: not breathing den passasjen inn.

  • Add the examples laster tydelig titulerte eksempeldokumenter som utkast (ikke godkjent), for å se hvordan det virker.
  • Try it matcher en anropstype, modifikatorer og litt tekst og viser passasjene en anropsmottaker ville sett, med tittelen, overskriften, slaget, versjonen og hvorfor, eller en merknad når ingenting matcher.

Et dokuments status er en brikke: godkjent eller utkast, og utdatert når utløpstiden har passert.

Kapittel 120

Anropsmottaksprotokoller

I webgrensesnittet: /admin/protocols

Etatens spørsmålssett, arbeidet på anropsmottakerens Entry-fane når anropet er sendt inn (docs/PROTOCOLS.md).

  • New protocol eller Start from the example (merket *not for use*). Gi den en ID, et navn og en versjon, og velg anropstypene den tilbys for.
  • Questions: hvert svar leder til neste spørsmål eller ender ved en determinant. Make first velger hvor den starter.
  • Determinants: en kode, hva den betyr, prioriteten og anropstypen den setter (eller beholder), og instruksjonene for innringeren, én per linje.
  • Hak av Approved for calls når din medisinske direktør eller sjef har godkjent den; utkast tilbys ikke. Lagring kontrollerer at hvert svar går et sted og at ingenting går i løkke.
  • På et anrop: ett spørsmål om gangen, svar på knapper eller tastene 1–9; hvert svar er på tidslinjen, og determinanten vises på operatørens hendelse.
  • Protokollprogramvare du lisensierer (ProQA og andre) kan sende sin determinant til hooken i stedet; den vises på samme måte, merket med systemet.
