Le manuel anglais fait foi ; en cas de divergence entre les deux, c’est l’anglais qui a raison. Partie 1

La répartition

L’écran du répartiteur et tout ce qui s’y fait : appels, incidents, unités, la carte et la ligne de commande.

Chapitre 1

Pour commencer

bitdispatcher est un système de répartition assistée par ordinateur (CAD) pour les centres 911 : un seul programme doté de sa propre interface web. Il crée et suit les incidents, recommande des unités selon le temps de trajet sur le réseau routier, affiche les unités, les appels et les incidents sur une carte de répartition avec photos aériennes, offre aux équipes de terrain un terminal mobile, et consigne chaque action dans un registre inviolable à partir duquel les rapports sont bâtis.

La première heure

  1. Sign in comme administrateur avec le mot de passe affiché au premier démarrage, et choisissez Administrator. Voir Ouvrir une session (chapitre 3).
  2. Enregistrez la carte : Admin › Map, choisissez le centre et le rayon, puis appuyez sur Record. Environ deux minutes pour 100 miles. Ouvrir Map (chapitre 108)
  3. Casernes et unités : où les unités sont basées et ce qu’elles sont. Ouvrir Stations (chapitre 104) Ouvrir Units (chapitre 103)
  4. Types d’appel et grilles de réponse : ce dont chaque genre d’incident a besoin. Les valeurs par défaut sont un bon point de départ. Ouvrir Call types (chapitre 106)
  5. Utilisateurs : répartiteurs, superviseurs et équipes de terrain. Ouvrir Users (chapitre 113)
  6. Traitement des appels : connectez BitVoice, ou pointez le déversement ALI et l’EIDO de n’importe quel système de traitement d’appels vers bitdispatcher. Ouvrir Integrations (chapitre 111)

Admin › Setup checklist suit ces étapes et le reste de ce qui précède le premier appel réel, et Admin › Go-live check teste le résultat. Voir Configuration en autonomie (chapitre 97). Ouvrir la liste de contrôle (chapitre 98)

bitdispatcher conseille ; c’est le répartiteur qui décide. Aucune fonction n’envoie une unité, ne clôture un incident ni ne change une priorité de son propre chef.

Mode démo

Lancé avec -demo, bitdispatcher amorce une agence fictive sur la carte de Roanoke, en Virginie (des casernes aux positions réelles des casernes, des unités inventées). Avec bvsim, un BitVoice simulé, des appels sonnent et des radios rapportent des positions ; tout ce qui est simulé est marqué SIMULATED.

Chapitre 2

Installing it

Ce chapitre a changé après sa traduction et est affiché en anglais jusqu’à ce que la traduction soit mise à jour.

bitdispatcher runs as a service on one computer, and every console opens it in a browser. Each installer sets it up to start with the computer, before anyone signs in, and shows the first administrator's password once, at the end. Upgrading means running a newer installer: the records, the settings and the users are kept. Uninstalling keeps the records unless you confirm twice that they should go.

Download them from the latest release at github.com/BioDream-LLC/bitdispatcher/releases, where SHA256SUMS lists each file's checksum. Or build them from the source on any computer with Go (see the README): make windows (needs NSIS), make linux and make macos (on a Mac) write them to the bin folder.

In every case the records folder is closed to everyone but the service and administrators: it holds criminal justice and personal information. The service listens on port 8443 (HTTPS) unless you choose another.

Windows

Run bitdispatcher-setup.exe and approve the administrator prompt. The pages: licence, what to install, the folder, Settings (the port and the records folder; a port another program holds is refused), and the First sign-in password. It adds a firewall rule for domain and private networks, and Start menu entries: bitdispatcher, its manual, and Reset admin password. It is removed from Settings › Apps.

For IT, a silent install: bitdispatcher-setup.exe /S /PORT=8443 /DATA=D:\bitdispatcher /NOFIREWALL (each option may be left out). A silent install shows no password: run Reset admin password afterwards. A silent uninstall keeps the records.

Linux

With the package manager: sudo apt install ./bitdispatcher_VERSION_amd64.deb or sudo dnf install ./bitdispatcher-VERSION-1.x86_64.rpm. The password is printed at the end. Without one: unpack the .tar.gz and run sudo ./install.sh, with --port 9443 for another port and --open-firewall to open it in ufw or firewalld; sudo ./uninstall.sh removes it, --purge deletes the records after you type DELETE twice.

Change the port or the records folder in /etc/default/bitdispatcher, then sudo systemctl restart bitdispatcher. A lost password: sudo systemctl stop bitdispatcher, sudo -u bitdispatcher bitdispatcher reset-password -data /var/lib/bitdispatcher admin, then start it again.

macOS

Open the .pkg and follow it. At the end a dialog shows the password, with Copy password and Open bitdispatcher. If port 8443 is taken it uses the first free port from 9443 and says so. It keeps the Mac awake while the service runs (a dispatch server must answer at any time; the display may still turn off): set BITDISPATCHER_KEEP_AWAKE=no in the settings file to let it sleep. If macOS's firewall is on, bitdispatcher is allowed through it.

Applications › bitdispatcher holds four things: bitdispatcher opens the console, Reset admin password, Uninstall bitdispatcher (it asks twice before deleting the records) and the manual. From Terminal: sudo installer -pkg FILE -target / installs without dialogs and leaves the password in /usr/local/etc/bitdispatcher.first-sign-in for root to read once; delete that file afterwards. After changing the settings file: sudo launchctl kickstart -k system/com.biodream.bitdispatcher.

The certificate

On first start bitdispatcher makes its own certificate, so each browser warns once until it trusts it. Give it one your network trusts with the -tls-cert and -tls-key options (on Linux and macOS in BITDISPATCHER_FLAGS in the settings file).

What has been tested

  • Windows: installing, three upgrades, the password reset and uninstalling, on one Windows desktop computer; and on every change, a silent install, upgrade and uninstall on Windows Server 2022 in CI.
  • Linux: the Intel .deb, .rpm and .tar.gz in Debian 12 and Red Hat UBI 9 containers running systemd (install, upgrade, reset, remove); the Arm ones in the same containers on an emulated Arm processor, not yet on Arm hardware; the .deb on Ubuntu 24.04 in CI.
  • macOS: installing, two upgrades, opening the console, the password reset and uninstalling with the records kept, on one Apple silicon Mac with macOS 26; in CI also a reinstall over the kept records and a full removal. Not yet on an Intel Mac, and not with macOS's firewall on.
  • Not signed. Windows SmartScreen warns about the installer, and macOS asks before opening a downloaded .pkg (System Settings › Privacy & Security › Open Anyway). Signed installers need code-signing certificates, which BioDream has not bought yet.
Chapitre 3

Ouvrir une session : votre fonction, vos codes et le verrou

Tapez votre nom d’utilisateur et votre mot de passe. Si vous exercez plus d’une fonction, choisissez celle que vous assurez : Call-taker, Police, Fire ou EMS dispatcher, Dispatcher (all disciplines), Supervisor, Administrator ou Records (les touches numériques choisissent). Votre espace de travail s’ouvre pour cette fonction, avec votre préréglage enregistré pour elle (Votre propre disposition (chapitre 7)) et vos agences habituelles (L’agence pour laquelle vous travaillez (chapitre 8)), et ce que vous pouvez faire en découle : c’est le serveur qui l’applique, pas seulement l’écran.

FonctionOuvrePeut
Call-takerSaisie d’appel (chapitre 4)Saisir et mettre à jour des incidents ; pas envoyer d’unités (sauf si l’agence le permet)
Police, fire, EMS dispatcherLa console pour cette disciplineEnvoyer et modifier les unités de sa discipline (toutes, si l’agence le permet)
Dispatcher (all disciplines)La consoleTout ce qui se passe sur le plancher
SupervisorLa console, le tableau (chapitre 51)Aussi intervenir partout, rouvrir, lire le registre, mener des exercices

Un superviseur qui tient un poste conserve ses droits de supervision. On ne vous demande jamais à quelle console vous êtes : un poste de travail inscrit (chapitre 114) donne le poste ; un navigateur qui n’en est pas un garde son propre poste web (WEB- et quatre lettres).

Codes à usage unique. Quand l’agence les exige (Settings › Roles and sign-in), la première ouverture de session affiche un QR code : scannez-le avec n’importe quelle application d’authentification et tapez ses six chiffres. Ensuite, tapez le code courant à chaque fois ; un code ne sert qu’une fois. Un administrateur le réinitialise en cas de téléphone perdu.

Le verrou. Ctrl+Shift+L, ou les minutes sans saisie fixées par l’agence, verrouille la console : rien n’est affiché ni modifié tant que vous ne la déverrouillez pas avec votre mot de passe (et votre code). Tout reste ouvert en dessous, y compris ce que vous étiez en train de taper. Les ouvertures et fermetures de session, les verrouillages et déverrouillages sont tous dans le registre, avec la fonction et le poste de travail.

Avant de vous appuyer sur ces mécanismes pour des informations de justice pénale, vérifiez les exigences CJIS et d’accès de votre État.
Chapitre 4

Saisie d’appel : l’espace de travail du preneur d’appel

Dans l’interface web : /taker

Un espace de travail calme pour les appels : la liste des appels à gauche, les appels en cours à côté, dix onglets en haut dont seul celui choisi est affiché, et l’appel (son lieu, sa transcription et ce qui a été entendu) avec le narrative toujours à droite.

De haut en bas, dans l’ordre où un appel est traité

  1. L’appel s’attache de lui-même. Un appel pris à votre position s’ouvre aussitôt sur la saisie d’appel avec son ANI, son ALI et toute position complémentaire, chacun avec sa source. Aucun second choix de l’appel n’est nécessaire. Un visiteur ou un signalement radio se saisit sans appel.
  2. Le lieu de l’incident d’abord (voir Lieux et position (chapitre 38)) : l’adresse, son point sur la carte, comment il est arrêté (un point d’adresse vérifié, une plage estimée, l’appareil de l’appelant, un point sur la carte, ou forcé pour cet incident) et la position en son sein : le nom du commerce ou du bâtiment, le complexe, le bâtiment, l’étage, l’appartement ou la pièce, et le détail d’entrée ou de portail. Les alertes à un lieu vérifié s’affichent aussitôt, avant l’envoi de l’appel, sur chaque onglet.
  3. L’appelant et le numéro de rappel, relus et cochés comme confirmés.
  4. Le type d’appel (saisissez un code ou un mot ; les flèches et Entrée choisissent), la priorité et les modificateurs (certains augmentent la priorité, certains ajoutent des personnes à prévenir ; ceux de sécurité des intervenants s’affichent en rouge).
  5. Send (F4 ou Ctrl+Enter). Le narrative à droite reçoit des commentaires tout du long : Entrée ajoute un commentaire avec son heure, il n’y a pas de second bouton. Les commentaires écrits avant l’envoi partent avec l’appel.

Quand il manque quelque chose dont l’appel a besoin, le message le nomme et le curseur va à ce champ. La seule chose qu’un appel doit avoir pour être envoyé est son type ; un lieu non vérifié ou forcé ne le retient jamais.

Plusieurs appels en cours

À gauche de la saisie d’appel, Working calls garde chaque appel en cours dans son propre écran, jusqu’au nombre que l’agence autorise pour la fonction (trois pour un preneur d’appel sauf indication contraire). Chacun garde son propre appelant, lieu, type, personnes, véhicules et commentaires.

  • Next call (F2 ou F5) ouvre un nouvel écran de saisie d’appel et garde l’actuel exactement tel qu’il est, envoyé ou non. Quand la limite de l’agence est atteinte, il demande s’il faut clôturer un appel envoyé pour faire de la place.
  • Un appel envoyé reste ouvert pour d’autres commentaires et mises à jour de l’appelant jusqu’à ce que vous appuyiez sur Close call (clôturer l’appel). Envoyer, choisir un autre appel ou ouvrir un autre écran ne le clôture jamais.
  • Chaque écran montre son numéro, le type ou l’incident, le lieu, depuis combien de temps il est ouvert, ACTIVE, SENT, et ! quand il lui manque encore un type ou une adresse.
  • Fermer un écran non envoyé contenant des informations demande d’abord et demande pourquoi ; le registre consigne chacun ouvert, déplacé, envoyé, clôturé ou abandonné. Ils reviennent après un rechargement ou à une autre console.

Avant un second incident. Send cherche d’abord les incidents ouverts à la même adresse, à proximité ou depuis le même numéro de rappel. Add this call to it (ajouter cet appel à celui-ci) met l’appel (et ce que vous avez écrit) sur cet incident ; Send de nouveau en crée un nouveau.

Chapitre 5

Resources : les consignes approuvées avec l’appel

À mesure que le type d’appel, les modificateurs et ce qui est dit changent, l’onglet Resources trouve les passages des politiques approuvées, des guides de prise d’appel, des guides de réponse et des listes de vérification de l’agence qui s’appliquent, et s’allume lorsqu’il y a du nouveau. Chaque passage indique son document, sa section, sa version et sa date d’entrée en vigueur, s’il s’agit d’une politique (obligatoire), d’un guide, d’une liste de vérification ou de questions suggérées, et pourquoi il correspond ; The whole document ouvre le texte approuvé complet à cette section. Les passages périmés et deux politiques qui s’appliquent toutes les deux sont signalés. Quand rien ne s’applique, il le dit.

Seul le texte approuvé est affiché, mot pour mot ; rien n’est généré. L’ouverture de l’onglet consigne quels passages, dans quelles versions, ont été affichés pour l’incident, afin qu’un réviseur voie plus tard ce qui était disponible à l’époque. Les documents sont conservés dans Consignes approuvées (chapitre 119).

Chapitre 7

Votre propre disposition

L’écran du répartiteur ne montre que les sections que vous voulez, là où vous les voulez. Un nouveau venu peut commencer avec deux et en ajouter d’autres quand il est prêt.

Votre préréglage enregistré pour chaque fonction

Votre disposition est un preset gardé avec votre compte, un pour chaque fonction que vous exercez (preneur d’appel, répartiteur police, incendie et EMS, superviseur…). Ouvrez une session pour une fonction à n’importe quelle console et votre préréglage pour elle s’ouvre de lui-même : rien à reconstruire au début d’un quart.

  • Il est verrouillé en travail normal : rien ne se déplace, ne se redimensionne ni ne disparaît par accident.
  • Pour le changer : le bouton lock (*Layout locked: edit it*), disposez, puis Save & lock. Choisir une disposition toute faite lance aussi la modification. Cancel remet celle enregistrée. Chaque enregistrement est dans le registre, avec qui l’a enregistré et quand.
  • Un stagiaire travaille avec le préréglage de formation attribué par l’agence ; les commandes de disposition ne sont pas affichées. Quelqu’un sans préréglage propre démarre à partir du préréglage de l’agence pour la fonction.

Chapitre 8

L’agence pour laquelle vous travaillez

Là où le centre répartit pour plusieurs agences (Admin › Agencies), la barre d’état montre l’agence pour laquelle vous travaillez : ses règles s’appliquent à ce que vous faites (ses numéros d’incident, ses types d’appel, ses minuteries et ses plans de réponse). Cliquez dessus pour la voir et la changer :

  • Working : une agence, toujours affichée.
  • Covered : les agences pour lesquelles vous répartissez à ce poste.
  • Watched : les agences affichées pour information seulement.

Votre couverture habituelle se charge d’elle-même à l’ouverture de session, depuis votre profil (Admin › Agencies › People) et celui du poste de travail (Admin › Workstations). Un changement est consigné. Vous ne pouvez couvrir que les agences que vous êtes autorisé à travailler, et surveiller celles-là, ou celles qu’un administrateur vous a attribuées à vous ou au poste de travail pour surveillance.

Ce que le tableau montre

Quelqu’un limité à certaines agences ne voit que sa part du tableau partagé : les incidents et les unités de ces agences, les incidents sans agence attribuée, les unités d’autres agences envoyées à ses incidents, et les appels 911 jusqu’à ce qu’ils deviennent l’incident d’une autre agence. Le serveur l’applique : l’incident ou l’unité d’une autre agence est refusé par un lien direct ou sur la ligne de commande, et la tentative consignée. Quelqu’un qui travaille toutes les agences voit tout, et peut choisir The board shows › Only the agencies covered and watched here pour restreindre son propre tableau sans perdre l’accès.

Un incident a une agence primary (déterminée par son type d’appel, ou votre agence de travail) et peut avoir des agences assisting. Chaque unité conserve son agence d’attache : une unité d’une autre agence envoyée à l’incident s’y affiche d’elle-même comme assistante. Agencies… sous les unités les change (une nouvelle agence primary exige un motif).

Chapitre 10

La répartition : motifs, avertissements, plans et accusé de réception

  • Send rec sur un incident en attente dans la file envoie sa recommandation en une seule pression.
  • Un motif. Envoyer des unités autres que la recommandation demande pourquoi (choix rapides, ou vos propres mots) ; sur la ligne de commande, écrivez-le après une barre oblique : D E5 / closer by radio. Le motif et le plan de réponse suivi sont gardés avec la répartition.
  • Avertissements. Quand le lieu n’est pas vérifié, est incertain ou manque, la recommandation le signale et vous confirmez avant d’envoyer.
  • Plans de réponse. Quand un plan (chapitre 107) s’applique, son ordre prévu prime ; une unité prévue qui ne peut pas partir est barrée avec la raison, et l’unité qui part à sa place indique la place de qui elle prend. Quand la recommandation change, le changement est affiché jusqu’à ce que vous le marquiez comme vu.
  • Accusé de réception. Une unité répartie qui n’a pas accusé réception dans les secondes fixées par l’agence clignote NO ACK ; appuyez dessus (ou ACK E1) quand elle le fait. Une équipe accuse réception sur son terminal.
  • Faits de la saisie d’appel sur l’incident : modificateurs, personnes et véhicules, un lieu changé (en ambre pendant une demi-heure), où se trouve l’appelant, correspondances BOLO, le groupe de conversation (TG FIRE-OPS2) et les notifications encore à faire, chacune avec done.
  • Situation : le journal de passdown du quart, les BOLOs actifs (émettre, annuler ; BOLO text sur la ligne de commande ; les équipes les voient) et les facilities avec ouverture / détournement / fermeture en une pression.

Chapitre 18

Les appels 911

Les appels arrivent du flux d’événements de BitVoice, de l’EIDO poussé par n’importe quel système de traitement d’appels, et du déversement ALI. Le même appel provenant de plusieurs sources est fusionné en une seule ligne.

  • Lieu : la position de l’appelant et son cercle d’incertitude, l’adresse quand il y en a une, et STALE quand la localisation est plus ancienne que le réglage dans Admin › Settings. Rebid en demande une nouvelle (BitVoice).
  • + Incident sur un appel crée un incident à partir de lui, avec le lieu et le numéro de rappel remplis. Les appels déjà rattachés montrent leur incident.
  • Un texto à l’appelant, un lien vidéo et la vidéo en direct sont sur l’appel quand BitVoice les offre.
  • Sa transcription (chapitre 57) et ce qui a été entendu, la traduction (chapitre 58), la localisation de l’appareil et l’étage (chapitre 59), les données de collision (chapitre 64), les appelants regroupés (chapitre 61) et les appels non urgents (chapitre 62) sont décrits dans leurs propres chapitres.
Chapitre 19

Les incidents

New incident : F2, le bouton New, + Incident sur un appel, clic droit sur la carte (l’adresse est remplie), le New incident d’un résultat de recherche, ou NEW SF 2001 Crystal Spring Ave sur la ligne de commande. Une adresse que la carte enregistrée connaît exactement est placée aussitôt sur la carte, de sorte que les unités sont classées par route sur-le-champ ; tout le reste demeure du texte à placer.

Le panneau de l’incident montre la recommandation, les unités qui y sont avec leurs heures, l’appelant et la chronologie. Les notes (N text) et les notes prioritaires (PN text) vont sur la chronologie ; les notes prioritaires sont montrées à chaque répartiteur et à chaque unité.

Close avec une disposition (CL Handled) ; les unités encore dessus deviennent disponibles. Les superviseurs peuvent rouvrir (RO #26-000123 reason).

Correct the record (les superviseurs, sur un incident clôturé) change le type d’appel, la priorité, la disposition, l’adresse ou les heures d’une unité sans le rouvrir : dites pourquoi, et la chronologie conserve ce que chacune était. Les rapports déjà envoyés (NERIS, NIBRS) sont renvoyés à la main.

Replay (les superviseurs, sur un incident clôturé) le rejoue depuis le registre : les unités se déplacent sur la carte le long de leurs positions enregistrées (environ toutes les 30 secondes) tandis que la chronologie se remplit, de 10× à 120×, avec un curseur vers n’importe quel moment.

Chapitre 20

Recommandations d'engins

Pour l'intervention sélectionnée, bitdispatcher établit une recommandation à partir de la fiche de départ de son type d'appel : pour chaque ligne (« 3 × engine », « 1 × als »), les unités disponibles ayant cette capacité, la plus proche d'abord. Les unités déjà engagées sur l'intervention remplissent les lignes en premier, et les capacités rares sont pourvues avant les courantes afin qu'une unité polyvalente ne soit pas employée là où une autre suffirait.

  • Les temps de trajet proviennent du réseau routier enregistré : vitesses affichées ou habituelles, sens uniques respectés, depuis la position AVL récente de l'unité ou depuis sa caserne. Le motif le précise : « 1.7 mi par la route, 4 min via Franklin Road ».
  • Les routes fermées et le trafic comptent aussitôt : un trajet contourne une route fermée (chapitre 25), et une route dont le trafic en direct signale un ralentissement prend plus de temps. La ligne de source sous la recommandation indique quand ils l'ont modifié (« contourne 1 route fermée, avec le trafic en direct »).
  • Hors de la carte enregistrée, ou en l'absence de route reliant les points, le temps est une estimation à vol d'oiseau et est marqué ~.
  • Une unité qui couvre une autre caserne est classée depuis l'endroit où elle est postée.
  • Des notes avertissent lorsqu'aucune unité n'a une capacité (envisager l'entraide) ou lorsque l'envoi des unités laisserait une caserne vide.

Les unités recommandées sont présélectionnées ; Dispatch (Ctrl Enter, ou REC) les envoie. Cliquez sur les unités pour modifier la sélection, Use recommendation pour y revenir, ou tapez D E1 M2. Le registre consigne ce qui a été recommandé et ce qui a été envoyé.

Chapitre 21

Les suggestions consultatives

À côté de l’incident et sur le panneau Situation, le panneau consultatif peut suggérer quelque chose : deux incidents qui pourraient être le même, un appel qui pourrait concerner un incident ouvert, des mots qui ne cadrent pas avec le type d’appel (« smoke » sur une alarme incendie, « not breathing » sur une chute), une adresse répétée, une priorité 1 toujours sans unité, une unité sur les lieux dont on n’a pas de nouvelles.

  • Why : ouvrez une suggestion pour voir les éléments sur lesquels elle s’est appuyée (avec leur source : unité, appelant, répartiteur, machine), ce qu’elle a supposé absent, et la règle en clair.
  • Cannot determine est une réponse : quand des sources de poids égal se contredisent (« smoke » et « no smoke » de deux appelants), elle le dit et c’est vous qui décidez.
  • Accept exécute la commande suggérée en votre nom (changer le type, rattacher l’appel, envoyer la recommandation), ou la note simplement. Reject avec un motif en un clic ; elle n’est plus montrée. Les deux sont consignés.
  • Il ne fait que conseiller. Il ne fusionne, ne retype, ne reclasse ni ne répartit jamais de lui-même, et la répartition de base fonctionne de la même façon quand il est désactivé ou en panne.

Quand une mise à jour fournit une nouvelle règle (comme *Silent or abandoned 911 call*), Admin › Advisory panel la propose au-dessus des règles : Add it, puis Save version. Un recueil de codes enregistré ne change jamais de lui-même.

Chapitre 22

Redéploiement et couverture

Quand une caserne n’a aucune unité disponible d’un genre qu’elle abrite normalement (son autopompe est sortie sur un appel), le panneau Situation montre une boîte Move-up avec le mouvement qui comble le manque : l’unité de ce genre la plus proche par route, depuis une caserne qui peut s’en passer.

  • Move E3 from ST3 poste l’unité à la caserne vide en un clic (MU E3 ST1). Elle reste disponible et est recommandée depuis là.
  • Un mouvement qui laisserait sa propre caserne vide n’est proposé qu’après les mouvements qui ne vident rien, et indique « empties ST4 ».
  • Quand l’unité propre de la caserne est de retour, un bouton Home renvoie la couverture à la maison (RET E3).
  • Les genres gardés couverts se fixent par type d’unité dans Admin › Settings (autopompes de première ligne, échelles, unités médicales, ambulances et patrouille par défaut).

  • Les routes fermées sont tracées en tirets rouges, et les ralentissements du trafic en jaune, orange et rouge en dessous ; cliquez sur une route fermée pour en connaître la raison, et pour la rouvrir (Lift).
  • Routes : pour l'intervention sélectionnée, l'itinéraire routier de chaque unité recommandée, choisie et affectée, avec son heure d'arrivée sur l'unité.
  • Day / Night change la palette ; Photos (F7) place des photos aériennes sous les rues ; 3D redresse les bâtiments (les étages d'OpenStreetMap là où ils sont cartographiés) et incline la carte, et un glisser-droit la fait pivoter ; Fit all affiche toutes les unités et interventions ; OOS et Stations affichent ou masquent ces éléments.
  • La ligne cyan en tirets est le bord de la carte enregistrée : au-delà, la carte en ligne est affichée, atténuée, et les temps de trajet sont des estimations.
Chapitre 25

Routes fermées et trafic

Une route fermée modifie aussitôt les temps de trajet et les recommandations d'unités : le calculateur d'itinéraire la contourne, sans reconstruire la carte.

  • Fermer un tronçon : clic droit sur la carte, sur la route, Close a road from here, puis cliquez le long du tronçon fermé et Done. Indiquez la raison, jusqu'à quand (vide : jusqu'à ce que quelqu'un la rouvre), le détour, et s'il faut la noter sur l'intervention sélectionnée.
  • Fermer une zone : clic droit, Close the roads around here, et donnez le rayon : toute route dont une partie se trouve dans le cercle est fermée (une inondation, un incendie, une scène).
  • Les routes fermées sont tracées en tirets rouges. Cliquez sur l'une d'elles pour la raison et depuis quand, et Lift pour la rouvrir. Une fermeture assortie d'une heure de fin se lève d'elle-même.
  • Une unité peut tout de même être envoyée à un endroit situé sur une route fermée : le point de départ et le point d'arrivée d'un trajet ne sont jamais refusés, seulement les routes intermédiaires.
  • Les équipages voient les routes fermées à cet instant, avec les détours, sur le terminal mobile (chapitre 48).
  • Le trafic en direct, lorsque l'agence dispose d'un flux (Routes fermées & trafic (chapitre 89)), ralentit les routes qu'il signale : le temps de trajet d'une route est son temps enregistré multiplié par son degré de ralentissement, jusqu'à dix fois. La ligne de source d'une recommandation indique quand le trafic et les fermetures l'ont modifié.
  • Chaque fermeture, modification et levée est un événement attribué dans le registre.
Chapitre 26

Caméras à proximité d'une intervention

Lorsque l'agence a activé les caméras (Caméras (chapitre 90)), une intervention ayant une position sur la carte affiche Cameras near : les caméras de l'agence situées dans son rayon, celles orientées vers le lieu d'abord, avec leur distance et si elles regardent dans cette direction.

  • Appuyez sur l'une d'elles : elle demande pourquoi (l'intervention, ou un motif), puis l'ouvre. Une caméra à image fixe montre ce qu'elle voit à présent, rafraîchie toutes les 5 secondes ; une caméra à vue en direct l'ouvre dans le système de caméras, qui vous connecte lui-même.
  • Chaque ouverture est enregistrée avec qui, quand, pourquoi et l'intervention, et figure sur la chronologie de l'intervention. Les superviseurs voient l'enregistrement dans Admin › Cameras (chapitre 90).
  • bitdispatcher ne conserve aucune vidéo et n'enregistre rien de la caméra ; l'image fixe est récupérée pour la personne qui a ouvert la caméra, et uniquement pendant une demi-heure.
Chapitre 27

Les photos aériennes

Les répartiteurs repèrent les lieux par les toits (« la maison blanche derrière l’église »). Avec Photos activé (F7 ou le bouton sur la carte), les photos aériennes sont le fond et les rues, les noms et les numéros de maison sont dessinés par-dessus.

  • Les photos sont enregistrées dans Admin › Map : plein détail près du centre, moins de détail jusqu’au bord. Zoomer au-delà de ce qui a été enregistré agrandit la photo en dessous, de sorte que la carte ne devient jamais vide.
  • La pastille à côté du bouton indique quand la photo au centre de la carte a été prise, où la source la publie (« 2023, 12 inch ortho ») : une vieille photo n’est jamais prise pour celle d’aujourd’hui.
  • Là où rien n’est enregistré, le serveur récupère la photo quand on la demande et la conserve, sauf si cela est désactivé.
Chapitre 28

Views : le lieu sous tous les angles

Les photos aériennes montrent le toit. Views montrent l’avant, l’arrière et les côtés : où est la porte arrière, la clôture, l’escalier, le côté où se trouve la borne d’incendie.

  • Views sur le panneau de l’incident (à côté du lieu), dans l’onglet Hazards du preneur d’appel, sur le terminal mobile (chapitre 48) des équipes, et par un clic droit sur la carte.
  • N E S W : les quatre photos aériennes obliques, regardant vers le nord, l’est, le sud et l’ouest, depuis la licence EagleView propre à l’agence. Regarder vers le nord montre le côté sud d’un bâtiment. Les touches fléchées font tourner la boussole.
  • Les photos Street qui regardent le lieu, la plus proche d’abord et au plus deux par direction, depuis Panoramax ou Mapillary (photos ouvertes, CC-BY-SA, la couverture dépend de qui a photographié la rue).
  • Les photos Pre-plan : les propres images d’un local par l’agence (la Knox box, la coupure de gaz, l’entrée arrière), hors ligne et sur ce serveur. Les équipes les ajoutent depuis le terminal avec l’appareil photo de l’appareil, les répartiteurs et administrateurs d’ici ou de Premises (chapitre 117) ; les superviseurs les retirent.
  • Chaque image indique d’où elle vient et quand elle a été prise, de sorte qu’une vieille image n’est jamais prise pour celle d’aujourd’hui. Le bouton d’agrandissement la montre en pleine taille.
  • Google Street View, quand il est offert, ouvre Google dans un nouvel onglet ; rien de Google n’est affiché à l’intérieur de bitdispatcher.
Rechercher un lieu indique au fournisseur où se trouve l’incident. Chaque fournisseur est désactivé jusqu’à ce qu’un administrateur l’active dans Integrations (chapitre 111), et les images passent par ce serveur, de sorte que les clés n’atteignent jamais un navigateur.
Chapitre 29

Les messages avec les équipes

Les messages vont du plancher aux terminaux des équipes, et des équipes vers la répartition ou vers une autre unité, sans la radio.

  • Write dans Messages (panneau Situation) : à une unité ou plusieurs (E1 M2), à une discipline (ALL-FIRE, ALL-EMS, ALL-POLICE) ou à tous (ALL). Laissez To vide pour écrire aux unités de l’incident sélectionné. ! le rend urgent.
  • Ligne de commande : MSG E1 M2 / Stage at the north lot, MSG ALL-EMS ! Carilion on diversion, MSG #26-000123 / Caller says the back door is open.
  • Des équipes : les messages vers la répartition sont en gras jusqu’à ce qu’un répartiteur clique dessus, et annoncés à leur arrivée. Un message sur un incident est aussi écrit sur sa chronologie.
  • Read : le terminal marque un message comme lu quand il est affiché (un urgent quand l’équipe appuie sur Got it) ; le plancher voit *read by E1*, ou *not read yet* après deux minutes.
  • Chaque message et chaque lecture est un événement du registre. Les équipes écrivent à la répartition ou à des unités, jamais à tout le monde.

Pour des messages avec sujet, priorité, pièces jointes, péremption et versions, et pour les BOLOs et les avis de sécurité des agents, utilisez Messages et BOLOs (chapitre 30).

Chapitre 30

Messages et BOLOs : la boîte de réception

Une boîte de réception comme un courriel à l’intérieur du CAD, pour les messages, les BOLOs, les avis de sécurité des agents et les avis administratifs (l’enveloppe dans la barre d’état ; l’agence peut ajouter ses propres genres).

En écrire un

Compose : le genre, la priorité, un sujet et le texte (l’avertissement essentiel va dans le texte, jamais seulement dans une pièce jointe), To et CC, l’agence propriétaire, l’incident et les incidents liés, et pour un BOLO la plaque, le véhicule, la personne et le signalement. Les destinataires peuvent être des unités, ALL, ALL-FIRE, ALL-EMS, ALL-POLICE, DISPATCH, une agence (@agency:RPD : ses postes CAD et les terminaux de ses unités), un rôle, une fonction, une personne nommée ou une console. Un BOLO sans personne nommée va à chaque poste et terminal de l’agence propriétaire. Les pièces jointes (images, PDF et les types autorisés par l’agence) sont vérifiées par leur contenu, analysées là où l’agence fait tourner un antivirus, et conservées avec leur empreinte. Les dates Effective et expires ; *no expiration* là où l’agence le permet. Save draft le garde sous Drafts.

Chaque priorité est montrée en mots et avec une icône, jamais par la couleur seule ; seuls les niveaux que l’agence autorise peuvent être mis en sourdine.

Les navigateurs gardent une page silencieuse jusqu’à ce que quelqu’un l’ait utilisée. Après un rechargement, la première touche ou le premier clic active le son ; jusque-là, une bannière urgente indique the browser is keeping this console silent avec un bouton pour activer les sons.

Dossiers, accusés et versions

Inbox, Drafts, Sent, Active BOLOs et Archived (les périmés, annulés et remplacés, étiquetés comme tels). La livraison, l’ouverture et l’accusé de réception sont consignés pour la personne et la fonction qu’elle exerçait, pas seulement l’écran. Update envoie une nouvelle version et Cancel une annulation ; les versions antérieures sont conservées, montrées dans l’historique, et restent sur la chronologie de l’incident avec les pièces jointes (pas téléversées deux fois). Une personne voit une communication seulement lorsqu’elle lui est destinée, ou en tant que superviseur ou personnel des dossiers de son agence. Tout est dans le registre.

Chapitre 31

Recherche : incidents, BOLOs, personnes, véhicules et unités

Une seule recherche (la loupe dans la barre d’état, ou Recall dans les touches classiques) à travers les incidents (numéro, type, adresse, narratif et commentaires), les messages et les BOLOs (chaque version), les personnes (noms dans n’importe quel ordre, alias, dates de naissance, téléphones, adresses, identifiants, signalements), les véhicules (plaque, plaque partielle avec ? pour un caractère que vous ignorez, VIN, marque, modèle, couleur), les pièces jointes (noms de fichiers, légendes, et les mots à l’intérieur : fichiers en texte brut, le texte des PDF, et les mots dans les images là où le serveur les lit) et les unités (indicatif, identifiant radio, qui est à bord).

  • Les résultats sont groupés, avec des filtres pour les genres, l’agence, les dates et le statut.
  • Chacun indique pourquoi il correspond (même plaque, VIN partiel, téléphone commun, signalement similaire, *dans le texte du fichier* avec les mots autour) et avec quelle force : exact, partial ou similar (orthographes voisines sur demande).
  • Les Possible matches sont marqués comme tels : une recherche ne relie jamais une personne, un véhicule ou un incident à quoi que ce soit.
  • Les BOLOs périmés, mis à jour et annulés le disent en majuscules ; un vieil avertissement n’a jamais l’air courant.
  • Vous cherchez dans les agences que vous couvrez et surveillez ; beyond my agencies seulement là où vous pouvez les travailler, et chaque résultat nomme son agence. Les noms de mineurs et les notes médicales sont retenus aux personnes sans droit, et rien de restreint n’est compté ni affiché.
  • Chaque recherche, et chaque dossier ouvert à partir d’elle, est consignée dans le registre.

Unit recall (depuis une unité dans les résultats, ou l’History d’une unité) : une unité sur une période, en une seule chronologie : ses statuts et mises en indisponibilité, les incidents avec leur type et leur adresse, qui l’a armée et à quel poste, les contrôles de statut, les messages, et où elle était selon l’AVL ou la radio. Restreignez par intervenant, statut ou incident ; téléchargez en CSV.

Chapitre 32

Alarmes, lecteurs de plaques et détection de coups de feu

Les sociétés d'alarme, les lecteurs de plaques et la détection de coups de feu envoient leurs alertes à bitdispatcher (Admin › Integrations ; le contrat est docs/ALERTS.md). Chacune arrive dans la liste des appels 911 comme un appel, données uniquement, avec ce dont il s'agit en un coup d'œil : le type d'alarme et la zone, VERIFIED lorsque la société d'alarme l'a vérifiée, la plaque et sa liste de recherche, le nombre de coups tirés.

  • Sélectionnez-la : le panneau d'intervention affiche tout ce que l'expéditeur a fourni (le site, le compte, le permis, le détenteur de clés, la ligne de rappel de l'opérateur, la caméra et son orientation, un lien vers l'image du lecteur).
  • Créez l'intervention à partir d'elle, ou rattachez-la à une autre, comme pour n'importe quel appel ; les types d'alarme et de coups de feu propres à l'agence sont suggérés lorsqu'ils existent.
  • Une mise à jour de l'expéditeur modifie le même appel ; une annulation d'une société d'alarme figure sur l'intervention comme une note prioritaire.
  • Les sociétés d'alarme sont informées de ce qu'est devenue leur alarme : acceptée, répartie, sur les lieux, clôturée.
  • Chaque alarme est vérifiée par rapport au registre des permis de l'agence : *Alarm permit P-1: valid*, *EXPIRED*, *SUSPENDED*, ou *none on the register*. Les fausses alarmes de son adresse au cours de l'année écoulée sont comptées ; à la limite fixée par l'agence, la note indique REPEAT FALSE ALARMS (Sociétés d'alarme & permis (chapitre 91)).
  • Phoned alarm (au-dessus des appels 911) : lorsqu'un opérateur d'une société d'alarme appelle par téléphone, saisissez son alarme sur la fiche d'alarme (société, opérateur, numéro d'événement, alarme, zone, site, adresse, permis, détenteur de clés). Elle entre dans la file comme une alarme transmise, avec les mêmes vérifications, et indique qui l'a saisie.
  • Une alerte sur laquelle personne n'agit quitte la file après 30 minutes ; elle reste dans le registre.
ASAP via Nlets, la norme nationale pour les alarmes, n'est pas encore raccordé : il faut le schéma de la norme et le commutateur de messages de l'État. En attendant, chaque société peut avoir sa propre adresse et son propre jeton via HTTPS (Sociétés d'alarme & permis (chapitre 91)).
Chapitre 33

L’écran de caserne et le déclenchement des tonalités

Dans l’interface web : /station

Quand des unités sont réparties, leurs casernes reçoivent les tonalités (là où un administrateur l’a activé dans Integrations). Dans la caserne, un écran sur un compte en lecture seule à #/station (choisissez la caserne une fois ; elle est retenue) montre les unités de la caserne et leurs statuts, et lors d’une alerte :

  • des tonalités montantes, deux fois plus nombreuses pour une priorité 1, puis l’appel lu à voix haute deux fois : les unités, le type d’appel et la rue ;
  • l’appel en gros caractères : la priorité, le type, l’adresse, les unités, les dernières notes prioritaires ;

  • Un contrôleur d’alerte d’un fournisseur reçoit la même alerte à son adresse (docs/STATION-ALERTING.md).
Chapitre 34

Les incidents avec les agences voisines

Les incidents vont et viennent des CAD des agences voisines sous forme d’EIDO, la norme NENA (Admin › Integrations › Neighbouring agencies ; docs/CAD-TO-CAD.md).

  • Send : sur un incident ouvert, Send to a neighbouring agency…, choisissez l’agence et dites pourquoi (*mutual aid, need a ladder* ; *on your side of the line*). Il part avec le lieu, le numéro de rappel, nos unités dessus et les notes ; la chronologie indique qu’il a été envoyé.
  • Receive : ce qu’un voisin envoie arrive dans la liste des appels 911 comme un appel de cette agence, data only, avec leur numéro d’incident, le type et les notes. Créez l’incident à partir de lui ou rattachez-le comme pour n’importe quel appel.
  • Chaque envoi est une pression : la clôture et le statut des unités ne reviennent pas d’eux-mêmes ici. Pour un voisin qui fait aussi tourner bitdispatcher, l’overflow (chapitre 76) va plus loin : ils prennent des appels pour nous, et ce que devient chacun nous revient à eux.
Chapitre 35

Un incident garde des fichiers : les photos d’une scène prises par une équipe, un PDF, un clip audio ou vidéo.

Les équipes ajoutent aux incidents sur lesquels elles sont. Jusqu’à 25 Mo chacun : images, PDF, texte brut, MP3, WAV, MP4, WebM. Le serveur se fie à ce qu’est le fichier, pas à son nom.

  • Un superviseur retire un fichier avec un motif. Il reste dans le dossier, masqué à tous ceux en dessous du superviseur.

Forcée pour cet incident exige un point sur la carte et un motif dans la liste de l’agence (et une note quand l’agence le demande). L’adresse est conservée exactement telle qu’elle a été saisie avec le point de la carte, l’adresse vérifiée la plus proche ou les rues transversales et les autres propositions offertes. Elle n’est jamais remplacée par une adresse voisine. L’appel est envoyé aussitôt.

Chaque position qui n’est pas un point d’adresse vérifié est marquée en capitales (FORCED LOCATION (lieu forcé), ESTIMATED LOCATION (lieu estimé)) à la saisie d’appel, sur l’incident du répartiteur, sur le terminal mobile et à l’impression, jusqu’à ce que l’agence la vérifie. Seules les fonctions que l’agence autorise peuvent forcer une position ; une tentative refusée est consignée sur l’incident et les informations de l’appel restent telles quelles.

La position

Le nom du commerce ou du bâtiment, le complexe ou le campus, le bâtiment, l’étage, l’appartement ou la pièce (le type et le numéro) et l’entrée, le portail ou le détail d’accès sont des champs séparés. Ils sont consultables et ils déterminent quelles alertes s’appliquent. Un changement ici ne modifie jamais les fiches d’adresses de référence de l’agence.

Ce qui se passe ensuite

Chaque position de ce genre ouvre une exception de lieu et alerte aussitôt le superviseur de service (voir Revue du superviseur (chapitre 44)). Quand l’agence vérifie ou fusionne l’adresse plus tard, l’incident est relié au point de référence ; ce qui a été saisi et ce qui a été montré aux intervenants restent consignés.

Chapitre 39

Alertes de lieu et de sécurité

Dans l’interface web : /admin/flags

Une alerte est l’avertissement de l’agence sur une adresse vérifiée ou une personne : lieu, position, danger, sécurité des intervenants, médical, commerce, détenteur de clé ou entretien, structure dangereuse, violence conjugale, animal dangereux, bureau de vote, lieu d’évacuation (l’agence peut renommer, ajouter ou désactiver des catégories).

  • Portée : chaque alerte est posée à l’endroit juste le plus étroit : toute la propriété, un complexe, un commerce nommé, un bâtiment, un étage ou un seul appartement. L’avertissement d’un appartement n’est jamais montré pour le reste du complexe.
  • Quand elle s’affiche : dès que le preneur d’appel vérifie l’adresse, avant l’envoi de l’appel, comme une ligne sur chaque onglet, puis sur l’incident du répartiteur et sur le terminal mobile. Les alertes critiques et élevées figurent sur cette ligne ; l’onglet Hazards (Dangers) liste chacune avec ce que les intervenants doivent faire.
  • Ce qu’elle dit : la gravité et la catégorie en toutes lettres, un titre, en quoi consiste la préoccupation et pourquoi, et ce que les intervenants doivent faire. Ouvrez-la pour la source et les détails.
  • Catégories restreintes (médical, violence conjugale, sécurité des intervenants, détenteur de clé) : ceux que l’agence n’autorise pas voient l’avertissement et la conduite à tenir, pas le motif ni la source. L’ouverture du détail est consignée ; une demande refusée l’est aussi.
  • Versions : modifier, renouveler, retirer ou rétablir une alerte crée une nouvelle version. Chaque incident conserve la version qu’il a montrée, de sorte que les changements ultérieurs ne réécrivent jamais ce que les répartiteurs ont vu.
  • Lieux non vérifiés n’ont jamais d’alerte permanente. Les alertes près d’un point non vérifié s’affichent seulement comme POSSIBLE MATCH NEARBY (correspondance possible à proximité) ; une note limitée à l’incident peut être conservée à la place.
  • Qui peut : chaque catégorie indique quelles fonctions la créent, l’approuvent et la voient. Les autres (et les stagiaires) proposent ; un superviseur approuve ou rejette. Deux alertes d’une même catégorie sur une même portée sont présentées pour décision plutôt que l’une n’écrase l’autre.

Ajoutez une alerte depuis la saisie d’appel (Hazards, Add a flag or a note for this place (ajouter une alerte ou une note pour ce lieu)) ou ici dans Admin, où les alertes proposées attendent l’approbation. Ouvrir Flags (chapitre 39)

Chapitre 40

Personnes et véhicules

Les personnes, de haut en bas

Le rôle (plusieurs quand il le faut), puis First, Middle and Last name (prénom, deuxième prénom et nom) dans des champs séparés, le suffixe et les alias ; où se trouve la personne (l’incident, ailleurs avec son bâtiment, étage et unité, inconnu, sans domicile) ; les numéros de téléphone (plusieurs, avec le type, l’extension, la source et s’ils sont vérifiés) ; le signalement d’ensemble (sexe, race, origine, taille, poids, corpulence, cheveux, yeux, vêtements, cicatrices, marques et tatouages, avec les codes approuvés) ; puis les identifiants : le numéro de sécurité sociale, le permis de conduire et l’État, une autre pièce d’identité, la date de naissance et, séparément, un âge approximatif déclaré. L’âge est calculé à partir de la date de naissance. Les notes en dernier.

Officer-safety concern (préoccupation de sécurité des intervenants) ouvre une section obligatoire : un court titre d’alerte, ce qui s’est passé et pourquoi c’est une préoccupation, armes ou menace, ce que les intervenants doivent faire, la source et sa fiabilité. On ne peut pas enregistrer sans eux. Choisissez This incident only (cet incident seulement) ou Propose a permanent warning (proposer un avertissement permanent) : une proposition part vers la revue de l’agence comme une alerte de personne. Partout l’alerte s’affiche comme OFFICER SAFETY: et son titre, et s’ouvre sur le motif, la source et la consigne.

Search (recherche) sur chaque partie du nom à part (le prénom John trouve tous les John), avec la date de naissance, l’âge approximatif, le téléphone, l’adresse, le permis, le sexe, la race, une plaque liée, à consonance proche et par correspondance partielle. Possible same person (même personne possible) s’affiche pendant que vous saisissez un nom et ne bloque jamais l’enregistrement.

Les numéros de sécurité sociale et de permis s’affichent masqués sur chaque écran partagé. Open (recorded) (ouvrir, consigné) les montre aux fonctions que l’agence autorise, avec le motif consigné.

Les véhicules, de haut en bas

Les rôles (suspect, victime, volé, retrouvé, contrôle routier, preuve, remorqué et d’autres), la plaque avec l’État de l’agence d’abord, le type et l’état de la plaque (temporaire, partielle, illisible, aucune, plusieurs), le VIN (contrôlé à la saisie ; un VIN partiel est conservé avec une note), puis Run DMV (interroger le DMV) ou Run NCIC (interroger le NCIC) une fois la plaque et l’État ou un VIN complet saisis. Le retour est rattaché à ce véhicule avec son heure, qui l’a interrogé et qui l’a demandé. Les valeurs officielles s’affichent à côté de ce qui a été déclaré et une différence est signalée ; rien de ce qui est déclaré n’est écrasé. Une nouvelle interrogation est une nouvelle version.

Reliez les conducteurs, propriétaires, locataires, passagers et occupants aux personnes de l’appel ; chaque personne montre aussi ses véhicules. Un possible véhicule volé ou recherché s’affiche comme POSSIBLE HIT: not confirmed (correspondance possible : non confirmée) jusqu’à ce qu’une confirmation de correspondance reçoive une réponse (voir Requêtes NCIC et d’État (chapitre 41)).

Tow (remorquage) sur un véhicule ouvre le remorquage de ce véhicule : la prochaine entreprise dans la rotation de l’agence en haut avec son téléphone et son dernier tour, puis Accepted (accepté), Declined (refusé, avec le motif) ou No answer (pas de réponse), l’heure de chaque étape, le chauffeur, le camion, la fourrière, le numéro de mise en fourrière, la retenue et la restriction de sortie. Une entreprise qui refuse perd son tour et la suivante est sollicitée. Chaque véhicule conserve ses propres remorquages. Sur la ligne de commande SE.AD6 puis F10 ouvre le même remorquage pour AD6 sur l’incident sélectionné et demande quel véhicule.

Chapitre 41

Requêtes NCIC et d’État

Dans l’interface web : /requests

Une seule file de travail pour toutes les transactions DMV, VCIC, NCIC, Nlets et d’autres États concernant les personnes, véhicules, plaques, VIN, articles, armes, bateaux et titres.

  • La file ne montre que des métadonnées : le type de requête, l’incident, la fiche, qui a demandé (unité ou agent), quand, le répartiteur responsable, qui l’a envoyée et où (ORI), qui a reçu la réponse et quand, le statut et la disposition. Le retour lui-même s’ouvre depuis la fiche de la personne ou du véhicule par ceux qui y sont autorisés.
  • Statuts : New (nouveau), Assigned (attribué), Sent (envoyé), Awaiting return (en attente du retour), Possible hit (correspondance possible), Hit confirmation sent (confirmation envoyée), Confirmed valid (confirmé valide), Not valid (non valide), Will not extradite (pas d’extradition), Extradition limited (extradition limitée), Pending further information (en attente d’informations), No record (aucune fiche), Error (erreur), Cancelled (annulé), Reassigned (réattribué), Complete (terminé) (l’agence peut les renommer).
  • Nearly due (bientôt dû) et OVERDUE (en retard) s’affichent en toutes lettres. Une requête en retard le signale une fois à son responsable et au superviseur de service.

Confirmation de correspondance

Depuis la fiche exacte de la personne ou du véhicule (ou la file) : la fiche et le retour confirmés, le demandeur, l’ORI de l’agence saisissante, la méthode, urgent (10 minutes) ou routine (une heure), selon ce que fixe la politique NCIC, et des notes. Consignez la réponse avec qui a répondu et quand : Confirmed valid, Not valid, Will not extradite, Extradition limited, Cancelled ou Pending further information, avec des notes sur les limites d’extradition, le rayon de prise en charge, la mise en garde et les numéros de référence. Envoyer une confirmation ne rend jamais une correspondance confirmée.

Au changement de service

Chaque requête ouverte a un seul répartiteur responsable. La déconnexion est refusée tant que vous avez des requêtes ouvertes : terminez chacune, ou passez-la à un autre répartiteur (qui l’accepte) ou à une file, avec une note de ce qui reste à faire. Toute la chaîne des responsables reste sur la requête. Ouvrir les requêtes (chapitre 41)

Dans la démonstration, l’aiguillage est le simulateur de formation : une plaque ou un nom commençant par TEST répond comme une correspondance possible, et chaque réponse est marquée simulée.
Chapitre 42

Street View à côté de l’appel

L’onglet Hazards (Dangers) ancre Street View pour la position actuelle de l’incident, avec l’adresse, les coordonnées et la date des images. Il ne vous laisse jamais sur une page blanche et ne touche jamais à l’appel.

  • Avec une clé Google Maps (Admin › Integrations › Views, restreinte à ce site) bitdispatcher demande d’abord à Google s’il existe des images dans un rayon de 50 m, puis les affiche ancrées.
  • Quand il n’y en a pas, qu’il y a dépassement de délai après 10 secondes, ou qu’aucune clé n’est définie, il le dit et propose Retry (réessayer), Aerial photos on the map (photos aériennes sur la carte), Open the map (ouvrir la carte) dans une autre fenêtre et Return to call (revenir à l’appel).
  • Quand la position change (corrigée, forcée, redemandée, déplacée sur la carte) il affiche le nouveau lieu et indique que la position a changé.
  • Les vues N, E, S, W du lieu montrent les photos de l’agence ou du fournisseur pour chaque côté, et indiquent quels côtés n’en ont pas.
Chapitre 43

Tester les touches sur un poste

Avant qu’une position entre en service, vérifiez que chaque touche de fonction du profil de touches de la fonction atteint bitdispatcher. Ouvrez le plan des touches (Ctrl+/) et appuyez sur Test the keys here (tester les touches ici), puis appuyez sur chaque touche demandée.

  • Une touche qui arrive est marquée comme fonctionnelle.
  • Une touche que l’ordinateur portable garde pour lui (F2 pour le volume, F4 pour le microphone) est consignée avec la solution : maintenir Fn, ou activer le verrouillage Fn (souvent Fn+Esc), ou utiliser la touche de remplacement de l’agence.
  • Après le test, les boutons et le plan des touches montrent la combinaison qui fonctionne sur ce poste (par exemple Fn+F4).
  • Le résultat est conservé sur le poste et sur le serveur ; les superviseurs voient le dernier test de chaque poste dans Revue du superviseur.
Chapitre 44

Revue du superviseur

Dans l’interface web : /supervisor

Un seul écran pour le travail de revue du superviseur, en onglets. Chaque élément reste jusqu’à ce qu’il soit traité.

Exceptions de lieu

Chaque position d’incident forcée, estimée ou autrement non vérifiée alerte aussitôt le superviseur de service (un message urgent ou élevé) et attend ici avec ce qui a été saisi, la position acceptée et le point de la carte, la source et la confiance, les alternatives vérifiées les plus proches, les coordonnées de l’appelant, qui l’a saisie à quelle position, le motif, les unités et le statut de l’incident. Ouvrir l’incident ne l’efface pas. Acknowledge (accuser réception), puis répondez à deux questions séparées :

  1. La meilleure information de position disponible a-t-elle été utilisée ? Oui, ou non avec ce qui aurait été mieux.
  2. La source d’adresses ou le flux de travail de l’agence demandent-ils un suivi ? Aucune action supplémentaire, Soumettre une mise à jour d’adresse ou de SIG, Corriger ou fusionner la fiche de référence, Renvoyer vers une autre juridiction, Revue de formation ou de flux de travail, Défaut du système ou Suivi en attente, chacun avec un responsable et une échéance, puis done (terminé).

La file des adresses la fait passer par New, Under review (en cours de revue), Verified (vérifiée), Rejected (rejetée) ou Merged (fusionnée) ; vérifier ou fusionner relie l’incident à l’adresse de référence (les répartiteurs et les unités d’un incident actif voient le changement) et conserve ce qui a été saisi.

Incidents critiques

L’agence indique quels types d’appel, modificateurs, priorités, événements (une urgence d’unité) et phrases rendent un incident critique (Admin › Critical incidents). Un déclencheur alerte le superviseur et ouvre une revue par incident ; d’autres déclencheurs s’y ajoutent. Un superviseur peut aussi marquer un incident comme critique, ou l’enlever, avec un motif ; les déclencheurs restent consignés.

Open full review (ouvrir la revue complète) l’assemble à la demande : l’inventaire des sources, les personnes et leurs fonctions, les jalons de traitement de l’appel avec l’événement dont chacun provient, les heures de chaque unité, le trafic radio marqué (marquages automatiques, une aide seulement), les requêtes (métadonnées), la matrice QA et les limites des preuves. Chaque durée calculée montre les événements entre lesquels elle a été mesurée. Répondez à chaque mesure QA par Met (atteint), Not met (non atteint), Not applicable (sans objet), Unable to determine (impossible à déterminer) ou Needs follow-up (suivi nécessaire) avec un commentaire et la preuve sur laquelle elle repose. Choisissez une date limite de preuve et Issue (émettre) une version (son empreinte est conservée) ; une preuve ultérieure crée une nouvelle version. Records-request copy (copie pour demande d’accès) et Accreditation copy (copie pour accréditation) appliquent les règles de divulgation de l’agence à une copie séparée avec un journal de caviardage ; la revue elle-même n’est jamais modifiée. Offer support (proposer un soutien) et Open after-action (ouvrir un retour d’expérience) ne consignent que des actions opérationnelles ; aucun détail clinique ou de bien-être n’entre dans le CAD.

Alertes de phrase

Les phrases configurées entendues dans les transcriptions d’appel ou radio ou écrites dans le récit alertent le superviseur avec le contexte, la source, le canal, le locuteur et l’heure. Une phrase niée (« pas de coups de feu ») est marquée NEGATED (niée) pour revue, et une à faible confiance UNCERTAIN (incertaine). Traitez chacune : Reviewed no action (revue sans action), Critical incident opened (incident critique ouvert), Linked to existing review (reliée à une revue existante), False positive (faux positif) ou Follow-up required (suivi requis).

Shift Intelligence

Un rapport pour chaque période opérationnelle (Admin › Call entry rules fixe les périodes), assemblé à partir des fiches : incidents majeurs et ouverts, exceptions de lieu et leur revue, incidents critiques, alertes nouvelles et critiques, BOLO et messages urgents, unités en sous-effectif, contrôles de statut en retard, requêtes ouvertes et le suivi dû, chacun avec sa source, son heure, son statut, son responsable, son échéance et la prochaine action. Exécutez-le pour la période courante, une période antérieure ou une plage personnalisée. Ajoutez le résumé du superviseur et les notes de passation (tenues à part des faits) et Finalize (finaliser) ; les changements ultérieurs sont des addenda avec un motif. Le superviseur entrant l’acknowledges (accuse réception) et accepte ou réattribue chaque suivi ouvert, qui se reporte, un élément par source, jusqu’à ce qu’il soit terminé. Le détail restreint ne s’affiche qu’aux personnes autorisées.

Personnes

La période de chaque personne : fonctions et positions, connexions, appels pris et leurs heures, incidents créés, dispatches, changements de statut, requêtes, incidents critiques et leur part dans ceux-ci, pauses formelles et, à part, verrouillages de console (un verrouillage n’est pas une pause). Un possible écart de partage de charge s’affiche comme une invite de revue avec le contexte qui l’explique, jamais comme une note ni un classement. Les personnes ajoutent du contexte ou des corrections à leur propre fiche.

Suivi et tests des touches

Chaque suivi tracé, avec son historique, son responsable et son échéance ; et le dernier test des touches (chapitre 43) de chaque poste.

Chapitre 46

Admin : Incidents critiques

Dans l’interface web : /admin/critical
  • Règles : un type d’appel, un modificateur, une priorité (celle-ci ou plus urgente), un événement (une urgence d’unité) ou une phrase d’alerte rend un incident critique.
  • Phrases d’alerte : les mots, leurs variantes (un * final correspond au début d’un mot), les mots de négation recherchés avant eux dans la même phrase, les sources (call, radio, text, narrative), les types d’appel, un seuil de confiance et la gravité. Testing (en test) empêche une phrase d’alerter pendant qu’on l’essaie. Try it (l’essayer) vérifie n’importe quel texte sans alerter personne. Les phrases de départ arrivent en test.

  • QA templates (modèles QA) : par type d’appel, les mesures (un intervalle entre deux moments avec sa norme, ou un contrôle), si chacune est notée, les motifs de « sans objet » autorisés et celles qui demandent un superviseur ou un spécialiste QA.

L’enregistrement crée une nouvelle version de la politique ; une revue ouverte plus tôt conserve la version en vigueur à son ouverture. Ouvrir Critical incidents (chapitre 46)

Chapitre 47

Admin : Connexion PSC PIP

Dans l’interface web : /admin/pip

Une connexion facultative qui n’envoie que des métadonnées opérationnelles et des références de source à PSC PIP : les décomptes de la période pour CEDE, les exceptions de lieu comme contexte, les incidents critiques (et, quand l’agence en marque un comme qualifiant, vers RESET), les retours d’expérience qu’un superviseur a ouverts (ARC), les pauses manquées documentées (ROC) et les offres de soutien (RESET), avec des corrections versionnées.

  • L’agence choisit quelles classes d’événements passent, si les personnes sont nommées ou envoyées sous un pseudonyme stable, et si seuls les totaux de période sont envoyés. Preview (aperçu) montre exactement ce qui serait envoyé.
  • Aucun détail d’appelant, de patient ou de victime, aucun récit, aucune transcription, aucune adresse exacte, aucun contenu de bien-être ou clinique, et aucune note. La logique propre à PSC PIP reste dans PSC PIP. Chaque transfert est consigné dans le registre sans les personnes en clair.
  • Avec la connexion désactivée, chaque alerte, revue et rapport du superviseur fonctionne de la même manière.

Le contrat est dans docs/PSC-PIP.md. Il n’a été testé que contre un récepteur de test local, pas contre un vrai système PSC PIP. Ouvrir PSC PIP (chapitre 47)

Sur le terrain

Le terminal mobile de données qu’une équipe utilise depuis le véhicule.

Chapitre 48

Terminal de données mobile

Dans l’interface web : /mdt

Un équipage se connecte sur l'ordinateur portable ou la tablette du véhicule avec un compte field (Admin › Users) et l'indicatif de l'unité comme position (E1). Le terminal s'ouvre aussitôt.

  • L'affectation : type, priorité, adresse en gros caractères, l'itinéraire routier tracé sur la carte avec son temps et les routes empruntées, le rappel, les autres unités engagées, et les notes de la répartition, les plus récentes d'abord. Les notes prioritaires ressortent.
  • Boutons d'état : une pression chacun, avec le prochain état habituel mis en évidence ; F1 à F6 sur un clavier.
  • Les notes à la répartition figurent sur la chronologie de l'intervention au nom de l'unité.
  • GPS : la position de l'appareil est transmise à bitdispatcher comme AVL toutes les quelques secondes (autorisez la localisation lorsque le navigateur le demande).
  • Urgence : maintenez le bouton pendant deux secondes. La répartition voit la bannière d'urgence et l'acquitte.
  • Photos sur la carte, comme sur la console.
  • Messages : ce que la répartition (ou une autre unité) écrit à cette unité, avec une ligne de réponse et des réponses rapides (Copy, Delayed, Need PD…). Un message urgent occupe le haut de l'écran et sonne jusqu'à ce que l'équipage appuie sur Got it ; voir Messages (chapitre 29).
  • Messages et BOLO : les communications adressées à cette unité ou aux terminaux de son agence (messages, BOLO, avis de sécurité des agents), les plus prioritaires d'abord, avec les tonalités, répétitions et acquittements de l'agence comme sur la console. Un message urgent ou de haute priorité à acquitter reste en haut jusqu'à ce que l'équipage appuie sur Acknowledge ; en l'ouvrant, on voit chaque version, la plaque et la description, et les pièces jointes. L'ouverture et l'acquittement sont enregistrés au regard de la connexion de l'unité ; voir Messages et BOLO (chapitre 30).
  • Routes fermées : chaque route fermée (chapitre 25) en vigueur, avec la raison, le détour et jusqu'à quand, rafraîchie toutes les 30 secondes ; l'itinéraire tracé les contourne.
  • Take it : là où l'agence autorise les équipages à se rattacher eux-mêmes (Settings › Roles), une unité disponible prend une intervention en attente dans la liste en une pression ; cela est consigné comme une répartition par l'équipage, en auto-rattachement.

Un équipage n'agit que comme sa propre unité. Les répartiteurs peuvent ouvrir le terminal à #/mdt pour voir ce que voit une unité (la position nomme l'unité).

Chapitre 49

Les rapports d’incident (RMS)

Dans l’interface web : /rms

Les agents et les répartiteurs rédigent les rapports d’incident à #/rms, ou avec Report sur un incident (le lieu et l’heure de l’incident sont remplis). Une équipe sur un terminal mobile rédige le sien depuis la voiture.

  • Sections : quand et où (type de lieu, s’il a été libéré), infractions, personnes, biens, véhicules et le narratif. Les codes sont montrés en mots et choisis en un clic ; l’écran ne demande que ce dont l’infraction a besoin (une arme pour une agression, le mode d’entrée pour un cambriolage, la drogue pour une saisie, la blessure et le lien avec chaque suspect pour un crime contre la personne).
  • Enregistré au fil de la frappe : un brouillon s’enregistre lui-même un instant après l’arrêt de la frappe.
  • Avant la soumission, liste ce qui manque encore pour la déclaration par incident : les éléments de données et les contrôles NIBRS du FBI, avec les ajouts de la Virginie (quantité de biens, l’indicateur de lecteur de plaques, les types de drogue). Submit devient disponible une fois la liste vide.
  • Approbation : un superviseur autre que l’auteur l’approuve, ou le renvoie avec ce qu’il faut corriger. Chaque enregistrement et chaque décision est un événement du registre.

Le fichier de l’État

Les superviseurs voient State IBR file sous la liste. Choisissez le mois et appuyez sur File : bitdispatcher écrit les rapports approuvés du mois dans le format de déclaration par incident de la Virginie (le fichier plat positionnel du FBI avec les ajouts de la Virginie, spécification 2025.2) : les incidents de Group A avec leurs segments infraction, biens, victime, auteur et personne arrêtée, les arrestations de Group B, ou un rapport à zéro quand il n’y a rien. Téléversez-le au Virginia Crime Repository avant le 15 du mois suivant. Les rapports qui échouent aux contrôles sont laissés de côté et listés. La création du fichier est un événement du registre, avec son SHA-256.

Format: FBI national écrit les mêmes rapports dans la disposition de fichier plat propre au FBI, sans les ajouts de la Virginie, pour les États qui prennent le fichier national. Ce fichier a été vérifié avec le validateur NIBRS Pre-Certification Tool de SEARCH, qui applique les contrôles du FBI (scripts/nibrs-validator.sh) ; le réussir n’est pas une certification du FBI ni de l’État.

Les réglages ont besoin de l’ORI à neuf caractères de l’agence (Admin › Settings). Avant le premier téléversement en production, la Virginia State Police demande un fichier d’essai par courriel (dart@vsp.virginia.gov).

Draft from the incident (sur un rapport rédigé à partir d’un incident) remplit le narratif d’une première ébauche : le type, le lieu, les heures, les unités, les personnes, les véhicules et les notes du dossier. Avec le modèle de langue activé (Admin › Integrations), le modèle le rédige à partir des mêmes faits et reçoit la consigne de n’ajouter rien, écrivant *[to be completed]* là où quelque chose manque. Dans les deux cas, c’est une proposition : vérifiez chaque ligne et finissez-la dans vos mots.

Chapitre 50

Les interrogations NCIC

NCIC (sur l’écran des rapports, F9 sur l’écran du répartiteur, ou sur le terminal mobile) envoie une interrogation NCIC 2000 par le commutateur de messages de l’État : personne recherchée (QW : nom avec date de naissance, ou nom, sexe et race), véhicule (QV : plaque et État, ou VIN), arme (QG) et article (QA) par numéro de série.

  • Chaque interrogation a besoin d’un code purpose et d’une reason (le numéro d’incident) : CJIS exige les deux.
  • Le registre garde qui a demandé, quand, le purpose, la reason et si un enregistrement est revenu. Les termes ne sont gardés que sous forme d’empreinte et la réponse pas du tout.
  • Un hit est une piste : confirmez-le avec l’agence qui l’a inscrit avant toute action.
  • Les administrateurs fixent l’ORI de l’agence et le commutateur dans Admin › Settings : désactivé, le simulateur d’entraînement (les plaques, noms et numéros de série commençant par TEST retournent un enregistrement ; chaque réponse indique SIMULATED), ou un adaptateur de commutateur par TCP.

Chapitre 52

Chapitre 53

Le recueil de codes consultatif

Dans l’interface web : /admin/advisory

Admin › Advisory panel contient le recueil de codes : les règles que le panneau utilise, en clair, avec leurs seuils.

  • Mode : désactivé ; shadow (évalué et gardé dans le registre, montré aux superviseurs seulement, pour que les règles puissent être jugées avant que quiconque s’y fie) ; live (les répartiteurs voient les suggestions). Un système neuf démarre en shadow.
  • Source precedence : glissez pour ordonner les éléments de preuve unité, appelant, répartiteur et machine, le plus fort d’abord. Une source plus forte l’emporte sur une plus faible ; des sources égales qui se contredisent donnent « cannot determine ». Un panneau d’alarme silencieux ne l’emporte jamais sur une personne qui peut voir de la fumée.
  • Rules : activez ou désactivez chacune, fixez sa gravité, ses distances, ses durées, ses mots et les types d’appel auxquels elles conviennent déjà, et modifiez son explication.
  • Test rejoue le registre enregistré du dernier jour, de la dernière semaine, du dernier mois ou du dernier trimestre avec les règles à l’écran, enregistrées ou non, et compte ce que chacune aurait suggéré.
  • Save version garde le changement avec une note ; chaque version est listée et peut être restaurée en un clic. Les décisions (acceptées, rejetées et pourquoi) sont listées : rejeter une suggestion n’est jamais traité comme une erreur.

Scripts d’agence

JavaScript script et Lua script ajoutent une règle qui est le code propre de l’agence, versionnée, testée et basculée entre shadow et live avec le reste du recueil de codes. Un script définit une fonction pour son point d’ancrage :

Point d’ancrageFonctionRetourne
Chaque incident ouvertadvise(i)rien, ou {title, detail, severity, action: {label, command}} (ou une liste) : une suggestion ; l’accepter exécute la commande sur l’incident, au nom de la personne qui accepte
Recommandation d’unitérecommend(r){prefer: [unit ids], notes: [text]} : une unité préférée parmi les meilleures suivantes d’une ligne prend une place ; les notes sont montrées avec la recommandation

Un script d’incident voit le numéro, le type et son nom, la priorité, le statut, l’adresse et la position, les minutes depuis sa création, les notes, les unités dessus, les dangers de ses locaux, le nom de l’appelant et le nombre d’appels. Try it exécute le script une fois sur l’incident réel le plus récent (ou le rapport) et montre ce qu’il a retourné, ce qu’il a journalisé avec log(), et combien de temps il a pris ; show the input montre exactement ce qu’il a vu.

  • Un script n’a ni fichiers, ni réseau, ni processus, ni environnement, ni chargement de code : seulement son entrée et log().
  • Il a toujours une limite de temps (50 ms sauf réglage, au plus 1 s). Il s’exécute après que l’état du CAD est libéré, de sorte qu’un script lent ne retarde jamais la répartition.
  • Un script qui échoue ou dépasse son temps est montré sous sa règle et dans le test ; le panneau et la recommandation continuent sans lui et le disent.
Chapitre 54

Le registre et la vérification

Dans l’interface web : /admin/ledger

Chaque action qui change l’état, requiert de l’attention ou crée une responsabilité est un événement dans un registre en ajout seul : qui (utilisateur, rôle, poste, session), quand, quoi, sur quel incident, unité ou appel. Chaque événement porte l’empreinte du précédent, de sorte qu’une modification où que ce soit brise la chaîne.

Chapitre 56

Les règles de divulgation

Dans l’interface web : /admin/disclosure

Les Disclosure rules sont les règles de l’agence, revues sur le plan juridique, pour les demandes de dossiers (FOIA). Rien n’est codé en dur comme exempté ; le système propose, les personnes décident, et votre conseiller juridique revoit chaque règle avant qu’elle soit activée.

Une règle a un id, un nom, un ressort et des types de dossiers, et correspond par :

  • Category : une catégorie nommée du dossier.
  • Words : l’un quelconque d’une liste séparée par des virgules.
  • Pattern : une expression régulière Go.

Une legal basis est requise, avec une explication, une fenêtre d’entrée en vigueur facultative, et un interrupteur d’activation. Une règle reste désactivée jusqu’à ce que le conseiller juridique l’ait revue.

  • Add the sample rules (disabled) charge des exemples ; ce sont des exemples, pas des conseils juridiques.
  • Try it colle le texte d’un dossier et le montre avec les passages proposés en surbrillance — ambre là où la confiance est « review », rose là où elle est « high » — et une liste de chacun avec son texte, sa règle, sa base et sa confiance.

Chapitre 57

Transcriptions et ce qui a été entendu

Quand le traitement des appels transcrit les appels, chaque appel montre sa transcription en direct, l’appelant en blanc et le preneur d’appel en bleu, et Heard on the call : les détails qui en sont extraits, pour que le preneur d’appel tape moins.

  • Ce qui est extrait : l’adresse, les armes, les véhicules, les plaques, la direction prise par quelqu’un, combien de personnes, les blessures (ne respire pas, inconscient, saigne), les dangers (incendie, coincé, gaz, un chien, une voiture électrique) et le nom de l’appelant. Les urgents sont en rouge et viennent d’abord, et s’affichent sur l’appel dans la file.
  • Use : sur une adresse, place l’incident de l’appel là (une recherche cartographique, exacte quand la carte connaît le numéro ; vérifiez-la sur la carte). Avant qu’il y ait un incident, cela copie l’adresse.
  • D’où viennent les transcriptions : la transcription en direct de BitVoice quand il en envoie une, sa transcription d’un appel enregistré après coup, ou n’importe quel moteur de reconnaissance vocale qui poste au point d’ancrage de transcription (Points d’ancrage (chapitre 78)).
  • Ce sont des règles, non un modèle, qui extraient les détails : les mêmes mots donnent toujours les mêmes détails, et chacun montre les mots dont il provient.
Une transcription est ce qu’une machine a entendu. Le jugement et les questions du preneur d’appel décident toujours.
Chapitre 58

Appelants dans une autre langue

Un appelant qui parle une autre langue est traduit ligne par ligne sur la transcription, marqué de la langue (Spanish · translated) ; Show original montre ce qui a été dit.

  • Le guide de conversation intégré à bitdispatcher fonctionne hors ligne. Pour l'espagnol, il traduit dans les deux sens les mots des urgences ; lorsqu'il connaît trop peu de mots d'une ligne, il indique gist only : prenez un interprète.
  • Douze autres langues : arabe, chinois (mandarin), français, créole haïtien, hindi, japonais, coréen, polonais, portugais, russe, tagalog et vietnamien. La langue est reconnue à son écriture ou à ses mots. La ligne d'un appelant devient un gist : les mots d'urgence trouvés, dans l'ordre, avec … pour le reste (« fire · my house · … · please hurry »). Les phrases prêtes du preneur d'appel sont dites dans chacune d'elles ; l'anglais tapé ne l'est pas, car le guide de conversation n'inventera pas une phrase qu'il ne possède pas. Ces guides ont été rédigés par machine et n'ont pas été vérifiés par des locuteurs natifs.
  • Dites-le dans la langue de l'appelant : appuyez sur une phrase prête (Help is on the way, Is the person breathing?, Get out of the house now…) ou, en espagnol ou avec le modèle de langue, tapez en anglais ; la traduction s'affiche à mesure que vous tapez. Elle est conservée sur la transcription, envoyée par SMS lorsque also text it est coché (BitVoice), et le bouton haut-parleur la prononce à voix haute sur cette console avec la voix du navigateur pour la langue.
  • Un modèle de langue (facultatif, Admin › Integrations) traduit ce que le guide de conversation ne peut pas, via une API de chat compatible OpenAI : l'un sur votre propre serveur, ou un service sous l'accord de votre agence. Ce que disent les appelants lui est envoyé, il est donc désactivé jusqu'à ce qu'un administrateur l'active.
Chapitre 59

Où se trouve l'appelant : localisation de l'appareil et étage

Chaque appel indique comment sa position a été trouvée : device location (le relevé propre au téléphone, souvent à quelques mètres, la localisation exploitable de la FCC), GPS, secteur cellulaire ou au fichier.

  • Étage : un étage civique issu du traitement de l'appel, et l'altitude d'un relevé en 3-D avec son incertitude, qui indique à quel étage d'un immeuble élevé se trouve l'appelant.
  • Trail : un appelant qui se déplace laisse sur la carte une trace en pointillés de chaque position reçue, celle de l'appel sélectionné plus vive.
  • Rebid demande une nouvelle position ; STALE marque une position ancienne (Admin › Settings).
  • Pas de bonne position ? Send location link (Liens de localisation (chapitre 60)) permet au téléphone de l'appelant d'envoyer la sienne.
Chapitre 60

Liens de localisation : l'appelant partage l'endroit où il se trouve

Lorsqu'un appel n'apporte aucune position exploitable (une ligne fixe renvoyée depuis un mobile, un appelant qui ignore où il se trouve, un relevé cellulaire médiocre), Send location link sur l'appel envoie à l'appelant un lien : transmis par SMS via BitVoice lorsque l'appel peut recevoir un texte, ou affiché pour être lu à voix haute.

  • L'appelant l'ouvre et appuie sur Share my location ; le téléphone demande l'autorisation. Sa propre position (GPS, à quelques mètres en extérieur) parvient à l'appel, marquée *Shared by the caller (phone's location, by link)*, puis de nouveau à mesure que l'appelant se déplace, environ toutes les quelques secondes tant que la page est ouverte.
  • L'appel affiche l'état du lien ; end it l'arrête. L'appelant peut appuyer sur Stop sharing. Un lien dure 30 minutes (Admin › Settings › Calls: location links) et accepte au plus 900 positions.
  • Le lien contient un long secret aléatoire ; seul son hachage est conservé. Il ouvre une petite page sans connexion et sans rien d'autre dessus.
  • Le lien utilise l'adresse publique définie dans Groupes d'appel (chapitre 84) : le téléphone de l'appelant doit pouvoir atteindre ce serveur à cette adresse, avec un certificat auquel le téléphone fait confiance.
Chapitre 61

Plusieurs appelants, un seul incident

Quand plusieurs personnes appellent au sujet de la même chose, la file les regroupe sous N callers about one place : des appels proches les uns des autres (300 m par défaut) sur une courte période (10 minutes).

  • Créez l’incident à partir d’un appel ; le groupe propose alors Attach N to cet incident, une pression pour le reste.
  • Avec un incident sélectionné, le groupe propose de les rattacher tous à lui.
  • Les appels déjà sur des incidents différents ne sont jamais regroupés ensemble. Changez la distance et le temps dans Admin › Settings (chapitre 110).
Chapitre 62

Appels non urgents

Les appels sur une ligne non urgente, ou dont l'appelant dit quelque chose qui est rarement une urgence (une plainte pour bruit, un stationnement, une panne de courant), vont dans la liste Non-emergency sous les appels 911, avec le motif.

  • Tout élément urgent dit lors de l'appel (une arme, ne respire pas, un incendie) le maintient en urgence, quoi qu'il ait été dit par ailleurs ; de même pour les données de collision.
  • It is an emergency le ramène en urgence ; la décision d'une personne prime toujours et est consignée.
  • Send the usual reply envoie par SMS la réponse définie dans Settings, par exemple où faire une déclaration en ligne.
  • Définissez les lignes, les mots et la réponse dans Admin › Settings (chapitre 110).
  • Les rapports pris par l'accueil non urgent (chapitre 63) attendent ici aussi, marqués *a report taken by the non-emergency intake*, avec chaque réponse ; ils n'expirent pas de la liste.
Chapitre 63

Accueil non urgent

Dans l’interface web : /admin/intake

Un robot vocal ou textuel sur la ligne non urgente (le réceptionniste IA de BitVoice, ou un autre) peut prendre des rapports. Le robot porte la voix ; bitdispatcher décide de ce qu'il demande.

  • Questions : posées dans l'ordre, chacune avec le type de réponse attendu (des mots, une adresse, un numéro de téléphone, oui ou non). *needed* repose la question une fois de plus lorsque la réponse est vide. Une question oui/non marquée yes = hand over transfère l'appelant à une personne en cas de oui, ou lorsque la réponse n'est pas claire. Les clés where, phone et name remplissent l'adresse du rapport (placée sur la carte lorsque la carte enregistrée la trouve exactement), le rappel et l'appelant.
  • Le transfert : dès qu'un appelant prononce l'un des mots d'urgence (par défaut : emergency, hurt, bleeding, fire, gun, breaking in, right now… et les mots critiques de l'agence), ou tout ce que le lecteur de transcription marque comme urgent, le robot reçoit l'instruction de dire la phrase de transfert et de transférer l'appelant à un preneur d'appel. Un mot placé juste après *no*, *not* ou *nobody* (« nobody is hurt ») ne compte pas.
  • Un rapport terminé est un appel dans la liste des non urgents (chapitre 62) avec chaque réponse, la conversation et un numéro de rapport communiqué à l'appelant. Rien n'est réparti par lui ; une personne en fait une intervention ou le clôt. Une conversation transférée est un appel marqué urgence, avec ce qui a été dit.
  • Le jeton du robot : Make the token (affiché une fois). Le robot appelle POST /api/intake/sessions pour démarrer et POST /api/intake/sessions/<id> à chaque chose que dit l'appelant ; chaque réponse indique quoi dire ensuite et s'il faut transférer (docs/INTAKE.md).
  • Try it exécute le script enregistré dans une discussion, comme le ferait un appelant, et ne produit aucun rapport.
Chapitre 64

Les données de collision de véhicule

La notification automatique de collision d’un véhicule arrive comme un appel avec CRASH DATA : le véhicule, le delta-V (le changement de vitesse lors de la collision), la direction de l’impact, le tonneau, les coussins gonflables, les occupants et les ceintures, et son énergie (électrique, hybride).

  • Injury risk est élevé pour un delta-V de 40 km/h (25 mph) ou plus, un tonneau, ou 20 km/h sans ceinture, plusieurs impacts ou un impact latéral ; moyen pour 20 km/h ou tout coussin gonflable. Des suggestions suivent : ALS, désincarcération, évacuation médicale aérienne, plus d’une ambulance, et pour une voiture électrique un mot aux équipes d’incendie.
  • C’est une règle empirique tirée des critères de triage sur le terrain pour aider à choisir la réponse, pas un diagnostic. Changez les seuils dans Admin › Settings (chapitre 110).
  • Les notifications de collision parviennent à bitdispatcher par le point d’ancrage de collision (Points d’ancrage (chapitre 78)).
Chapitre 65

Les drones

Avec un système de drones connecté (Admin › Integrations (chapitre 111)), un incident sur la carte montre Send a drone. bitdispatcher envoie au système de drones l’incident, son type, sa priorité, sa position et son résumé ; le système de drones décide quel drone vole.

  • Launch rule : les incidents des types d’appel marqués Send a drone (Call types) demandent d’eux-mêmes, une fois chacun.
  • Le drone rend compte au point d’ancrage de drone : son statut, sa position, sa batterie et son image en direct. Il vole sur la carte, son statut va sur la chronologie de l’incident, et Live picture ouvre sa vidéo.
Chapitre 66

Admin: Drones

Dans l’interface web : /admin/drones
Ce chapitre a changé après sa traduction et est affiché en anglais jusqu’à ce que la traduction soit mise à jour.

Drones bitdispatcher flies itself, over MAVLink, the protocol of the PX4 and ArduPilot autopilots. Each drone has:

  • MAVLink link: udp-listen:0.0.0.0:14550, udp:host:port, tcp:host:port or serial:/dev/ttyUSB0:57600, and the autopilot's system id (0 takes the first one heard).
  • Signing key: 64 hex digits for MAVLink 2 signing. Turn it on: without it anyone who can reach the link can command the drone. A drone signing with another key is ignored.
  • Camera: an RTSP address for H.264 video. The password is masked here and never logged.
  • Height (10 to 120 m) and the lowest battery for a launch.
  • Needs pilot approval and the pilots: listed pilots approve a launch; with none listed, supervisors do. A launch rule always waits for a person.
  • Record video: while the drone is on an incident its video is kept with the incident, with its size and SHA-256 written to the ledger every 10 seconds. A recording that no longer matches is not served.

On an incident, Send a drone picks the nearest ready drone. Dispatchers can press Hold or Return home; the pilot's own controller can take over at any time. Training boards never fly real drones. Check Part 107, Remote ID and your state's drone laws before flying.

Tested with the bundled simulator (bin/dronesim) only, not yet a real drone. Details in docs/DRONES.md. Open Drones (chapitre 66)

Chapitre 67

Les transcriptions radio

Quand BitVoice ou le système radio transcrit les transmissions, les paroles d’une unité vont sur la chronologie de son incident en italique (E1: on scene, smoke showing), de sorte que le dossier garde ce qui a été dit sur les ondes. Les paroles arrivent avec les événements radio de BitVoice, ou par le point d’ancrage des paroles radio (Points d’ancrage (chapitre 78)).

Chapitre 68

Les résumés d’incident

Chaque incident ouvert a un Summary : quoi et où, ce que les appelants ont dit d’important (l’urgent d’abord), les notes prioritaires, les dangers au fichier pour le lieu, qui est sur les lieux et qui répond, et un drone au-dessus.

  • Il est bâti à partir du dossier par des règles, de sorte qu’il ne dit rien que le dossier ne dise ; il change à mesure que l’incident change.
  • Il s’affiche sur le panneau de l’incident (Copy le met dans le presse-papiers) et en haut du terminal mobile (chapitre 48) des équipes.
Chapitre 69

Les appels critiques et le soin

Certains appels restent avec les personnes qui les prennent. Un incident est un critical call quand son type d’appel est marqué critique (arrêt cardiaque, fusillade et coups de couteau pour commencer) ou quand des mots comme ne respire pas, RCR, agent à terre ou nourrisson y sont dits.

  • Tous ceux qui l’ont travaillé (le preneur d’appel et les répartiteurs qui ont saisi, envoyé ou noté) vont sur la care list du tableau du superviseur (chapitre 51), avec le motif.
  • Le superviseur offre une pause à chaque personne, organise un débreffage (avec une note du moment et du lieu) et le marque Done. Chacun est consigné.
  • Une fois l’incident clôturé, chaque personne voit une ligne discrète sur sa propre console : c’était un appel difficile, prenez un moment, et la ligne de soutien fixée dans Settings. Take a break les met en pause.
  • Fixez les mots, la ligne de soutien et les types d’appel dans Admin › Settings (chapitre 110) et Call types (chapitre 106).
Chapitre 70

Pauses et charge de travail

La tasse dans la barre d’état vous met en pause et vous ramène ; le tableau du superviseur le montre.

Le panneau People du tableau liste chaque poste connecté : les appels de la dernière heure, les actions, le temps écoulé depuis la dernière pause, les appels critiques en quatre heures, et un état :

  • watch : deux heures sans pause (Settings), un appel critique, ou une heure très chargée ;
  • relieve : trois heures sans pause, ou deux appels critiques.

Il nomme les postes les moins occupés et libres pour relever quelqu’un.

Chapitre 71

La formation

Cochez Training à l’ouverture de session. La console ouvre un tableau à elle, marqué TRAINING en violet : les unités, casernes, types d’appel, locaux et carte de l’agence, sur un registre à elle. Chaque stagiaire a son propre tableau, même sur un compte partagé ; un tableau laissé inactif deux heures est effacé. Rien de ce qui s’y fait n’atteint le tableau en direct. L’administration y est de la préparation : les changements d’un administrateur restent sur le tableau de formation jusqu’à leur publication (voir Exercices, injections et préparation (chapitre 72)) ; les utilisateurs, les connexions et les cartes sont ceux du tableau en direct.

  • Scenarios jouent des appels, des transcriptions, des données de collision et du trafic radio dedans sur la carte propre de l’agence : un incendie de maison avec trois appelants, un arrêt cardiaque en espagnol, une collision sur l’autoroute avec données de collision, un vol à main armée, et un déferlement d’appels sur la ligne.
  • Score vérifie ce qui a été fait : chaque appelant sur un incident, le type d’appel, les unités envoyées, une réponse dans la langue de l’appelant, et la revue de qualité (chapitre 73) de chaque incident.
  • Reset vide votre tableau et le recommence ; les tableaux des autres stagiaires ne sont pas touchés.
Chapitre 72

Exercices, injections et préparation

Un exercice est un seul tableau de formation pour tous ceux qui s’y joignent : cochez Training à l’ouverture de session et tapez le nom de l’exercice (n’importe quel nom ; le premier à se joindre le crée). Les stagiaires ouvrent une session avec leurs propres fonctions, de sorte qu’un preneur d’appel, des répartiteurs et un superviseur le travaillent ensemble, et les équipes peuvent se joindre sur le terminal mobile (chapitre 48) de la même façon. Pour s’exercer seul, laissez le nom vide.

L’instructeur (un superviseur ou un administrateur) appuie sur Inject : un nouvel appelant (où, qui, et ce qu’il dit à mesure que l’exercice avance), l’appelant qui en dit plus ou qui se déplace, une unité qui tombe hors service, un bouton d’urgence, ou une unité sur la radio. Timeline télécharge chaque événement pour le débreffage, et quand l’exercice se termine sa chronologie est conservée (superviseurs : /api/exercises).

Préparation. Un administrateur connecté avec Training change les types d’appel, les unités, les casernes, les plans de réponse, les consignes ou les installations sur le tableau de formation, les essaie là, puis ouvre Staged changes : il liste ce qui diffère du tableau en direct ; choisissez les parties, dites pourquoi, et Publish. Avec *Change configuration only through staging* activé (Settings), ces changements ne peuvent pas être faits directement sur le tableau en direct.

Le tableau de formation n’est pas une sauvegarde du tableau en direct. Un site de continuité est un dispositif distinct et éprouvé : voir Plusieurs sites (chapitre 115).

Chapitre 74

Travailler pendant une panne

Chaque console garde le dernier tableau qu’elle avait. Quand le serveur est injoignable, une barre ambre le signale et la console montre ce tableau, tel qu’il était, avec l’heure. Une console rechargée pendant la panne s’ouvre quand même.

  • Offline log : les nouveaux incidents, les notes et les statuts d’unités sont gardés dans ce navigateur, dans l’ordre.
  • Quand le serveur est de retour, la barre propose Send them now : chacun entre marqué « entered offline at 14:02 by jlee » ; tout ce que le serveur refuse reste, avec le motif.
  • Pour un serveur qui ne disparaît jamais, faites tourner bitdispatcher sur deux sites (Plusieurs sites (chapitre 115)) : chacun continue de fonctionner quand l’autre est coupé.
  • Quand c’est l’internet, plutôt que le serveur, qui est parti, ou que le centre doit quitter son bâtiment, voyez Continuité (chapitre 75).
Chapitre 75

Continuité : pannes et centre de secours

Dans l’interface web : /continuity

La page Continuité (le bouton bouée dans la barre d’état, ou une pastille là quand quelque chose ne va pas) est ce qui garde le centre en marche quand un lien ou le bâtiment est perdu.

Quand l’internet tombe

bitdispatcher tourne sur le propre serveur du centre, de sorte que perdre l’internet n’arrête pas la répartition. La saisie des appels, les incidents, les unités, la carte des rues enregistrée, le routage et les adresses, le registre et l’impression continuent de fonctionner.

  • Ce qui attend l’internet : les tuiles de carte en ligne, Street View et les photos aériennes non enregistrées, le trafic, les mises à jour de carte, les centres voisins et l’overflow, NERIS, PSC PIP, et BitVoice ou la radiomessagerie quand ils sont atteints par internet.
  • bitdispatcher vérifie les adresses qu’un administrateur fixe (Admin › Continuité (chapitre 116)), BitVoice, les autres sites et chaque voisin d’overflow. Quand aucune des vérifications d’internet ne répond, chaque console montre Internet down en rouge et les superviseurs reçoivent un message ; un autre lien tombé se montre comme une pastille ambre.
  • Chaque lien qui tombe et qui revient est au registre ; la page liste les liens et les pannes.

Passer au centre de secours

Quand le centre doit quitter son bâtiment, le personnel va au centre de secours : un second site bitdispatcher que le comté possède ou fait tourner dans le cloud (Plusieurs sites (chapitre 115)). Il détient déjà chaque enregistrement, de sorte que le travail reprend là où il en était.

  1. Au centre de secours, un superviseur presse We are working from the backup site, avec une note. Chaque console sur chaque site montre At backup site, et chacun de service reçoit un message.
  2. La liste de contrôle fixée dans Admin › Continuité est cochée au fur et à mesure (rerouter le 911, les stations de contrôle radio, prévenir le terrain) ; chaque coche est au registre.
  3. De retour chez soi, We are back in our building y met fin.
Les appels 911 n’atteignent le centre de secours que lorsque le réseau téléphonique les y envoie : le routage alternatif de l’autorité 911, ou le routage de BitVoice en NG911. bitdispatcher ne peut pas déplacer les appels lui-même.

Le pack de continuité

Open to print donne une page des incidents ouverts (avec les noms des appelants et les rappels), chaque unité et son statut, la liste de contrôle, les contacts et des lignes de journal vierges, pour travailler sur papier si le CAD ne peut pas être atteint du tout. Il peut être écrit selon un horaire vers des dossiers qu’un administrateur fixe : un lecteur partagé ou un disque USB sur une autre machine garde une copie récente si ce serveur est perdu. Traitez les copies imprimées comme des enregistrements.

Chapitre 76

Overflow vers un centre voisin

Dans l’interface web : /overflow

Quand le centre est débordé, ou hors de son bâtiment, un centre voisin qui fait aussi tourner bitdispatcher peut prendre ses appels ; et ce centre peut prendre les leurs. Cela se configure pour chaque voisin dans Admin › Continuité (chapitre 116), après que les deux centres en conviennent par écrit.

Demander de l’aide

  1. Sur la page Overflow, un superviseur presse Ask (neighbour) to take our calls, dit pourquoi et pour combien de temps (4 heures sauf réglage contraire).
  2. Le superviseur du voisin accepte ou refuse ; un voisin dont les réglages acceptent d’eux-mêmes démarre aussitôt. Les barres d’état des deux centres le montrent : *(neighbour) is taking our calls*.
  3. Chaque appel qu’ils prennent devient un incident ici, sous nos numéros et nos types d’appel, marqué Taken for us by (neighbour) avec le nom de leur preneur d’appel. Nos répartiteurs envoient nos unités, sauf si nous laissons le voisin les assigner aussi.
  4. Un superviseur de l’un ou l’autre centre presse End quand c’est fini.

Prendre des appels pour un voisin

Tant que cela dure, la page Overflow montre Take a call for (neighbour) : le lieu, leur type d’appel, l’appelant, le rappel et ce qui s’est passé. Send crée l’incident dans leur CAD et montre son numéro.

  • Ce que devient l’appel revient : son statut, les unités dessus, leurs notes et la clôture. Les notes ajoutées ici leur vont.
  • S’ils nous le permettent, Their units liste leurs unités disponibles à assigner.
  • Si leur CAD ne peut pas être atteint, l’appel est gardé ici et renvoyé toutes les 20 secondes ; prévenez-les par radio ou par téléphone si c’est urgent.

Ce qui traverse

Seulement les appels que le voisin prend, et ce qu’ils deviennent : aucun autre incident, aucun enregistrement, aucun historique de personne, aucun retour NCIC. Chaque demande, réponse, appel, note et assignation est aux registres des deux centres.

Les appels 911 eux-mêmes atteignent le voisin par le routage alternatif du réseau téléphonique, que l’autorité 911 met en place, ou par le routage de BitVoice en NG911. L’overflow porte le travail, pas les appels.
Chapitre 77

Les attaques des lignes (TDoS)

Un déni de service téléphonique sature les lignes pour que de vrais appelants ne puissent pas passer. bitdispatcher surveille les appels et lève Possible telephony denial-of-service sur chaque console et sur le tableau du superviseur quand :

  • bien plus d’appels arrivent en une minute que d’habitude (cinq fois le débit de la dernière heure, au moins 12, ou le nombre fixé dans Settings) ;
  • un même numéro appelle cinq fois ou plus en dix minutes (montré comme ×5 sur ses appels) ;
  • huit appels silencieux ou très courts ou plus arrivent en cinq minutes.

Un superviseur l’accuse ; elle se dissipe après dix minutes tranquilles. Continuez de répondre : une vraie urgence peut s’y trouver.

Chapitre 79

Niveaux d’alarme : 2e et 3e alarmes

Un incendie qui travaille dépasse sa première grille de réponse. Chaque type d’appel peut avoir d’autres alarmes (Admin › Call types) : la 2e alarme, la 3e, chacune ajoutant des unités à ce dont l’incident a besoin. La première alarme est la grille de réponse propre du type d’appel.

L’élévation

  • Sur l’incident, Upgrade to 2nd alarm indique ce qu’elle ajoute (+2 engine, 1 ladder…) ; ou tapez ALARM (2ND, 3RD, ALARM 3 pour un niveau).
  • L’élévation est une ligne prioritaire sur la chronologie que chaque répartiteur et chaque équipe voit, avec ce qu’elle ajoute.
  • La recommandation remplit alors la grille de réponse plus grande, comptant les unités déjà là, et REC (ou Ctrl Enter) envoie les unités supplémentaires. Les groupes d’appel par pagette et les alertes de caserne suivent la répartition comme d’habitude.
  • Bring down revient d’un niveau, avec un motif.
Configuration : Admin › Call types › un type › Further alarms. Chaque alarme a un nom et des lignes de grille de réponse (capacité et nombre). Le type structure fire est livré avec une 2e et une 3e alarme à modifier.
Chapitre 80

Le personnel et les équipes

Dans l’interface web : /admin/personnel

Le roster est les gens de l’agence : un numéro, un nom, un grade, des qualifications (ambulancier paramédical, EMT, conducteur, agent…), une caserne d’attache, et comment les joindre par pagette (un téléphone pour les textos, un courriel, un sujet de notification poussée). Ajoutez-les un par un ou Import from CSV (colonnes : id, name, rank, qualifications séparées par ;, station, phone, email, volunteer).

Qui est à bord

Sur n’importe quelle unité (le panneau de l’unité › Crew › change) ou depuis le terminal propre de l’équipe (Crew), choisissez qui la monte ce quart. Un membre est sur une unité à la fois : le mettre sur une autre le déplace. La chronologie de l’incident consigne les changements d’équipe sur une unité qui y travaille.

Ce que change l’armement

  • Minimum aboard (Admin › Settings › Unit types, ou par unité dans Admin › Units) : une unité en dessous est montrée en sous-effectif, dans les motifs de la recommandation et dans les exceptions du superviseur.
  • What a capability needs (Admin › Settings › Crews) : par défaut, ALS a besoin d’un ambulancier paramédical à bord. Une unité médicale dont l’équipe enregistrée n’a pas d’ambulancier paramédical n’est pas recommandée pour une ligne ALS (elle reste BLS et transport).
  • Une unité sans équipe enregistrée est tenue pour armée : une agence qui ne tient pas ses rosters ici ne voit aucun changement.
Les répartiteurs voient le roster sans les numéros de téléphone ni les courriels ; les superviseurs les voient.
Chapitre 81

L’armement : qui est en service et sur chaque unité

Dans l’interface web : /staffing

Staffing (le bouton des personnes dans la barre d’état) montre qui est en service, où, et qui arme réellement chaque unité. Un indicatif seul ne suffit pas : l’équipe suit l’unité dans les incidents, les recommandations, l’historique et les rapports.

Personnes en service

Sign on avec le genre de service (régulier, temps supplémentaire, prolongation, un détachement temporaire et où, un rappel), le quart, jusqu’à quand et la disponibilité (disponible, affecté, non disponible, formation, cour, repas, service de caserne, administratif). Sign off retire la personne de toute unité. Cherchez par nom, qualification, agence, caserne, unité et disponibilité.

Équipes

Edit crew nomme les gens d’une unité et leurs positions (conducteur, agent, pompier, ambulancier, coéquipier, chef d’équipe, ou celles de l’agence). Le genre d’unité peut exiger des positions et un minimum (Admin › Settings › Unit types). Une équipe peut se mettre elle-même en service depuis le terminal ; l’agence décide par genre d’unité si c’est permis, requiert l’approbation d’un superviseur (Sign-ons waiting) ou est réservé à la répartition.

  • Une personne est sur une unité active à la fois. La mettre sur une autre demande : move them (relève, échange) ou une affectation secondaire avec un motif.
  • Chaque changement a un motif et une heure effective, gardée à côté du moment de la saisie.
  • Une unité laissée à court (en dessous de son minimum, une position vide) est limited, ou mise out of service, selon ce que dit l’agence, à moins qu’un superviseur n’enregistre un override avec un motif.
  • Une perte de connexion ne met personne hors service.

Sur les incidents et plus tard

Quand une unité est affectée, l’incident garde qui était à bord et pour quoi ils étaient qualifiés à ce moment-là ; les changements ultérieurs ne le réécrivent jamais, et les changements pendant l’incident (qui s’est joint, qui est parti, les positions) sont sur sa chronologie. Un superviseur peut corriger un dossier d’équipe avec un motif : l’original reste à côté de la correction, avec les heures de saisie et d’entrée en vigueur. Le rappel d’unité et les rapports montrent les personnes autant que l’indicatif.

Les superviseurs voient aussi les saved crews pour un shift change en une étape (chaque personne et chaque heure toujours consignées), et la coverage : le minimum de personnes qualifiées que l’agence veut en service, les manques, les accréditations qui expirent et la capacité de chaque unité (une vue de supervision que l’agence contrôle).

Chapitre 82

Qualifications, équipes spéciales et accréditations

Dans l’interface web : /admin/qualifications

Chaque agence tient un fichier de compétences contrôlé (Admin › Qualifications & teams ; les superviseurs).

  • Qualifications : les équipes spéciales (Swift Water, HazMat, Technical Rescue, Dive, K-9, SWAT, UAS), les spécialités (technicien en preuve, enquêteur incendie, négociateur de crise, répartiteur tactique), les rôles de formation (CTO, FTO, instructeur, évaluateur) et les accréditations (EMT, ambulancier paramédical…), chacune avec ses niveaux, l’agence qui en est propriétaire, combien de mois elle dure, quand le renouvellement est dû, ses préalables, si elle doit être vérifiée avant de compter, et les documents qu’elle exige.
  • Les accréditations d’une personne : le niveau, l’état (stagiaire, qualifié, instructeur, évaluateur, restreint, temporairement indisponible, suspendu, expiré), l’émetteur, les dates, les restrictions et les certificats joints. Un superviseur en marque une verified ; une auto-saisie non vérifiée ne compte jamais là où la vérification est requise. Chaque changement est conservé.
  • Equivalencies : la qualification d’une autre agence acceptée comme l’une des nôtres, avec sa portée et son expiration, pour l’entraide ; le dossier propre de la personne n’est jamais fusionné ni écrasé.
  • Reminders : les superviseurs sont avisés une fois quand le renouvellement d’une accréditation arrive à échéance et quand elle expire.

La capacité en direct

La capacité d’une unité vient des véhicules et des personnes valablement qualifiées à bord maintenant : une unité HazMat sans ses techniciens requis n’est pas apte au HazMat, et montre LIMITED avec le motif (ce dont chaque capacité a besoin d’une équipe se fixe dans Personnel). La recommandation utilise la capacité en direct ; l’agence décide si envoyer une unité à court est seulement averti, requiert le override d’un superviseur, ou est bloqué. Les répartiteurs voient la capacité et les noms des qualifications ; les détails des accréditations sont pour les superviseurs et la personne.

Chapitre 83

La comptabilité sur le terrain d’incendie : les appels nominatifs (PAR)

Lors d’un incendie qui travaille, le commandant d’incident fait un appel nominatif (un PAR) de chaque équipe sur les lieux à intervalles fixés, et la répartition tient l’horloge.

  • Un type d’appel marqué Fire-ground accountability (Admin › Call types) démarre l’horloge quand la première unité arrive sur les lieux ; Start roll calls la démarre sur n’importe quel incident d’incendie.
  • L’incident montre le temps écoulé depuis le démarrage de l’horloge et quand le prochain PAR est dû ; il passe à l’ambre quand il est en retard, et le tableau du superviseur le liste.
  • All accounted for (ou PAR) consigne un appel nominatif de chaque équipe sur les lieux. Une équipe qui n’a pas répondu : cliquez dessus, puis Report … missing (ou PAR MISSING E3). C’est une ligne rouge clignotante sur l’incident et une exception urgente pour le superviseur jusqu’à E3 found (PAR FOUND E3).
  • Les benchmarks que le commandant rapporte (fouille primaire terminée, incendie maîtrisé, pertes stoppées…) sont un clic chacun, ou BM UC, avec le temps écoulé depuis le début de l’incident.
  • L’horloge s’arrête quand l’incident se clôture ; elle ne peut pas être arrêtée tant qu’une équipe est manquante.
L’intervalle est de 20 minutes sauf changement dans Admin › Settings ou sur le type d’appel.
Chapitre 84

L’appel des intervenants par pagette

Dans l’interface web : /admin/paging

Les pompiers et EMT volontaires et hors service sont appelés par page. Un paging group dit qui est appelé par pagette ensemble et comment :

  • Members depuis le roster (Personnel (chapitre 80)).
  • Gateways : comment les pagettes sortent, configurées par un administrateur dans Admin › Integrations › Paging : un texto par Twilio, un courriel, une notification poussée aux téléphones par ntfy, un webhook, ou IamResponding et Active911 (les deux prennent la répartition par courriel dans leurs formats documentés).
  • Automatic : appeler le groupe par pagette quand l’une de ses unités ou casernes est répartie, ou quand un incident de l’un de ses types d’appel reçoit des unités. Chaque groupe est appelé une fois par incident selon sa règle.

Une pagette

Le sujet de la pagette est le type d’appel et l’adresse, le texte le résumé de l’incident et les unités. Chaque personne reçoit un lien pour répondre : Responding to the station, Going straight to the scene, ou Not available, avec l’heure d’arrivée prévue. Pas d’ouverture de session : le lien est la clé, et ne fonctionne que pour cette personne et cette pagette.

Sur l’incident, Responders montre combien ont été appelés et répondent, la réponse de chaque personne et les minutes avant son arrivée ; Page appelle d’autres groupes. PAGE <group> / text le fait depuis la ligne de commande. Une pagette à laquelle personne n’a répondu après cinq minutes est dans les exceptions du superviseur ; les livraisons échouées sont sur la chronologie.

Fixez l’adresse à laquelle les intervenants accèdent (Admin › Integrations › Paging) à l’adresse par laquelle les téléphones joignent ce serveur ; sans elle, les pagettes sortent sans lien de réponse. Éprouvé contre des substituts de Twilio, ntfy, courriel et un webhook ; non certifié par IamResponding ni Active911.
Chapitre 85

La rotation des dépanneuses

Dans l’interface web : /admin/tows

La police appelle des dépanneuses de compagnies approuvées à tour de rôle. Chaque compagnie dépanne certaines classes (légère, moyenne, lourde) dans certaines zones (Admin › Settings liste les deux ; une seule zone pour toute la région par défaut).

  • Next on rotation sur l’incident (ou TOW, TOW heavy North) donne la compagnie dont le dernier tour dans cette classe et cette zone est le plus ancien, avec son numéro à appeler, et consigne l’appel.
  • Marquez ce qu’ils ont dit : Accepted, Declined ou No answer (les deux font perdre le tour ; demandez la suivante), puis Arrived ou Cancel.
  • Un owner’s choice ou officer’s choice de compagnie est consigné mais ne prend le tour de personne.
  • Une compagnie suspendue est sautée, et l’écran de rotation dit pourquoi chaque compagnie est offerte ou non.

Chaque demande et chaque réponse est sur la chronologie de l’incident et dans le registre, de sorte que l’équité de la rotation peut être démontrée.

Chapitre 86

Appels planifiés et événements spéciaux

Le travail connu d’avance (le bouton calendrier dans la barre d’état) :

  • Un scheduled call (un transport planifié, une escorte, une vérification d’entreprise) devient un incident de lui-même à son heure, ou un nombre fixé de minutes à l’avance, et envoie ses unités si elles sont disponibles (celles qui ne le sont pas sont nommées sur l’incident).
  • Un special event (une foire, un défilé, un match) devient un incident de garde pour ses heures, et est listé comme en cours sur chaque console.
  • L’un ou l’autre peut se répéter chaque jour, les jours de semaine ou chaque semaine, jusqu’à un dernier jour.

Scheduled today sur le panneau Situation liste ce qui vient dans les 24 prochaines heures et ce qui est en cours maintenant. Une occurrence manquée de plus d’une heure (le serveur était hors service) n’est pas rendue en retard ; elle est sautée et consignée.

Chapitre 87

L’annuaire des contacts et les listes de garde

Dans l’interface web : /admin/directory

Les numéros que la répartition appelle : services publics, agences, le médecin légiste, les interprètes, les travaux publics. Chaque entrée a des numéros avec des étiquettes (après les heures, cellulaire), un courriel, des notes et des mots-clés.

  • Les on-call lists disent qui répond ce soir : des tours d’entrées de l’annuaire par date et heure, avec une relève quand aucun tour ne couvre le moment.
  • Une entrée ou une liste peut être sur la call-out list de types d’appel : chaque incident du type liste To call avec la personne de garde maintenant et le numéro (une tape l’appelle sur un téléphone), et Called le consigne sur l’incident. Les notifications d’un type d’appel (Admin › Call types › Notify) sont rattachées aux entrées par nom, organisation ou mot-clé.
  • Le bouton annuaire dans la barre d’état (ou DIR water) cherche par nom, organisation, mot-clé ou numéro ; le panneau Situation montre qui est de garde maintenant.
Chapitre 88

Les zones sur la carte (géorepères)

Dans l’interface web : /admin/geofences

Des zones dessinées sur la carte :

  • Une alert area avise la répartition quand une unité y entre ou en sort (une unité qui quitte le comté, qui entre dans une zone de danger, qui arrive à un hôpital) : un avis sur chaque console, les Area alerts du panneau Situation, et une ligne sur l’incident de l’unité. Elle peut ne surveiller que certaines disciplines ou unités.
  • Une caution area met sa note sur chaque incident à l’intérieur (une zone scolaire, un champ de tir, un pâté de maisons réputé à problèmes), sur la console et sur les terminaux des équipes.

Draw a new area : cliquez les coins sur la carte, puis Finish. Les zones s’affichent sur la carte de la console, en pointillés. Si une unité est à l’intérieur se calcule à partir de ses positions à mesure qu’elles arrivent, de sorte qu’une zone dessinée autour d’une unité déjà là n’est pas une arrivée.

Chapitre 89

Routes fermées & trafic

Dans l’interface web : /admin/roads

Chaque route fermée à présent, avec la raison, les routes qu'elle emprunte, depuis quand, jusqu'à quand, le détour et qui l'a fermée ; et celles rouvertes au cours de la dernière journée.

  • Lift rouvre une route. Remove est destiné à une fermeture saisie par erreur (elle reste dans le registre) ; une fermeture qui était réelle doit être levée, afin que le relevé indique qu'elle a été fermée.
  • Une fermeture dont la ligne ou le cercle ne couvre aucune route enregistrée le signale : tracez-la de nouveau le long de la route.

Trafic en direct (administrateurs) :

  • Waze for Cities est le programme gratuit de partage de données de Waze destiné aux organismes publics. Une fois que l'agence a adhéré, Waze lui donne l'adresse de son flux de trafic (JSON) ; collez-la ici. La vitesse de chaque embouteillage ralentit les routes qu'il recouvre ; une route que Waze signale fermée est fermée.
  • GeoJSON : toute autre source, une FeatureCollection de lignes avec speed_kmh, factor (fois plus lent) ou closed: true, et name.
  • Récupéré toutes les 2 minutes par défaut (de 30 secondes à une heure), avec un jeton envoyé en Bearer lorsque le flux en a besoin. L'état indique quand il a été récupéré pour la dernière fois, combien de ralentissements il comportait, ou pourquoi il a échoué. Un flux qui s'interrompt laisse les temps de trajet enregistrés.
Chapitre 90

Caméras

Dans l’interface web : /admin/cameras

Les caméras que les répartiteurs peuvent ouvrir pour une intervention (Caméras à proximité d'une intervention (chapitre 26)) : caméras de circulation, bâtiments de l'agence, écoles et partenaires ayant accepté de partager.

  • Offer cameras near incidents est désactivé jusqu'à ce qu'un administrateur l'active ; le rayon (400 m par défaut) indique jusqu'à quelle distance d'une intervention les caméras sont proposées.
  • Add a camera : son nom, son propriétaire, son emplacement, la direction dans laquelle elle regarde (degrés depuis le nord ; vide si elle pivote), sa largeur et sa portée de vision, et l'adresse de sa live view (ouverte dans une nouvelle fenêtre dans le système de caméras) et/ou l'adresse de sa still picture (un JPEG de l'instant, récupéré via bitdispatcher). Uniquement des adresses https, ou http sur le réseau propre à l'agence.
  • Who looked, and why liste chaque ouverture. Convenez d'une politique avant d'activer les caméras : quelles caméras, pour quels appels, et qui révise ce relevé.
Chapitre 91

Sociétés d'alarme & permis

Dans l’interface web : /admin/alarms

Companies : chaque station centrale avec laquelle l'agence travaille reçoit sa propre adresse (/api/hooks/alarm/<company>) et son propre jeton, affiché une fois lors de sa création ; ses alarmes arrivent avec son nom, et ce qu'elles deviennent va à sa propre adresse de réponse. Un nouveau jeton annule l'ancien. Les sociétés absentes de la liste peuvent tout de même utiliser le jeton de hook partagé (Admin › Integrations).

Permits : chargez le registre des permis d'alarme de l'agence au format CSV, avec une ligne d'en-tête : numéro, adresse, détenteur, société, expiration (YYYY-MM-DD), statut (active, suspended, revoked). Le chargement remplace le registre. Chaque alarme est appariée par son numéro de permis, sinon par son adresse de voirie.

False alarms : les interventions d'une adresse au cours de l'année écoulée dont la disposition est une fausse alarme sont comptées (par défaut, les dispositions comportant « false ») ; à la limite (3 par défaut), l'alarme indique REPEAT FALSE ALARMS.

Les alarmes transmises par téléphone sont saisies sur la fiche d'alarme (Alarmes (chapitre 32)).

Chapitre 92

L’historique des statuts d’une unité

History sur le panneau d’une unité montre sa journée depuis le registre : une barre de ses statuts au fil de la journée, chaque statut avec le moment, la durée, l’incident et qui l’a changé, ses contrôles de statut, ses changements d’équipe et ses redéploiements, les incidents qu’elle a travaillés, et la part de son temps connu passée sur des incidents. Choisissez un autre jour avec la date ; CSV télécharge la même chose.

Unit recall (Recherche (chapitre 31)) donne n’importe quelle période en une seule chronologie pour l’usage de première ligne, avec qui a armé l’unité, ses messages et ses positions.

Chapitre 93

Les rapports de soins aux patients (NEMSIS)

Une équipe EMS rédige son rapport de soins au patient dans son système ePCR ; la partie répartition (quand l’appel est entré, quand l’unité a été avisée, en route, sur les lieux, a quitté les lieux, à l’hôpital, de retour en service, où, et le motif de répartition) vient de bitdispatcher.

  • NEMSIS sur une unité EMS de l’incident télécharge sa réponse comme un enregistrement NEMSIS 3.5, à importer dans n’importe quel ePCR qui prend les fichiers NEMSIS.
  • Avec un système de rapports de soins aux patients configuré (Admin › Integrations › Patient-care reports), Send l’y poste, et automatic envoie la réponse de chaque unité EMS quand elle se libère. Ce que le système a répondu est sur l’incident.
  • Le motif de répartition est le code NEMSIS du type d’appel (Admin › Call types), ou suggéré d’après son nom.
Le dossier ne porte que la répartition, les heures et la scène ; l’équipe remplit les sections du patient. Il suit le schéma NEMSIS 3.5.1 pour ces sections ; éprouvé contre un substitut, pas le système d’un fournisseur.
Chapitre 94

Mandats et actes à signifier

Dans l’interface web : /papers

Les actes qu’un bureau du shérif ou un service de police détient pour signification : mandats d’arrêt et mandats du tribunal, ordonnances de protection, expulsions, assignations et citations à comparaître (le bouton maillet dans la barre d’état). Chacun a la personne, où le signifier, le tribunal et le numéro, toute caution (armé, violent, chien), et chaque tentative.

  • Un incident près de l’adresse d’un acte actif (ou nommant sa personne) montre active paper at this address avec la mise en garde à chaque console et aux terminaux des équipes de police ; Details (répartition police, dossiers et superviseurs) montre les actes.
  • Record the attempt : l’unité, le résultat (pas de réponse, pas là, déménagé, refusé, signifié) et une note. Signifié le clôture ; Recalled et Returned unserved exigent un motif.
  • Chaque consultation des actes est consignée dans le registre.
Confirmez chaque mandat avec l’agence émettrice (et NCIC là où cela s’applique) avant d’agir.
Chapitre 95

Alerter la population

Les superviseurs avertissent la population depuis la console : shelter in place, evacuate, activité policière, un déversement dangereux, un enfant disparu, le 911 en panne. Appuyez sur le megaphone dans la barre d’état, ou sur Alert the public sur un incident.

Rédiger une alerte

  • Real alert, Exercise ou Test : un exercice ou un test est marqué comme tel partout où il va. Vérifiez ceci en premier.
  • Kind of alert : le code d’événement SAME (SPW mise à l’abri, EVI évacuation, LEW application de la loi, HMW matières dangereuses, CAE enlèvement d’enfant, TOE panne du 911…). En choisir un remplit la formulation, en anglais et en espagnol, pour partir de là.
  • Headline, what is happening et what to do.
  • Phone alert : ce que les téléphones affichent d’abord (Wireless Emergency Alerts, 90 caractères) et ce que disent les textos et les notifications poussées ; le compteur passe au rouge au-delà de la limite. Une longer phone alert (360) est facultative.
  • Also in Spanish ajoute une version espagnole ; les personnes des listes qui ont choisi l’espagnol la reçoivent.
  • Where : autour de l’incident (d’un quart de mille à deux milles), une zone dessinée sur la carte (Admin › Geofences), ou everyone dans le ressort (ses codes de comté).
  • Expires after une à 24 heures.
  • Send to les listes d’abonnés et les systèmes CAP (sirènes, logiciel d’alerte) choisis ; keep it off some channels demande au logiciel d’alerte IPAWS de laisser de côté la radio et la télé, la radio météo, les téléphones ou les sites publics.

Check montre le message CAP qu’elle produit et tout ce qui cloche, et combien de personnes elle atteint. Send demande une fois de plus, avec le texte exact du téléphone et la zone. Avec la two-person approval activée, l’alerte attend qu’un deuxième superviseur appuie sur Approve (le mégaphone montre *to approve*) ; son auteur peut la retirer, et le deuxième superviseur peut la rejeter avec un motif.

En vigueur

Une alerte en vigueur s’affiche en rouge sur la carte (ambre pour un test) et sur le mégaphone, et est dans le flux d’alertes publiques. Update envoie une nouvelle version aux mêmes personnes qui la remplace ; Cancel envoie la fin d’alerte. Chaque alerte, approbation et livraison est dans le registre et sur la chronologie de l’incident.

Envoyer à IPAWS lui-même (Wireless Emergency Alerts et l’EAS) exige l’accord de la FEMA et le propre logiciel d’origination d’alertes de l’agence ; bitdispatcher écrit ses messages au profil IPAWS pour ce logiciel, et les vérifie avec la bibliothèque CAP de Google et son profil IPAWS et avec le lecteur de flux d’EAS Station. Aucun message n’a été envoyé à IPAWS.
Chapitre 96

Les alertes publiques : réglages et listes

Dans l’interface web : /admin/publicalerts

Comment les alertes publiques sont rédigées et où elles vont (Admin › Public alerts). Les administrateurs changent les réglages ; les superviseurs tiennent les listes.

  • Sender : l’identifiant d’expéditeur CAP de l’agence, une adresse qu’elle possède (alerts@county.gov), et son nom.
  • Jurisdiction et county codes : les codes SAME à six chiffres des comtés couverts (0, le code FIPS de l’État et celui du comté : 051770 est la ville de Roanoke), utilisés pour une alerte à tous et ajoutés à chaque alerte pour la radio et la télé.
  • Time zone : les heures CAP portent le décalage de l’agence.
  • Two-person approval (recommandé) : un deuxième superviseur approuve chaque alerte avant qu’elle parte.
  • Public alert feed : un flux Atom pointant vers chaque message CAP, et un flux de style IPAWS avec les messages à l’intérieur, pour les sirènes, les encodeurs EAS des diffuseurs et les applications. Ils ne montrent que les alertes en vigueur.
  • CAP receivers : les systèmes auxquels chaque alerte est POSTée en CAP (avec un jeton Bearer) ; Send a test envoie un message d’essai.
  • Subscriber lists : les personnes qui ont demandé des alertes, jointes par les passerelles de pagette (texto, courriel, notification poussée). Une personne ayant donné un lieu ne reçoit que les alertes dont la zone le contient. Import a CSV avec les colonnes name, phone, email, topic, lang, lat, lon. Une passerelle de notification poussée sans personne listée publie sur son propre sujet, un canal que n’importe qui peut suivre.
Les flux sont publics par conception : ils ne contiennent que ce qui a été envoyé à la population.

Chapitre 97

Configuration en autonomie

Une agence peut configurer bitdispatcher par elle-même, sans personne de l’extérieur sur place. Tout se configure sur les écrans d’administration, et la liste de contrôle de configuration (chapitre 98) montre ce qui reste à faire. Le soutien, qu’il vienne du support communautaire ou d’un contrat de support, est à distance : courriel, téléphone ou appel vidéo.

Qui fait quoi

  • Votre administrateur parcourt la liste de contrôle sur les écrans d’administration : la carte, les casernes, les unités, les types d’appel, les utilisateurs et les connexions.
  • Votre personnel informatique fait tourner le serveur (ou deux, pour un second site (chapitre 115)), ses sauvegardes et son certificat.
  • Vos fournisseurs de téléphonie, de radio et de messagerie d’alerte connectent leurs systèmes aux interfaces documentées de bitdispatcher : déversements ALI ou EIDO pour les appels, la passerelle d’alerte des casernes, les passerelles de messagerie d’alerte. Tout ce qui demande des mains, des câbles ou une visite sur site leur revient.
  • Celui qui vous soutient répond aux questions et lit le dossier de support (chapitre 100) que vous envoyez. Personne n’a besoin de voir votre écran ni d’ouvrir une session dans votre système.

L’ordre qui marche

  1. Installez un serveur et ouvrez une session comme administrateur. Voir Pour commencer (chapitre 1).
  2. Suivez la liste de contrôle depuis le haut : Admin › Setup checklist. Chaque étape ouvre sa page et son chapitre ici. Ouvrir la liste de contrôle (chapitre 98)
  3. Importez les données de l’ancien système : locaux et dangers, types d’appel et grilles de réponse et, si vous le souhaitez, les incidents passés (Migration (chapitre 118)) ; permis d’alarme (Sociétés d’alarme & permis (chapitre 91)).
  4. Formez en mode Training : une copie du système où rien n’atteint les unités réelles. Voir La formation (chapitre 71).
  5. Fonctionnez en parallèle de l’ancien système pendant quelques semaines : saisissez les appels dans les deux, et comparez les recommandations et les temps.
  6. Réussissez le go-live check : Admin › Go-live check. Corrigez ce qui échoue et relancez-le. Ouvrir le contrôle (chapitre 99)
  7. Basculez à une heure calme, l’ancien système restant en lecture seule pendant une journée.

Sauvegardes

Le registre (chapitre 54) est le système : chaque réglage, unité et incident est reconstruit à partir de lui. Copiez tout le répertoire de données hors du serveur chaque nuit, conservez plusieurs nuits, et de temps à autre restaurez-en une sur un ordinateur de rechange et ouvrez une session. Un second site n’est pas une sauvegarde : une erreur est copiée sur les deux à la fois. Le go-live check prouve que le registre se rejoue ; il ne peut pas voir les copies conservées ailleurs, c’est pourquoi la liste de contrôle vous demande de les confirmer.

bitdispatcher n’envoie rien à BioDream ni à personne d’autre de lui-même. Un dossier de support ne quitte votre système que lorsqu’un administrateur le télécharge et choisit de l’envoyer.
Chapitre 98

Liste de contrôle de configuration

Dans l’interface web : /admin/setup

Admin › Setup checklist énumère tout ce qu’il y a à faire avant le premier appel réel, dans l’ordre. bitdispatcher vérifie lui-même la plupart des étapes à mesure que vous travaillez : une étape est faite quand sa page a ce qu’il lui faut.

  • Les étapes Required (requises) doivent être faites avant la mise en service : le nom de l’agence, la carte enregistrée, les casernes, les unités, les types d’appel avec grilles de réponse, les personnes (des administrateurs avec une application d’authentification), aucune donnée de démonstration, les sauvegardes nocturnes, la formation, et un go-live check (chapitre 99) réussi au cours de la dernière semaine.
  • Les étapes Recommended (recommandées) rendent le système bien plus utile : le GIS du comté, le système téléphonique, l’alerte des casernes et la messagerie d’alerte, un second site, le fonctionnement en parallèle de l’ancien système, et qui vous soutient.
  • Optional (optionnelle) : le NCIC via le commutateur de messages de l’État, que le bureau CJIS de l’État doit approuver.

Chaque étape dit pourquoi elle compte et ce que bitdispatcher a trouvé (*3 casernes ; pas sur la carte : Station 4*). Open ouvre la page qui la réalise ; le ? ouvre son chapitre.

Mark done sert à ce que seule une personne peut savoir : la formation donnée, les sauvegardes copiées hors du serveur, le fonctionnement en parallèle terminé. Ajoutez une note si vous voulez (*les trois quarts*). Not needed sert à une étape recommandée ou optionnelle dont l’agence se passe, avec la raison (*pas de messagerie d’alerte : les casernes sont alertées par radio*). Les étapes que bitdispatcher vérifie lui-même ne peuvent pas être marquées faites à la main. Chaque marque est dans le registre avec qui l’a faite ; Undo la retire.

Chapitre 99

Go-live check

Dans l’interface web : /admin/golive

Admin › Go-live check lance des tests automatiques avant le premier appel réel. Relancez-le après tout grand changement : une nouvelle carte, de nouvelles casernes, un nouveau système téléphonique. Run the check prend quelques secondes ; le résultat est dans le registre, et la liste de contrôle de configuration (chapitre 98) le compte comme fait quand rien n’a échoué au cours de la dernière semaine.

Chaque test réussit, a quelque chose à regarder, ou échoue :

  • Le registre est intact : le hachage et le lien de chaque événement, depuis le premier.
  • Le registre se restaure : une copie du registre est rejouée seule et comparée au système en marche (casernes, unités, types d’appel, incidents).
  • De la place sur le disque : échoue sous 2 Go libres, avertit sous 10 Go.
  • Aucune donnée de démonstration : pas de casernes, de locaux, de comptes ni de simulateur NCIC de démonstration.
  • Les administrateurs utilisent une application d’authentification (CJIS exige un second facteur).
  • Cryptographie FIPS 140-3 : réussit quand le serveur a été compilé avec make fips (le Go Cryptographic Module sous le certificat FIPS 140-3 n° 5247) ; avertit sinon. Le CJIS demande une cryptographie validée pour les informations de justice pénale.
  • Un certificat de confiance : avertit quand le serveur utilise le sien, auto-signé.
  • La carte enregistrée couvre chaque caserne.
  • Des appels de test à chaque caserne : chaque type d’appel ayant une grille de réponse, à chaque caserne qui a des unités. Chacun est calculé puis jeté : rien n’est écrit dans le registre et aucune unité n’est touchée. Il avertit quand les temps de trajet sont des lignes droites, quand l’unité d’une autre caserne arrive avant celle de la caserne elle-même (un plan de réponse (chapitre 107) peut en être la raison), et quand une grille de réponse demande des unités que l’agence n’a pas disponibles.
  • Le système téléphonique est connecté, l’alerte des casernes et la messagerie d’alerte fonctionnent (un message livré au cours des 30 derniers jours) et un second site copie bien (au cours des 2 dernières minutes).

Fix ouvre la page qui corrige un test. Le contrôle ne fait jamais de message, de texto ni de requête à personne. Il ne peut pas voir les sauvegardes conservées ailleurs, le câblage propre du système téléphonique ni la radio : confirmez-les sur la liste de contrôle.

Chapitre 100

Le support et le dossier de support

Dans l’interface web : /admin/support

Admin › Support indique à qui votre agence demande de l’aide et construit un dossier de support à leur envoyer.

À qui demander de l’aide est le texte propre à l’agence : le service d’assistance informatique, le numéro et les heures d’un contrat de support. Vide, il renvoie au support communautaire sur GitHub (n’y publiez jamais de données d’appelants, d’adresses ni de secrets). Le support de bitdispatcher est à distance ; tout ce qui demande des mains est fait par votre propre personnel et vos fournisseurs.

Download the bundle construit un seul fichier zip avec ce qu’il faut à un aidant pour trouver un problème sans voir votre écran : la version, le système d’exploitation et la durée de fonctionnement ; la taille du registre et sa vérification ; l’espace disque ; la liste de contrôle de configuration et le dernier go-live check ; le lien vers le système téléphonique et les autres sites ; le nombre d’unités, de casernes et d’incidents et les genres d’événements des 7 derniers jours ; les réglages, les casernes, les unités, les types d’appel et les plans de réponse ; les connexions ; et les avertissements et erreurs récents du serveur.

Chaque jeton, mot de passe et clé dans les connexions devient *(set)*. Les adresses courriel, les numéros de téléphone et tout ce qui ressemble à un jeton sont retirés de chaque fichier.

Lisez-le avant de l’envoyer. Un nom que quelqu’un a tapé dans un réglage ou dans la liste de notification d’un type d’appel y reste. bitdispatcher n’envoie rien de lui-même : vous téléchargez le dossier et décidez de l’envoyer ou non, et à qui. Chaque téléchargement est enregistré dans le registre avec qui l’a fait.

Chapitre 101

Les agences

Dans l’interface web : /admin/agencies

Chaque organisation pour laquelle le centre répartit est une agency (RPD, RCPD, SPD, RFD, RCFR, SFD, un service de travaux publics, et le centre lui-même) : la police, l’incendie et l’EMS sont des disciplines, pas des agences. Un centre sans agences fonctionne comme une seule, avec les réglages à l’échelle du centre.

  • Une agence : son code et son nom, ses disciplines, active ou non, l’ORI, le NERIS ID et d’autres identifiants, son propre préfixe de numéro d’incident, ses dispositions, ses minuteries de contrôle de statut, ses groupes de conversation et ses règles de dossiers.
  • Ce qui lui appartient : les unités, les casernes, les types d’appel et les plans de réponse nomment leur agence (choisie dans la liste, non tapée). Le plan de réponse d’une agence n’est que pour ses incidents ; ses minuteries que pour ses unités.
  • People : les agences que chaque personne peut travailler, celle pour laquelle elle travaille habituellement, celles couvertes et surveillées par défaut, si elle est trainee, et son entrée au roster. Une personne limitée à certaines agences ne change que la configuration de ces agences et ne voit que leurs vues de supervision.
  • Workstations peuvent indiquer quelles agences ils couvrent et surveillent (Admin › Workstations).

Le contrôle des changements

Les changements de configuration peuvent être ébauchés sur le tableau de formation, essayés là, et publiés sur le tableau en direct avec un motif, tous d’un coup ou pour une seule agence : une publication pour une agence n’emporte jamais les changements d’une autre ni ceux du centre. Chaque publication garde les versions qu’elle a remplacées : Roll back remet la version approuvée antérieure, avec un motif, et est elle-même consignée.

Chapitre 102

Les règles d’exploitation

Dans l’interface web : /admin/operations

Les règles de l’agence pour le travail quotidien (Admin › Operations rules ; les administrateurs).

  • Vues de supervision : le tableau du superviseur, le rapport d’exploitation, la revue de qualité et le soin, le registre et la couverture d’armement appartiennent à l’agence. Sans règle, les superviseurs les voient ; avec une règle, seulement les rôles, les personnes et les agences qu’elle nomme. Les administrateurs les voient toujours. Une personne sans droit ne voit pas la vue et ne l’atteint pas par un lien direct : le serveur refuse, et consigne la tentative.
  • Presets : le préréglage attribué par l’agence pour chaque fonction (ce avec quoi les stagiaires travaillent et ce dont les autres partent), et la protection du préréglage d’une personne pour que seuls les administrateurs le changent.
  • Working calls : activés ou non, combien par fonction et pour les stagiaires, et après combien de temps un appel en cours laissé par quelqu’un déconnecté est offert aux superviseurs.
  • Communications : les genres (qui peut les envoyer, leur priorité et péremption par défaut, s’ils attendent les personnes déconnectées), la tonalité, la répétition, l’accusé de réception et l’escalade de chaque priorité (avec un bouton pour entendre chaque tonalité), et les pièces jointes autorisées.
  • Staffing : ce qui arrive à une unité laissée à court (avertir, limiter, mettre hors service), si les unités à court peuvent être envoyées (avertir, override d’un superviseur, bloquer), et le minimum de personnes qualifiées que le centre veut en service.
  • Command line and keys : le délimiteur, l’ordre des identifiants pour field initiate et unit status, le type d’appel du contrôle, une ou deux passes, l’interrogation automatique de plaque, plusieurs unités à la fois, les codes de statut (et ceux retirés), et le key profile de chaque fonction, standard ou classique (PremierOne-style) ou la copie propre de l’agence. Check trouve une touche qui fait deux choses sur un écran, une touche que le navigateur garde pour lui, ou une action inconnue ; les réglages sont refusés jusqu’à ce que ce soit corrigé.
Chapitre 103

Les unités

Dans l’interface web : /admin/units

Chaque unité a un indicatif (E1, M12, 2A31), un type (qui donne ses capacités), une caserne, et éventuellement des capacités supplémentaires, l’identifiant d’unité de la radio et son alias (pour que les urgences et les positions radio la trouvent) et une agence pour l’entraide. Les nouvelles unités démarrent hors service.

Chapitre 104

Les casernes

Dans l’interface web : /admin/stations

Les casernes sont les endroits où les unités sont basées. Leurs positions placent les unités sans AVL, sont là où les redéploiements postent les unités qui couvrent, et sont là d’où partent les temps de trajet quand l’AVL d’une unité est périmé. Tapez l’adresse et choisissez-la dans les suggestions de la carte enregistrée : la position se remplit. Ou tapez la position.

Chapitre 105

Les installations réceptrices

Dans l’interface web : /admin/facilities

Les Receiving facilities sont les hôpitaux et centres spécialisés où un patient peut être amené, et si chacun prend des patients. Les équipes et la console voient le statut à côté d’une décision de transport.

  • Add une installation avec un id, un nom et un genre (hôpital, trauma, brûlés, AVC, cardiaque, psychiatrique ou autre), son téléphone et sa position.
  • Status est une pastille colorée : ouvert (prend des patients), en détournement, ou fermé. Un bouton rapide le change en un clic, et le changement est un événement du registre attribué.

Rien ici ne décide d’une destination ; cela indique aux personnes qui décident ce qui est ouvert.

Chapitre 106

Les types d’appel et les grilles de réponse

Dans l’interface web : /admin/calltypes

Un type d’appel est un genre d’incident (SF structure fire, CHEST chest pain) avec une priorité par défaut, une discipline et une grille de réponse : combien d’unités de chaque capacité il faut (« 3 × engine, 1 × ladder, 1 × als »). Les recommandations remplissent la grille de réponse. Les capacités viennent des types d’unités (Admin › Settings) et des unités.

Critical call met les personnes qui en travaillent un sur la liste de soin (chapitre 69) du superviseur ; Send a drone fait demander un drone (chapitre 65) par la règle de lancement de drone.

Auto-dispatch (types de priorité 3 à 5 seulement) : quand aucun répartiteur n’a envoyé d’unités dans le délai d’attente fixé dans Settings (60 secondes sauf changement), les unités recommandées partent d’elles-mêmes, consignées comme *auto-dispatch*. Seule une recommandation complète sans avertissements est envoyée (un lieu vérifié, chaque ligne remplie) ; sinon la chronologie dit pourquoi et un répartiteur l’envoie. Il essaie une fois par incident.

Chapitre 107

Les plans de réponse

Dans l’interface web : /admin/plans

Un response plan est un ordre de réponse : les unités qu’une agence veut, dans l’ordre prévu, quand un plan s’applique. La recommandation suit l’ordre prévu d’un plan lorsqu’il s’applique ; si une unité prévue ne peut pas partir, il dit pourquoi et qui part à la place. Une personne décide toujours.

Un plan s’applique quand toutes ses conditions correspondent à l’incident :

  • Call types : les codes sélectionnés (vide signifie chaque type).
  • Modifiers : les modificateurs sélectionnés, s’il y en a.
  • First-due station area : la zone d’une caserne, ou Anywhere.
  • Addresses : l’adresse de l’incident commence par l’une de ces lignes (une par ligne), pour un plan propre à une adresse.
  • From / To : une fenêtre d’heure de la journée (HH:MM), facultative.

L’ordre prévu est les ids des unités dans l’ordre où elles sont voulues ; ajoutez depuis la liste, réordonnez avec les boutons haut et bas, retirez-en. Un plan sans ordre ne restreint rien et est ignoré.

Chapitre 108

Enregistrer la carte

Dans l’interface web : /admin/map

bitdispatcher enregistre les données OpenStreetMap d’un cercle autour de votre centre dans son propre dépôt, puis dessine la carte de répartition, route les unités par route et trouve les adresses depuis ce dépôt sans internet.

  1. Choisissez le centre (un préréglage, le centre de la carte de la console, ou une position) et le rayon (100 miles couvre un comté et ses voisins d’entraide).
  2. Les téléchargements dont la zone a besoin sont listés aussitôt (extraits d’État de Geofabrik). Appuyez sur Record.
  3. L’enregistrement prend quelques minutes ; la répartition continue avec la carte courante, qui reste jusqu’à ce que la nouvelle soit complète. Chaque enregistrement est un événement du registre.

Bring up to date applique les fichiers de changements quotidiens d’OpenStreetMap (Geofabrik en publie un par jour par extrait) depuis l’enregistrement de la carte : quelques mégaoctets au lieu des extraits entiers, puis le dépôt est reconstruit. Enregistrez de nouveau pour une nouvelle zone, ou quand la carte a plus d’un an de retard ; les téléchargements déjà faits sont vérifiés contre leurs sommes de contrôle publiées et réutilisés.

Automatic updates

Automatic updates fait la même chose selon un horaire : désactivé, quotidien ou hebdomadaire, à l’heure que vous choisissez, dans le fuseau horaire de l’agence (Admin › Call entry rules › operational periods).

  • La nouvelle carte est bâtie à côté de celle en usage, qui continue de fonctionner pendant tout ce temps. On ne bascule vers elle que lorsqu’elle est complète et qu’elle n’a pas perdu plus que le pourcentage que vous fixez (10 par défaut) de ses segments de route ou de ses adresses ; un fichier de changements endommagé se montre comme des routes disparues, et il est refusé.
  • Une exécution qui échoue, qui n’a pas d’internet, ou qui trouve un enregistrement déjà en cours laisse la carte en usage telle qu’elle était, et la fenêtre suivante réessaie. Une exécution planifiée échouée envoie un message aux superviseurs et aux administrateurs.
  • Chaque exécution est au registre. Le panneau montre la prochaine exécution et le résultat de la dernière, tout comme la page Continuité (chapitre 75).

Les photos aériennes

Sous la carte, Aerial photos enregistre les photos autour du même centre : plein détail dans le rayon que vous choisissez (zoom 19 : toits et voitures) et moins de détail jusqu’au bord (zoom 16). L’estimation (tuiles, taille, temps) suit le formulaire ; les tuiles déjà enregistrées sont sautées, de sorte qu’un enregistrement arrêté reprend là où il était. Les sources et leurs conditions sont listées : le Virginia Base Mapping Program de VGIN pour la Virginie, USGS The National Map (NAIP, domaine public) ailleurs.

Chapitre 111

Les intégrations

Dans l’interface web : /admin/integrations

Comment bitdispatcher se connecte au traitement des appels et à la radio. Chaque intégration montre son état en direct et une liste de vérification des points d’ancrage en usage.

  • Attachments (sous Connections) : un ClamAV daemon (clamd, host:port ou son socket) analyse les fichiers d’incident et les pièces jointes des messages avant de les conserver ; un fichier qu’il signale est refusé et consigné, et si clamd est injoignable, le téléversement est refusé plutôt que conservé non analysé. Test vérifie qu’un fichier propre passe et que le fichier de test antivirus standard est attrapé. Read the words in pictures utilise le programme Tesseract sur le serveur pour la recherche (les images ne le quittent jamais) ; le texte brut et les PDF sont lus sans lui.
  • BitVoice : son adresse et son jeton d’API, et son certificat épinglé avec Read it. Voir BitVoice (chapitre 112).
  • More BitVoice systems : Add a BitVoice en suit un autre aussi, comme celui d’un PSAP voisin : son nom, son adresse, son jeton d’API, et son propre jeton EIDO et secret radio (New les crée). Ses appels montrent son nom dans la file des appels, et ce que vous faites avec l’un d’eux (texto, nouveau relevé, vidéo, photos) retourne à ce BitVoice.
  • Neighbouring agencies : leurs CAD, pour l’envoi et la réception d’incidents. Voir Les incidents avec les agences voisines (chapitre 34).
  • Supplemental location (RapidSOS, NG9-1-1 LIS) : un serveur de localisation interrogé par HELD pour l’endroit où se trouve le téléphone de l’appelant : son adresse et les identifiants que le fournisseur vous donne, Ask for every new 911 call, et Try a number. Le preneur d’appel peut appuyer sur Ask <name> sur le panneau ANI / ALI. Pas encore éprouvé contre RapidSOS lui-même (docs/SUPPLEMENTAL-LOCATION.md).
  • Public incident feed : les incidents ouverts pour la population ou des applications comme PulsePoint : adresses au pâté de cent, points à environ 100 m, sans appelants ni notes ; jeton et adresse de poussée facultatifs ; See what it shows avant de l’activer.
  • EIDO : le jeton qu’un système de traitement d’appels utilise pour pousser l’EIDO vers /api/ng911/eido.
  • Radio : le secret des webhooks radio vers /api/radio/events.
  • ALI spill : l’adresse TCP sur laquelle bitdispatcher écoute, et Test.
  • Hooks, drones and translation : le jeton de point d’ancrage pour les transcriptions, les données de collision, les rapports de drone et les paroles radio, le système de drones, et le modèle de langue facultatif. Voir Points d’ancrage et connexions (chapitre 78).

Views (le lieu sous tous les angles, voir Views (chapitre 28)) :

  • EagleView : une application sur le portail développeur d’EagleView avec l’accès à l’Imagery API sous la licence de l’agence ; son client ID et son secret. Sandbox utilise la zone de test d’EagleView (Omaha) pour l’essayer.
  • Panoramax : pas de clé ; vide utilise le catalogue de chaque instance, ou donnez l’instance propre de l’agence.
  • Mapillary : un jeton client du tableau de bord développeur de Mapillary.
  • Google Street View link : un lien seulement.
  • Test at the map's centre cherche le centre avec chaque fournisseur activé et dit ce qui est revenu. Enregistrez d’abord.

NERIS (déclaration incendie et EMS) : le NERIS ID du service (FD et huit chiffres), le client ID et le secret d’une intégration CAD obtenus de NERIS, et le nom du centre de répartition. Avec *Send each fire or EMS incident when it closes*, chaque incident clôturé ayant un type d’appel ou une unité incendie ou EMS va à NERIS comme un enregistrement CAD (heures d’appel, d’unité et de libération, le lieu, la disposition, les notes ; les unités de police laissées de côté) ; NERIS le garde en attente jusqu’à ce que le service d’incendie le complète. Check the last closed incident demande à NERIS d’en valider un sans le conserver. Les superviseurs voient *NERIS sent* (ou pourquoi il a été refusé) sur un incident clôturé, avec Send to NERIS pour le renvoyer ; un deuxième envoi met à jour le même enregistrement. Utilisez l’environnement de test de NERIS jusqu’à ce que NERIS ait vérifié l’intégration.

  • number verified (ou NOT verified) issu du contrôle STIR/SHAKEN de l’identification de l’appelant, avec l’attestation. Un contrôle échoué est une raison de douter du numéro, pas de l’urgence.
  • ESInet, le service demandé, un CAMA sur circuit ancien et comment sa localisation a été recherchée, et les moyens par lesquels le texte est arrivé (MSRP, SIP, RTT, TTY).

  • La vidéo de l’appelant s’ouvre floutée et muette ; Reveal est consigné dans le dossier d’exposition de BitVoice.
  • Un appel texto-vers-911 en attente d’un preneur d’appel : Take this text, puis répondez dans la boîte.
  • Quand un preneur d’appel transmet l’appel : le breffage de BitVoice pour qui le prend, et qui l’a transmis.
  • Après l’appel : le nom de l’enregistrement et son résumé. Le breffage et le résumé sont tous deux gardés, chacun marqué comme écrit par un modèle de langue.

Si BitVoice met fin à un appel parce que the caller's audio stopped (la ligne est devenue silencieuse et aucun raccrochage n’est venu), l’appel le dit et le panneau consultatif le lève comme un appel 911 silencieux : rappelez.

Reports › Operations report montre les temps de réponse de BitVoice (la norme NENA : 90 % en 15 secondes), qui a regardé les photos et la vidéo des appelants, et les événements de journal i3 reçus. Le voyant BitVoice dans la barre d’état passe à l’ambre quand un PSAP vers lequel l’ESInet route est plein, en panne ou sans personnel.

Chapitre 114

Les postes de travail

Dans l’interface web : /admin/workstations

Un workstation est l’un des postes de console de l’agence. Un navigateur inscrit comme poste de travail s’y connecte, et on ne demande à personne à quelle console il est : chaque action est consignée avec le poste déjà connu.

Chaque inscription et chaque révocation est un événement du registre.

Chapitre 115

Plusieurs sites

Dans l’interface web : /admin/sites

bitdispatcher tourne sur deux sites ou plus, tous en direct en même temps : un centre principal et un centre de secours, ou des comtés voisins qui partagent un système. Il n’y a pas de principal à partir duquel basculer.

  • Chaque site écrit son propre registre et copie ceux des autres par https, chaque seconde, chaque événement vérifié contre la chaîne d’empreintes de son site avant d’être conservé.
  • La même image partout : chaque site applique tous les événements dans le même ordre (par heure, puis par site), de sorte que les sites qui ont les mêmes événements montrent le même état, quel que soit l’ordre d’arrivée.
  • Coupé, un site continue de fonctionner seul ; quand le lien revient, les événements sont échangés et les deux sites convergent vers le même état. Si deux sites ont changé la même unité entre-temps, le changement le plus tardif l’emporte, aux deux.
  • Les numéros d’incident portent le préfixe de chaque site (N26-000001, S26-000001), de sorte que deux sites ne donnent jamais le même numéro.
  • Configuration : donnez à ce site un nom et un préfixe et enregistrez ; copiez son jeton et l’empreinte de son certificat vers les autres sites. Ajoutez chaque autre site avec son adresse, son jeton et son empreinte (Read it lit le certificat ; vérifiez-le contre celui montré sur ce site). La barre d’état montre combien de sites sont reliés.
Le nom et le préfixe d’un site sont écrits dans chaque événement qu’il produit, de sorte qu’ils ne peuvent plus changer une fois en usage.
Chapitre 116

Admin : continuité et overflow

Dans l’interface web : /admin/continuity

Ce que les pages Continuité (chapitre 75) et Overflow (chapitre 76) utilisent.

Les vérifications d’internet

Jusqu’à 10 adresses https que bitdispatcher interroge toutes les 30 secondes (10 à 600) ; n’importe laquelle qui répond signifie que l’internet fonctionne. Choisissez-en auxquelles le centre se fie : le portail du commutateur de messages de l’État, le fournisseur de radiomessagerie, un grand site public. Sans aucune de fixée, les consoles ne peuvent pas dire si l’internet est en service ; BitVoice, les autres sites et les voisins d’overflow sont vérifiés de toute façon.

Passer au centre de secours

  • Checklist : une étape par ligne, cochée sur la page Continuité quand le centre se déplace.
  • Contacts : le centre de secours, les voisins, l’opérateur téléphonique, l’autorité 911 ; imprimés sur le pack de continuité.

Le pack de continuité

À quelle fréquence il est écrit (1 à 240 minutes, ou pas selon un horaire) et jusqu’à 5 dossiers, en chemins complets, à côté du répertoire de données. Les fichiers ne sont lisibles que par le compte du serveur.

Overflow

Ajoutez d’abord le voisin dans Admin › Integrations › Neighbouring agencies, avec l’adresse de son CAD (https://their-cad/api/cad/eido/(l’ID qu’ils nous ont donné)) et un jeton dans chaque sens ; si leur certificat est le leur plutôt que d’une autorité, ajoutez son empreinte SHA-256 pour l’épingler. Ensuite, pour chaque voisin :

  • We may ask them to take our calls, et they may assign our units pendant qu’ils le font.
  • We take their calls when they ask, et accept their requests on our own pour un accord qui dit oui à l’avance.
  • Our agencies pour lesquelles ils peuvent prendre des appels (vide : toutes ; avec une, leurs appels sont ses incidents et seules ses unités sont partagées), et call types qu’ils peuvent utiliser (vide : tous).
  • An overflow lasts 240 minutes sauf réglage contraire ou fin.
Convenez de l’overflow par écrit avec le voisin, et avec l’autorité 911, qui met en place le routage alternatif du réseau téléphonique qui envoie les appels 911 par-dessus.
Chapitre 117

Les locaux et les dangers

Dans l’interface web : /admin/premises

Un local est ce que le centre sait d’un lieu avant que quiconque n’appelle : les hazards pour les équipes (un chien, de l’oxygène en usage, un occupant armé, une Knox box), les notes et les contacts. Il est montré avec chaque incident à moins de 40 m de lui, sur le panneau d’incident du répartiteur et sur le terminal mobile, les dangers d’abord en rouge. Un local périmé (un danger temporaire au-delà de sa date) est montré comme périmé.

  • Add a premise : tapez l’adresse et choisissez-la dans les suggestions (cela le place), cliquez les dangers courants ou tapez-en d’autres, ajoutez des notes et des contacts.
  • Search par adresse, nom, danger ou id ; cliquez sur un pour le changer ou le retirer.
  • Les superviseurs et les administrateurs changent les locaux ; tout le monde les voit. Chaque changement est un événement du registre.
  • Pre-plan photos and views : sur un local, ajoutez des photos (avec une légende et le côté d’où elles le montrent) et voyez les views (chapitre 28) du lieu. Le SHA-256 d’une photo est dans le registre : un fichier modifié sur le serveur est refusé, pas affiché.

Les locaux d’un système antérieur entrent par Migration.

Chapitre 119

Les consignes approuvées

Dans l’interface web : /admin/guidance

Les Approved guidance sont les politiques, guides de prise d’appel, guides de réponse et listes de vérification de l’agence. L’onglet Resources du preneur d’appel montre les passages correspondants avec les citations ; rien n’est inventé, seul le texte approuvé est affiché.

Un document a un id, un titre, un kind (Policy (mandatory), Guide, Prompts ou Checklist), une version, une date d’entrée en vigueur, une expiration facultative, ce qu’il remplace, et la source où se trouve la copie approuvée complète. Restreignez-le aux types d’appel, aux modificateurs ou aux mots, ou marquez-le always shown. Seul un document marqué Approved for use est montré aux preneurs d’appel.

Le texte est en Markdown avec des titres #/##/###. Les titres le divisent en passages. Sous un titre, une ligne comme Applies: CARD, CHEST; modifiers: WEAPONS; words: not breathing restreint ce passage.

  • Add the examples charge des documents d’exemple clairement intitulés comme brouillons (non approuvés), pour voir comment cela fonctionne.
  • Try it rattache un type d’appel, des modificateurs et un peu de texte et montre les passages qu’un preneur d’appel verrait, avec leur titre, leur section, leur genre, leur version et pourquoi, ou une note quand rien ne correspond.

Le statut d’un document est une pastille : approuvé ou brouillon, et périmé une fois son expiration passée.

Chapitre 120

Les protocoles de prise d’appel

Dans l’interface web : /admin/protocols

Les jeux de questions de votre agence, travaillés sur l’onglet Entry du preneur d’appel une fois l’appel soumis (docs/PROTOCOLS.md).

  • New protocol ou Start from the example (marqué *not for use*). Donnez-lui un ID, un nom et une version, et choisissez les types d’appel pour lesquels il est offert.
  • Questions : chaque réponse mène à la question suivante ou aboutit à un determinant. Make first choisit où il commence.
  • Determinants : un code, ce qu’il signifie, la priorité et le type d’appel qu’il fixe (ou garde), et les directives pour l’appelant, une par ligne.
  • Cochez Approved for calls quand votre directeur médical ou votre chef l’a approuvé ; les brouillons ne sont pas offerts. L’enregistrement vérifie que chaque réponse mène quelque part et que rien ne boucle.
  • Sur un appel : une question à la fois, les réponses sur des boutons ou les touches 1–9 ; chaque réponse est sur la chronologie, et le déterminant s’affiche sur l’incident du répartiteur.
  • Un logiciel de protocoles que vous licenciez (ProQA et autres) peut poster son déterminant au point d’ancrage à la place ; il s’affiche de la même façon, marqué avec le système.
